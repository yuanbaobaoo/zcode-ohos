# 02 运行时架构与适配层（OHOS）

平台约束（权限、V8 ABI、沙箱限制）见 [03-平台权限与系统约束.md](./03-平台权限与系统约束.md)；
本文只讲**本仓库的架构与代码结构**。

## 进程模型

```
HAP（ai.ohpc.zcode）
 └─ main 进程（Electron main，ArkTS EntryAbility 拉起）
     ├─ renderer / GPU 等 Chromium 子进程（XComponent 内 web 内容）
     └─ NodeService（utility host，appspawn 拉起，不继承 main env）
         ├─ host 服务（本地会话/任务索引/存储）
         │   └─ agent CLI = 进程内 Worker（node:worker_threads 跑 zcode.cjs，
         │       stdio 管道模拟 ChildProcess；Bash 工具子进程由 host 派生）
         └─ 终端会话池在 main（pty-main 中继，见终端节）
```

要点：

- **agent 以进程内 Worker 运行**（`zcodeAgentProcessManager.spawnZCodeAgentInProcessWorker`）：
  exec 路径全部不可用（见约束文档）后的落地形态。Worker 的 `online` 事件映射为
  适配器的 `spawn` 事件——**这是 runtime lifecycle "available" 的触发源**，
  task-index syncer 等 v4 订阅方依赖它建立 sessions-index 摄入；缺失会导致
  任务列表永远为空（勿删）。
- Worker argv 形如 `[execPath, workerFile, ...args]`（CLI 取 `slice(2)`）；
  适配器以 `defineProperty` 提供 `pid`（=threadId）/`killed`/`exitCode`/`kill`。
- `process.title` 在 Worker 内赋值会 SIGSEGV：`assignProcessTitle()` 统一收口跳过。

## 启动序列（main 进程，index.ts import 顺序即执行顺序）

```
1. desktopEarlyOhosEnvBootstrap   ← 必须最前（见下）
2. desktopEarlyDataBaseDirBootstrap
3. desktopEarlyChromiumHardwareAccelerationBootstrap
   ... 其余模块（logger 等按 getDataBaseDir() 建目录）
app.whenReady()
  ├─ ensureOhosHomeGrant()   ← 授权流程（见下）
  └─ 正常启动（窗口、host fork、服务）
```

## 早期环境引导（desktopEarlyOhosEnvBootstrap.ts）

1. **数据根**：优先真实用户 home。`/storage/Users` 在应用沙箱内通常不可见
   （mount 隔离），回退标准路径 `/storage/Users/currentUser`。
   - 写权探测 = 在 `{home}/.zcode` 内**真实落/删一个临时文件**
     （不能用 mkdir(recursive) 的成功与否判断——目录已存在时会误报）。
   - 可写 → HOME/`ZCODE_DATA_BASE_DIR`/`ZCODE_HOME` 全部指向真实 home（零交互）。
   - 不可写 → 先落应用沙箱 `/data/storage/el2/base/files` 保证启动不崩，
     置 `ZCODE_OHOS_HOME_GRANT_PENDING=1`，待授权后迁回（见授权流程）。
2. **JIT 引导**：`loadNodeSqlite()` 加载随包 sqlite 绑定，其模块初始化执行
   `prctl(PRCTL_SET_JITFORT)` 放开 V8 可执行内存。main 在此引导；host 在自身
   入口引导；agent Worker 由 host env 继承。
3. **内置 Provider 配置**：`ZCODE_BUILTIN_PROVIDER_CONFIG_FILE` 显式指向
   resfile 实际落盘位置（OHOS Electron 的 `resourcesPath` 语义与打包布局不保证对齐）。

## 用户 shell 环境注入（services/ohos/ohosUserShellEnv.ts）

**语义**：用户授权读取用户文件后，`~/.zshenv` / `~/.zprofile` / `~/.zshrc` 中
定义的环境（典型：harmonybrew 的 PATH 前置）必须对 **main / host / agent / 终端**
四端一致生效。

```
applyOhosUserShellEnvToProcessEnv()（共享模块，幂等）
  ├─ 读 ~/.zshenv → .zprofile → .zshrc（zsh 加载顺序）
  ├─ 解析单行 export（alias/函数/多行值跳过；$HOME/~/ 展开）
  ├─ PATH：按文件顺序重放（$PATH 为插入位，支持前置/后置/整体替换，去重）
  ├─ 其他变量：仅补齐应用未定义的键（管理键 HOME/ZCODE_*/XDG_* 等不覆盖）
  └─ harmonybrew 兜底：直探测 /storage/Users/currentUser/.harmonybrew（顶层
     readdir 不可用，见约束文档），PATH 前置 bin:sbin，ZCODE_OHOS_BREW_PREFIX 下发

双入口执行（appspawn env 隔离，main 的注入 host 继承不到）：
  ├─ main：desktopEarlyOhosEnvBootstrap（数据根解析通过后）
  └─ host：host/index.ts 入口（任何 agent Worker spawn 之前）
       └─ agent Worker env = sanitize(process.env) + 显式项 → Bash 子进程继承
终端：main 持有会话池，resolveTerminalEnv(main process.env) 经中继下发 shell
```

## 授权流程（desktopOhosHomeGrant.ts）

首个窗口就绪后，若授权待办：`dialog.showOpenDialog`（defaultPath=用户 home，
「授权此目录」）→ ArkTS 层 `UriGrantHelper` 持久化 URI（冷启动 `activateSaved`
自动复活）→ 探测写权通过后 `setDataBaseDir(真实home)` 并更新 HOME/ZCODE_* env
（之后 fork 的 host/agent 子进程继承）。拒绝则写标记文件不再打扰，
删沙箱内 `ohos-home-grant.json` 可重新触发。

已知问题：授权后**本会话**已按沙箱启动的 host 不自动迁移，需重启应用
（v1 可接受；后续可在授权成功回调里重建 host）。

## sqlite 后端（shared/nodeSqliteCompat.ts）

```
loadNodeSqlite()
  ├─ 非 OHOS → 真实 node:sqlite（Node ≥22.5，行为与上游一致）
  └─ OHOS → 候选逐一加载 + 真实读写自检（数组/对象/宽参数全覆盖）：
      1. zcode_sqlite.node   —— 本仓库自有 NAPI 绑定（ohos/native/zcode-sqlite，
         app 根 + HAP libs 两份；libs 份被 hvigor strip 去符号属正常）
      2. ohos_sqlite_adapter.node —— 发行包绑定（经 OhosDatabaseSync 包装绕过
         其缺陷：写语句 run() 空转、裸命名参数绑 NULL；backup 用 VACUUM INTO 等价）
      └─ 全失败 → 抛含全部失败原因的诊断错误
```

**Smi 参数铁律**：数字绑定参数只走 cb_info 位置通道（根因与规则见约束文档）。
包装层 `wrapStatementPositional` 负责数组/对象 → 位置参数展开；native 侧
run/get/all 的 argv 按实际 argc 动态分配（cap 256）。
自有绑定价值：语义正确、用户域签名（宿主可直测）。
配套回归：`.ohos-test/nodeSqliteCompat.test.mjs`（支持
`ZCODE_SQLITE_TEST_MODULE` 直测绑定本体）。

## 终端（pty-main 中继）

```
renderer xterm ──RPC──▶ host terminalService ──专用 MessagePort──▶ main desktopTerminalPtyRelay
                                                              ├─ 首选：node-pty 真 pty（forkpty）
                                                              └─ 降级：stdio 管道 + 应用层行级回显
                                                                   └─ sh -i（/bin/sh，系统 rootfs 可 exec）
```

- 降级原因（ptmx SELinux / el1 noexec / 系统 zsh 不可见）见约束文档；
  平台开放 ptmx 后首选路径自动接管
- 协议与实现：`services/terminal/ohosTerminalPty.ts`（host 客户端 + IPty 中继，
  注意 Electron utility MessagePort 的 `{data, ports}` 包装）、
  `desktop/main/desktopTerminalPtyRelay.ts`（main 会话池 + 探针组 + 回显变换：
  `\r`→回显、`\u007f`→`\b \b`）
- 中继端口随 init-local 转移（`terminalPtyAttached` 标志，`e.ports[1]`）
- shell 候选：`ZCODE_OHOS_SHELL`（随包 zsh，el1 noexec 未解除前不生效）→
  `$SHELL` → zsh/bash 候选 → `/bin/sh`；`resolveTerminalEnv` 前置 brew bin/sbin

## JIT / WebAssembly（进程矩阵）

| 进程 | JIT 来源 | WebAssembly |
|---|---|---|
| main / host / agent（Node 侧） | 早期引导 `loadNodeSqlite()` 触发 prctl(PRCTL_SET_JITFORT) | 随 JIT 恢复 |
| renderer / GPU 等 Chromium 子进程 | `kernel.ALLOW_WRITABLE_CODE_MEMORY` 声明 → libadapter 不再注入 jitless | ✅（CDP 实证实例化执行成功） |

## 出站平台标识（shared/runtimeEnv.ts）

- `isOhosRuntime()`：平台分支统一入口（`@types/node` 无 "openharmony"，避免 TS2367）
- `mapOutboundPlatformKey()`：openharmony→linux，应用于服务端上报
  （client/configs、release manifest、builtin cache、force update、context prompt）
- `assignProcessTitle()`：进程名赋值收口（OHOS 下 `process.title` 赋值 SIGSEGV）

## 其他适配

- `fs/promises.glob`：Node 20 无此 API 且命名导入在 ESM 链接期即崩；
  `sshConfigAlias.ts` 改运行时检测 + 字面量回退
- autoUpdater：OHOS 禁用（HAP 分发无更新通道）
- ARMS：init 失败降级为错误日志不阻断启动
- node-pty：OHOS prebuild 注入 `prebuilds/openharmony-arm64/`
- 运行时 spawn 的登录 shell env 探测（`runtimeLoginShellEnvCapture`）：OHOS 下
  直接返回 null（spawn 链路风险大于收益，环境注入由上述共享模块承担）
