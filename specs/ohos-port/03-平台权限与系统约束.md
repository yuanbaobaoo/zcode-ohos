# 03 平台权限与系统约束

适配层依赖的**平台事实清单**：每条约束对应代码中的对策，破坏对策会崩溃或功能回退。改适配层代码前先过一遍本文。

环境与终端统一按**用户 zsh 登录环境**描述：HiShell 与 HarmonyBrew 是这套环境的常见来源，不是适配目标；应用不识别、不探测任何包管理器前缀。

## 系统权限（module.json5）

| 权限 | 作用 | 缺失后果 |
| --- | --- | --- |
| `CUSTOM_SANDBOX`（ACL） | 允许 exec **用户目录 ELF**（zsh 环境里的工具链） | 终端/agent 执行用户安装的工具报 EPERM（toybox 文案与"未安装"相同） |
| `kernel.ALLOW_WRITABLE_CODE_MEMORY`（受限 ACL） | 阻止 libadapter 向 Chromium 进程注入 jitless | renderer 退回解释执行，WebAssembly 不可用 |
| `READ_WRITE_USER_FILE`（user_grant） | 读真实用户 home（rc、用户工具） | 用户 shell 环境注入失效 |
| `ACCESS_USER_FULL_DISK`（manual_settings） | home 以外未授权路径读写；引导见 [08](./08-全盘文件权限引导.md) | 沙箱外文件不可读 |
| `CUSTOM_SCREEN_CAPTURE`（user_grant） | `@ohos.screenshot` 截屏 + 帧流录屏 | 截图/录屏不可用 |
| `CONTROL_DEVICE`（manual_settings） | 输入注入、跨应用拉起、应用枚举 | 电脑控制整体不可用 |

ACL 类权限由 debug Profile 携带（签名材料生成时申请）。电脑控制的**聚合门禁**只要求
`CONTROL_DEVICE + CUSTOM_SCREEN_CAPTURE` 两个权限（见 [13](./13-本机电脑控制.md)）。

## 授权 API 语义（决定 UX 的关键）

| API | 适用权限类型 | 行为 |
| --- | --- | --- |
| `requestPermissionsFromUser(ctx, [perm])` | user_grant | 弹窗；必须在窗口就绪/前台后调用（`onCreate` 阶段会返回 -1） |
| `requestPermissionOnSetting(ctx, [perm])` | **仅** user_grant 且被用户撤销 | 弹窗；传 manual_settings 必报 `12100014`（SDK 契约，since 21） |
| `openPermissionOnSetting(ctx, perm)` | **仅** manual_settings | 直接打开该权限的系统设置页（since 22） |

- `12100014` 不是运行时缺陷：`CONTROL_DEVICE` / `ACCESS_USER_FULL_DISK` 是 manual_settings，
  弹窗类 API 不接受这种类型。旧代码用 `requestPermissionOnSetting` 请求它们，因此必然失败。
- manual_settings 权限只能由用户在设置页手动开启；API 不可用时回退
  `startAbility({ bundleName: 'com.huawei.hmos.settings', …, uri: 'application_info_entry',
  parameters: { pushParams: 'ai.ohpc.zcode' } })` 到应用信息页。
- 设置页开关要求应用**先停止**（运行中切换会提示"请关闭应用后修改"且可能不生效）；
  `atm perm -g/-c` 只对 user_grant 生效，manual_settings 无法脚本授权。
- manual_settings 的「屏幕共享」开关还会触发**生物识别确认**；本产品不依赖它（见下）。

## 截屏与录屏

- **截图唯一路径**：`@ohos.screenshot.capture({ displayId })`（公开 API，`@atomicservice`，
  `@since 14`）+ `image.createImagePacker()` 编码 JPEG。只需 `CUSTOM_SCREEN_CAPTURE`。
  真机实测返回 3120×2080、约 380–540KB。
- **被系统拒绝的是 AVScreenCapture 自定义录屏**：`desktopCapturer` 元数据可枚举但取帧永不
  返回；renderer `getDisplayMedia` 挂起；系统日志 `Verify custom screen recording failed`。
  这不是"鸿蒙没有三方截屏能力"。
- **录屏 = 截屏帧流**：`record_start/record_stop` 以 1–5 fps 连续截图（JPEG 落
  `computer-control/recordings/<session>/`），因此只需要截屏权限，不需要
  `CUSTOM_SCREEN_RECORDING`（该权限自 2026-11-05 起不再声明）。
- 历史 native/hdcd 取屏回退已删除；失败时如实报 `unavailable`，由设置页引导授权。

## V8 / NAPI：Smi 参数铁律（最重要）

libelectron 的 V8 为间接 Local ABI，而 `v8::Object::Get` 的 Smi 快路径返回**裸 tagged 值**——
任何数字经 `napi_get_element/get_property` 进入 native 即 SEGV（被当槽位地址二次解引用）。

- 安全通道：字符串/对象/BigInt、`napi_get_cb_info` 位置参数（argv）；
- 对策：sqlite 包装层把数组/对象参数展开为位置参数；**新增任何 NAPI 取值路径必须维持"数字只走 cb_info 通道"**。

## 内核 / 沙箱约束

| 约束 | 事实 | 对策 |
| --- | --- | --- |
| io_uring 被 seccomp 拒 | syscall 425 → SIGSYS；host 不继承 env 无法注入变量 | 构建期二进制补丁（见 02） |
| el1 bundle noexec | HAP 安装区 ELF 不可 exec；不再分发随包 shell 二进制 | 终端 shell 用 main 域系统 `/usr/bin/zsh`（见 02） |
| ptmx 被拒 | openpty/forkpty 不可用 | main 托管 shell + 管道哑终端（见 02） |
| `/storage/Users` 顶层不可枚举 | readdir/glob 返回空，子目录直访正常 | `resolveOhosRealHome` 优先 `currentUser`，其次首个非隐藏目录 |
| appspawn env 隔离 | host 不继承 main env | 登录 shell 快照在 main/host 双入口各自应用（见 02） |
| 用户目录 ELF 默认禁 exec | debug_hap 域 MAC 拦截 | `CUSTOM_SANDBOX`；保持本地 debug 签名 |
| 用户文件属主被虚拟化 | `/storage/Users` 属主恒为 file_manager ≠ 应用 uid，chmod/chown 被忽略 | ssh/scp wrapper 统一加 `-F`（见 02） |
| 子进程视图由启动方式决定 | main/GPU 由 appspawn 拉起（`/usr/bin` 完整）；Renderer/NodeService 由 nativespawn 拉起（`/usr/bin` 是 0411 空挂载） | agent 用 `/bin` 或用户环境工具；shebang 由 exec shim 兜底 |
| main 同步 `child_process` 会终止应用 | 同步 spawn/execFile 任一目标都 SIGABRT；异步 spawn 可用 | 同步路径禁用；异步仅限登录 shell 采集与终端 zsh 两条登记路径 |
| `/tmp` 对应用域不可写 | 属主 uid 1076、0770 sticky | agent/终端 `TMPDIR=<realHome>/.zcode/tmp`；main 保持原值 |
| 未签名来源 ELF 副本被拦 exec | 随包 zsh 副本一律 EACCES | 终端直接使用系统 `/usr/bin/zsh` |
| AF_UNIX 路径 bind 被拦截 | `/storage/Users` 上 `listen()` EPERM | socket 落 el2 区，`ZCODE_OHOS_SOCKET_DIR` 下发 |
| 管道执行合并 stderr→stdout | agent Bash 失败时 `stderr` 为空、错误在 `stdout` | 依赖 stderr 的判定必须同时看 stdout |
| bundle 树 ELF 无执行位 | 安装区 `libs/.../electron` 与 `libelectron.so` 是 0644，stdio MCP 全起不来 | bootstrap 解析可执行 node（`ZCODE_OHOS_SPAWNABLE_NODE` → PATH → harmonybrew）；根治需打包侧加执行位 |
| `~/` 语义随授权切换 | 授权前 agent 的 `HOME` 是沙箱 el2 目录；目录授权后 main 把 `HOME`/`ZCODE_HOME` 迁到真实用户目录（`desktopOhosHomeGrant.ts`，一次性）。Agent 不应假设 `~` 指向用户文件 | 系统提示词事实卡写明：默认 `~/` 在沙箱，访问用户文件用全路径 `/storage/Users/currentUser/...`（`ohos-device/context-section.ts`） |
| `Desktop` 子目录创建 EPERM | 授权后 `Documents` 可 mkdir，`Desktop` 下新建子目录仍 EPERM（2026-11-05 实证，系统级 DAC，与全盘权限无关） | 工作区新目录放 `Documents` 或既有目录内；此边界已写入系统提示词事实卡 |
| 用户自装 CLT 的 node 无执行位 | `~/local/commandline-tools-*/node/bin/node` 0644，hvigorw/devecocli 构建报权限错（2026-11-05 dogfood 实证） | agent 首次构建前 `chmod +x`；配方已入 `ohos-dev` bundled skill |

### nativespawn 视图修复（未解，需厂商）

```
/proc/<main>/root/usr/bin/env        → /system/bin/toybox      (存在)
/proc/<node>/root/usr/bin            → mode 0411，readdir EACCES
```

平台侧没有可用挂载开关（ArkTS `startNativeChildProcess` 只有 isolation 选项；schema 无 mount
字段），启动链路在 vendor 的 `libadapter.so`。当前用 exec shim 兜住 shebang；根治需厂商把
`/usr/bin` 纳入 nativespawn 沙箱。

### LD_PRELOAD exec-shim

`native/ohos-exec-shim/exec_shim.c`（`libzcode_exec_shim.so`）拦截
`execve/execv/execvp/execvpe/posix_spawn(p)`，解析 shebang；解释器缺失时改写成
`/bin/env <命令> <脚本>` 交给 PATH 解析，存在时完全透明。

- 注入：host 引导 `LD_PRELOAD=<bundle libs>/libzcode_exec_shim.so`，作用于继承该 env 的进程树。
- **预加载只认 bundle 内库**：用户目录路径被加载器忽略；`LD_LIBRARY_PATH` 不受此限。
- 边界：host/CLI 自身与不经该 env 的 exec 不受覆盖。

## 平台身份

`isOhosRuntime()` 以 `ZCODE_OHOS_RUNTIME=1` 为权威信号（host 引导 `??=` 注入，agent / MCP /
Bash 经 env 继承）。原因：MCP 子进程可能跑在用户环境的 Linux node 里，`process.platform`
报 `linux`；只按平台名判定会让整个 CUA 退化成占位实现。信号只做加法，缺省判定与旧版一致。

## 工具链行为

- hvigor 增量不感知 resfile/libs 变化 → 装机迭代前清缓存（脚本已自动）；
- HAP libs 的 `.node`/`.so` 会被 strip 去符号 → 对账用行为验证，勿按 md5 误判；
- `app.isPackaged` 恒 false（exec 名是 electron）→ 打包态分支用 OHOS 显式守卫；
- tsup 失败不回滚 out/ → 构建有 error 时勿装机。
