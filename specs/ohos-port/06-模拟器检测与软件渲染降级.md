# 06 模拟器检测与软件渲染降级

## 背景

DevEco 模拟器（平板和 2in1 都实测过）的 GPU 直通扛不住 Chromium GPU 进程的用法：

- 现象：GPU 直通是 express_gpu → 宿主 Metal，上下文一创建就丢
  （`SharedImageStub: context already lost` → `RasterDecoderImpl: Context lost`），GPU 进程每几百毫秒
  崩一次重启，一帧都没提交，应用窗口纯黑。系统 UI 走客户机自己的合成器，所以看起来是「桌面正常、
  ZCode 窗口黑」。
- 对策：模拟器上把 GL 后端切到 ANGLE + SwiftShader（纯 CPU，编译在 libelectron.so 里）。呈现通道
  `skia_output_device_buffer_queue` 写 `OH_NativeWindow` buffer，本来就不依赖 GPU。
- 实测：注入 `use-gl=angle` + `use-angle=swiftshader` 后 GPU 进程稳定、登录页完整、可交互，CPU 约 8%。

## 判据

| 环境                         | const.product.model | const.product.name  | hardwareversion | 判定   |
| ---------------------------- | ------------------- | ------------------- | --------------- | ------ |
| 平板模拟器 MatePad Pro 13    | emulator            | emulator            | emulator        | 模拟器 |
| 2in1 模拟器 MateBook Pro     | emulator            | emulator            | emulator        | 模拟器 |
| 真机 MateBook Pro（HAD-W32） | HAD-W32             | HUAWEI MateBook Pro | L1001           | 真机   |

- 主判据：`deviceInfo.productModel === 'emulator'`。ArkTS 的 `@ohos.deviceInfo` 是免权限公开 API，
  映射到 const.product.model；再辅以 `hardwareModel`。这几个字面量是模拟器镜像写死的，真机不可能
  出现，所以零误判。
- 没采用的旁路：`ohos.qemu.hvd.name` 只在模拟器里存在，但只有 shell 能读；`/proc/cpuinfo` 和
  device-tree 在模拟器里连 shell 都没权限。app 通道用不了。

## 所有权与事件顺序

```
ArkTS 页面 aboutToAppear（NodeHandleWindow / Index 二选一被加载，均接入）
  → 同步写 <context.filesDir>/device-profile.json     [唯一写者：DeviceProfileWriter]
      （filesDir 为 haps 形态；写失败仅告警不阻断）
XComponent 创建 → adapter 拉起 electron runtime → main/index.js 顶部 import 链
  desktopEarlyOhosEnvBootstrap（修好 HOME）
  → desktopEarlyChromiumHardwareAccelerationBootstrap
  → desktopOhosRenderCompatBootstrap                   [唯一读者+决策者]
      读 device-profile.json（flat + haps 双候选）+ setting.json 三态设置
      → 决策注入 appendSwitch(use-gl=angle, use-angle=swiftshader)
      → GPU 子进程继承开关（appendSwitch 需在 app ready 前，模块顶层即满足）
```

- 顺序是保证过的：页面 `aboutToAppear` 先于 XComponent 构建（同步写盘），早于 electron main。
- 读不到 profile 一律按真机处理、不注入。这个极性是故意的：误判漏网最多回到「模拟器黑屏」的现状，
  绝不会把真机降级成软件渲染。
- profile 每次启动覆盖写，幂等，不用考虑版本迁移。

## 三态设置

`setting.json` 里加了 `desktopOhosRenderCompat`：

| 取值           | 行为             |
| -------------- | ---------------- |
| `auto`（默认） | 按上面的判据走   |
| `software`     | 强制 SwiftShader |
| `hardware`     | 强制硬件 GL      |

设置页在 OHOS 平台可见，改完要重启生效。链路是 shared zod schema + protocol + SettingsPage，和
`desktopChromiumHardwareAccelerationEnabled` 同一套 plumbing。

## 边界

- 只在 `isOhosRuntime()` 下生效；mac / win / linux 桌面构建零行为变化（文件和设置都不存在，天然 no-op）。
- 和 `app.disableHardwareAcceleration()` 独立并存：那是上游既有的全局禁硬加速能力。本机制在 v40
  模拟器的 `auto` / `software` 模式下也会调它作为稳定回退，`hardware` 模式不调。
- 平板模拟器整屏黑属于系统级图形栈崩溃，本机制只救应用窗口，系统 UI 恢复不在应用能力范围，按验收
  矩阵如实记录。

## v40 的策略

**现象**：模拟器主页交互或重绘时闪屏、黑屏，过几分钟自己恢复。hilog 里 GPU 初始化报
`libGLESv2_angle.so: No such file or directory`，随后系统 `render_service/DGLES` 持续输出
`createimage with ctx null` / `bind external with nullptr gbuffer`。

**约束有两条**：

1. v40 守卫必须按版本串的首个数字段判断 major。OHOS Electron 报的是 `v40.0.1-release`，
   `Number("v40")` 会得到 `NaN`；判错就会去注入 `use-gl=angle` + `use-angle=swiftshader`，而 HAP
   没带 ANGLE 拆分库，GPU 初始化失败后掉到软件合成。
2. 厂商的 `--use-gl=egl` 在这个模拟器上一直 `Context was lost`，GPU 进程约 0.8s 重启一次
   （`Restarting GPU process due to unrecoverable error`）；ANGLE 库又不在包内，两条 GPU 路径都不通。

**实现**：版本 major 取版本串首个数字段（`v40.0.1-release` → 40）。v40 模拟器的 `auto` /
`software` 模式调用 `app.disableHardwareAcceleration()`（Chromium 软件合成），`hardware` 模式保留
厂商 EGL（当前模拟器上仍会 Context lost，只作排查用）；pre-v40 注入 ANGLE + SwiftShader。单测覆盖
带 `v` 前缀和 `-release` 后缀的版本串、hardware 覆盖、pre-v40 注入三种情况。

**验收**：v40 下 `app.getGPUFeatureStatus().gpu_compositing` 为 `disabled_software`（预期如此），但
GPU 进程 PID 稳定、日志里没有 `Restarting GPU process`；没有 `libGLESv2_angle.so` 缺失；鼠标移动、
点击、按键连续触发重绘时设备截帧全部正常（干净重启后两轮实测 8/8 + 6/6 帧非黑）。

**别拿 DGLES 日志当判据**：系统 `render_service/DGLES` 的 `createimage with ctx null` 在正常运行
时也会以约 2Hz 出现。真正的判据是 GPU 进程重启循环，加上交互期间截帧出现整窗黑帧。另外 GPU 崩溃
循环之后，即使改回软件合成，也建议重启一次模拟器，把损坏的系统合成器状态清掉。
