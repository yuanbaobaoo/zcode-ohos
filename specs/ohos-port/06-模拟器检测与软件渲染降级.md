# 06 · 模拟器检测与软件渲染降级

## 背景与问题

DevEco 模拟器（平板 / 2in1 均实测）的 GPU 直通（express_gpu → 宿主 Metal）撑不住
Chromium GPU 进程的 EGL 用法：上下文创建即丢失（`SharedImageStub: context already lost`
→ `RasterDecoderImpl: Context lost`），GPU 进程以每数百毫秒一次的频率崩溃重启，
一帧都未提交，应用窗口纯黑。系统 UI 走客户机自身合成器不受影响，故表现为
「桌面正常、ZCode 窗口黑」。

对策：模拟器上把 GL 后端切到 ANGLE + SwiftShader（纯 CPU，编译在 libelectron.so 内），
呈现通道 `skia_output_device_buffer_queue` 写 `OH_NativeWindow` buffer 本就不依赖 GPU。
实测（2026-10-01）：注入 `use-gl=angle` + `use-angle=swiftshader` 后 GPU 进程稳定、
登录页完整渲染、可交互、CPU 占用约 8%。

## 判据（实测矩阵）

| 环境 | const.product.model | const.product.name | hardwareversion | 判定 |
| --- | --- | --- | --- | --- |
| 平板模拟器 MatePad Pro 13 | emulator | emulator | emulator | 模拟器 |
| 2in1 模拟器 MateBook Pro | emulator | emulator | emulator | 模拟器 |
| 真机 MateBook Pro（HAD-W32） | HAD-W32 | HUAWEI MateBook Pro | L1001 | 真机 |

- 主判据：`deviceInfo.productModel === 'emulator'`（ArkTS `@ohos.deviceInfo` 免权限公开
  API，映射 const.product.model）。辅以 `hardwareModel`。字面量由模拟器镜像写死，
  真机不可能出现——零误判。
- 旁路佐证（未采用，shell 才可读）：`ohos.qemu.hvd.name` 仅模拟器存在；
  `/proc/cpuinfo`、device-tree 在模拟器内连 shell 都无权限，不可作 app 通道。

## 所有权与事件顺序

```
ArkTS 页面 aboutToAppear（NodeHandleWindow / Index 二选一被加载，均接入）
  → 同步写 <context.filesDir>/device-profile.json     [唯一写者：DeviceProfileWriter]
      （filesDir 为 haps 形态；写失败仅告警不阻断）
XComponent 创建 → adapter 拉起 electron runtime → main/index.js 顶部 import 链
  desktopEarlyOhosEnvBootstrap（修好 HOME）
  → desktopEarlyChromiumHardwareAccelerationBootstrap
  → desktopOhosRenderCompatBootstrap                   [唯一读者+决策者]
      读 device-profile.json（flat + haps 双候选）+ setting.json 三态设置
      → 决策注入 appendSwitch(use-gl=angle, use-angle=swiftshader)
      → GPU 子进程继承开关（appendSwitch 需在 app ready 前，模块顶层即满足）
```

- 顺序保证：页面 aboutToAppear 先于 XComponent 构建（同步写盘），早于 electron main；
  main 侧读不到 profile 一律按真机处理（不注入），安全极性：误判漏网最多回到
  「模拟器黑屏」现状，绝不把真机降级到软件渲染。
- profile 文件每次启动覆盖写（幂等，无版本迁移问题）。

## 三态设置（兜底）

`setting.json` 新增 `desktopOhosRenderCompat`：`auto`（默认，按判据）/
`software`（强制 SwiftShader）/ `hardware`（强制硬件 GL）。设置页 OHOS 平台可见，
改动需重启生效。shared zod schema + protocol + SettingsPage 全链路，与
`desktopChromiumHardwareAccelerationEnabled` 同款 plumbing。

## 边界

- 仅 `isOhosRuntime()`（process.platform === 'openharmony'）生效；mac/win/linux 桌面
  构建零行为变化（文件与设置均不存在，天然 no-op）。
- `app.disableHardwareAcceleration()` 与本机制独立并存：前者是全局禁硬加速的既有
  上游能力，本机制只做 OHOS 模拟器的 GL 后端选择。
- 平板模拟器系统级图形栈崩溃（整屏黑）场景：本机制只救应用窗口，系统 UI 恢复
  不在应用能力范围（如实按验收矩阵记录）。

## 验收场景

1. 2in1 模拟器：默认（auto）→ UI 完整渲染、GPU 进程稳定不重启循环。（2026-10-01 实测通过，
   子进程命令行含 use-gl=angle/use-angle=swiftshader，截图亮度 101.1）
2. 平板模拟器：同上装机验证，结果如实记录（系统 UI 状态不影响判定应用窗口）。
   （实测记录：进程级闪退——SIGTRAP(TRAP_BRKPT)@libelectron.so+0x667be24，崩溃线程
   Chrome_InProcGp，app 存活 2~5s 后循环退出；注入前旧构建在同一地址同样崩溃，
   即与本机制无关。成因是该镜像图形栈整体损坏（连系统桌面的合成输出都是坏的），
   且 GPU 走进程内线程（Chrome_InProcGpuThread），CHECK 失败直接带走整个 app。
   结论：平板模拟器列为不支持环境。）
3. 真机：默认（auto）→ 硬件 GL 不受影响（hilog GPU 进程无 use-gl=angle），UI 正常。
   （2026-10-01 实测通过：零注入痕迹，UI 完整渲染）
4. 真机改 `software` 重启 → SwiftShader 生效（证明开关通路）；改回 auto 恢复。
5. profile 文件缺失/损坏 → 不注入，行为与现状一致（不崩、不降级真机）。
6. 单测：parse 判废矩阵、emulator 判据、flat/haps 候选推导、三态决策表。
   （4/4 通过；4 的 UI 侧需登录态，自动化未覆盖，留人工验收）
