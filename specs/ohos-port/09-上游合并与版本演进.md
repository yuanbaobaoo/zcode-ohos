# 09 上游合并与版本演进

上游 ZCode 与鸿蒙移植是**同源不同运行时**：业务代码跟随上游，平台适配集中在 OHOS 层。
本文记录合并边界、冲突分类、验证清单与版本史；具体平台事实见 [02](./02-运行时架构与适配层.md)/[03](./03-平台权限与系统约束.md)。

## 合并流程

1. `git fetch upstream <commit>`，用 `merge-tree --write-tree` 演练（不落地）；
2. 按「内容冲突 / modify-delete / rename 自动合并 / 接缝文件」四类分派（见下）；
3. 冲突解决后先跑 `pnpm typecheck`，再跑 `pnpm test:engineering` 与 `pnpm architecture:check -- --changed`；
4. 真机装机冒烟（见验证清单）；
5. 合并提交单独一笔，不与平台功能混提。

## 冲突分类（v3.17.1 实测）

| 类型 | 典型文件 | 处理 |
| --- | --- | --- |
| 内容冲突 | `package.json`、`architecture-policy.yaml`、i18n、`bash.ts`、`autoUpdater.ts` | 取上游结构 + 原样保留 OHOS 专属行/分支 |
| modify/delete | 上游删除的旧单测（14 个） | 以 OHOS 版本迁入 `engineering-test-files.json` |
| rename 自动合并 | `scripts/engineering-tests/scope.mjs` | 逐行核对 `origin/main` 基线改造没丢 |
| 接缝文件 | `host/index.ts`、`services/node.ts`、`TerminalSession.tsx`、`App.tsx`、`main/index.ts` | 自动合并成功也要逐项核对 OHOS 符号 |

## 静默风险清单

| 风险 | 现状 | 处理 |
| --- | --- | --- |
| OHOS 单测退役失效 | 根 `vitest.config.ts` 只跑 `scripts/engineering-test-files.json` 清单 | OHOS 测试必须登记进清单；未登记即被 `retired-app-unit-evidence` 判退役 |
| affected 基线 | `scope.mjs` 上游仍硬编码 `origin/staging` | 本仓保持 `origin/main`，每次合并后核对 |
| pre-push 新门禁 | 要求工作区干净 + 多项检查 | 合并解冲突后先 commit 再 push |
| Electron 44 类型 vs 40 运行时 | typecheck 用 44 类型，运行时 40.1 | 新 API 调用逐面真机冒烟；不假设编译通过=可运行 |
| 构建期 define | `__ZCODE_TELEMETRY_REPORT_ENDPOINT__` 等上游注入 | 核对 tsup / bundle / agent bundle 链同样注入 |
| 新增 `node:sqlite` / `Promise.withResolvers` | OHOS 已运行 Node 24，原生支持 | 仍需确认 `nodeSqliteCompat` 钩子没被绕过 |

## 验证清单

- `pnpm typecheck` / `pnpm lint` / `pnpm architecture:check -- --changed`；
- `pnpm test:engineering`（受影响的清单文件）；
- 真机冒烟：启动、终端、agent 会话、MCP（node_repl）、`ohos_hdc shell`、devecocli 设备列表、
  截图/录屏、电脑控制开关与权限门禁；
- 关键路径日志：`bridge ready`、`permissions refreshed`、`screenshot ok`、`devecocli device list`。

## 历史教训

- 上游删除的单测会连带移除 OHOS 的回归保护：合并前先 `git diff --diff-filter=D` 找出被删测试，
  再决定迁入清单还是补等价工程测试。
- 自动合并成功 ≠ 语义正确：OHOS 的接缝往往只有一行（如 `formatModelContent`），
  逐文件核对比看冲突数更可靠。
- 平台适配不要写进上游业务文件：优先扩展点/薄包装，合并成本与文件改动数成正比。
