# 02 运行时架构与适配层

移植过程按「遇到的问题 → 解法」记录；平台事实的根因见 [03](./03-平台权限与系统约束.md)。

## 进程模型

```
HAP（ai.ohpc.zcode）
 └─ main（Electron main，ArkTS EntryAbility 拉起）
     ├─ renderer / GPU（Chromium 子进程，XComponent 内 web 内容）
     └─ NodeService host（appspawn 拉起，不继承 main env）
         ├─ host 服务（会话/任务索引/存储）
         │   └─ agent CLI = 进程内 Worker（worker_threads 跑 zcode.cjs）
         └─ 终端会话池在 main（shell 由 main 域托管）
```

## 问题 → 解法（按适配点）

**agent 无法独立进程**（exec 链路受限；随包 HNP 曾报 9568407——官方错误码语义为「native 软件包损坏」，根因是当时手工 zip 打包、未用 SDK `hnpcli pack`，非分发渠道限制）
→ agent 以 host **进程内 Worker** 运行，stdio 管道模拟 ChildProcess；Worker `online` 事件映射为 spawn 事件，是 runtime lifecycle "available" 的触发源（任务列表依赖，勿删）。

**agent Worker 的 stdout 是 JSON-RPC 协议专用通道，OHOS 适配代码严禁 `console.log`**（2026-10-20 装机实证：nodeSqliteCompat 的 `console.log("[ohos-sqlite] backend loaded")` 落进协议管道，宿主 JSON.parse 失败即 protocol_parse_error 断链 → agent 无限重生 → 30 个 Worker isolate 23 秒堆到 4.4GB RSS → V8 Allocation failed SIGABRT 带崩整个 NodeService；faultlogger 的 `Heap::CollectGarbage` 栈顶只是 OOM 落点不是病因）。规则：OHOS 下任何会被 agent Worker 加载的模块（@zcode/shared 的 sqlite/compat 链路），日志一律 `console.error`/serviceLogger。诊断面补强：transport 异常关闭落 warn（带肇事帧首 300 字符）、worker stderr 实时落 serviceLogger，均在 `packages/services/src/zcode-agent/`。另注意：OHOS worker_threads 的 `exit` 事件在 stdout 异常关闭场景可能不触发，进程回收不能只靠 exit。

**seccomp 拒 io_uring（syscall 425）→ 任一进程首次异步文件 IO 即 SIGSYS**，且 host 由 appspawn 拉起不继承 env、无法用 `UV_USE_IO_URING=0` 注入
→ 构建期对 libelectron.so 做 4 字节×2 二进制补丁禁用 io_uring（`ohos-patch-libelectron.mjs`，按 `UV_USE_IO_URING` 字符串地址反查 adrp/add 引用对做动态锚定——2026-10-20 起不再硬编码指令字节，新旧基线通吃；幂等，纯 Node）。

**沙箱默认禁 RWX → V8 保留 CodeRange 直接 OOM**
→ 各进程入口早期 `loadNodeSqlite()` 触发 JIT 解锁：首选绑定 `zcode_sqlite.node` 模块初始化自带 `prctl(0x6a6974, …)`（选项号 ASCII 即 "jit"，与 adapter 二进制反汇编实证一致）；兼容层在旧二进制（无 prctl）命中时额外加载 adapter 仅取其解锁副作用（过渡兜底，全部产物换新二进制后可移除）。agent 经 host env 继承；Chromium 侧靠 `ALLOW_WRITABLE_CODE_MEMORY` 权限阻止 jitless 注入。

**HOME 对应用常无写权**（首个 logger mkdir 即 EPERM）
→ main 最早引导做**真实落文件**的写权探测（mkdir 成功不代表可写）；可写则以真实 home 为数据根，不可写先落应用沙箱保启动，首窗就绪后弹一次目录授权（ArkTS UriGrantHelper 持久化），授权后迁回。

**GUI 应用继承不到用户 zsh 登录环境，agent 的非交互 spawn 不读 rc 文件 → 工具链全不可见**
→ 共享模块 `services/ohos/ohosUserShellEnv.ts` 在 **main 与 host 双入口**注入用户 shell 环境（appspawn env 隔离），agent Worker、Bash 子进程与终端 shell 都从 host env 继承。
用户环境**只有登录 shell 快照 v3 一个来源**：不再静态重放 rc、不探测或前置任何包管理器前缀（exec shim 只解决脚本执行，不提供 PATH，见 03）；首个 Host spawn 前等待快照落盘（有界 4s），此后 agent 与终端都从 host env 继承。HiShell 与 HarmonyBrew 只是这个 zsh 环境的常见来源；应用把它们当普通用户配置，不识别、不特判。

**登录 shell 快照 v3：main 采集、落盘、host 合并（与用户 zsh 登录环境同构）**
→ main 引导后**异步**跑 `/usr/bin/zsh -ilc 'env -0'`（与用户在 HiShell 或任意终端里打开的是同一个 shell、同一套 rc；标记对提取防 rc stdout 污染，12s 超时）。采集参数是根因所在：`cwd=<realHome>`——rc 里的工具链初始化要求 cwd 对进程 uid 可读，cwd=`/` 时 shellenv 类脚本直接失败（真机实证 "current working directory must be readable"）；**显式最小基线 env**（`HOME/PATH/LANG/TMPDIR/TERM=dumb`）而非继承 `process.env`，同时避免内部变量泄漏与 PATH 逐次叠层。结果剔除 `_/SHLVL/PWD/OLDPWD/TERM` 与空值，落盘 `<realHome>/.zcode/v2/ohos-login-env.json`（v3：`{version, capturedAt, shell, cwd, env}`）。
→ 应用：PATH 用快照**整体替换**（rc 完整演算结果，唯一来源）；其余键覆盖，`SHELL_EXPORT_SKIP_KEYS` 保护 HOME/XDG/TMPDIR 等应用管理键。**无快照**（首次启动采集未完成/失败）时保持引导自身 PATH，不做任何 rc 重放——下次启动由快照自愈；main 在首个 Host spawn 前等待快照（`awaitRuntimeEnvReady`，4s 超时，见 09 接缝）。**采集仅在 main**：host 视图无 `/usr/bin/zsh`（见 03），且 main 异步 spawn 不触发 clone3 SIGSYS。文件即 main→host 传输通道。

**TMPDIR = `~/.zcode/tmp`（与用户 zsh 环境功能等价的有意偏离）；socket 目录单独走 el2**
→ 平台 `/tmp` 属主 1076、`0770`，应用 uid 无写权（真机实证，见 03）；HiShell 的登录环境用 `TMPDIR=$HOME`。zcode 取 `<realHome>/.zcode/tmp`：与 `/storage/Users` 同一文件系统，临时文件 move 到工作区不会 `EXDEV`；启动时请求 `0700` 创建（真机实测落成 `0771`，与 `.zcode` 同级权限，属平台虚拟化层的既有行为，见 03），只在 host（agent）与终端生效，main 保持原值；`TMPDIR` 进 `SHELL_EXPORT_SKIP_KEYS`，用户 rc 不能改回不可用路径。
→ **AF_UNIX 路径型 bind 在 `/storage/Users` 被虚拟化层拦截（EPERM，真机实证 `znr-*.sock`）**，socket 不能跟随 TMPDIR：host 引导另建 `/data/storage/el2/base/files/tmp` 并经 `ZCODE_OHOS_SOCKET_DIR` 下发，node-repl broker 优先使用该目录（其余 tmpdir 用法仍是文件操作，可留在真实 home）。

**agent 命令无缝：LD_PRELOAD exec shim（改写缺失解释器的 shebang）**
→ agent 视图没有 `/usr/bin/env`，包管理器安装的 shim 脚本（`#!/usr/bin/env node`）在 agent 里一律失败。host 引导注入 `LD_PRELOAD=<bundle libs>/libzcode_exec_shim.so`（native/ohos-exec-shim），Bash/MCP/插件子进程在执行脚本时被改写为 `/bin/env …` 交 PATH 解析；解释器存在时透明（主进程/终端本就有 /usr/bin，不受影响，机制与边界见 03）。

```
main 引导 ── 采集 v3（cwd=realHome, 最小基线） ──落盘──► v2/ohos-login-env.json
host 引导 ── 有快照：PATH 整体替换 + 用户键覆盖；无快照：保持引导 PATH ──► agent Worker / Bash
终端      ── main 域 spawn `/usr/bin/zsh -il`（env 随 spawn 消息下发：快照 PATH/LD_PRELOAD/TMPDIR）；rc 幂等叠加
（快照由 main 每次启动重写；host 启动读到的可能是上一次的——下次启动自愈，可接受）
```

**终端 shell = Main 域托管（系统 zsh 只在该域可见）**
→ 三个候选域的真机结论（2026-10-27）：**native child（nativespawn）域**没有 `/usr/bin` 且禁止 exec 非系统 ELF（bundle libs/el2/用户目录副本全 EACCES）；**host 域**同样没有 `/usr/bin/zsh`，用户目录只可 exec「平台认可来源」的 ELF（用户从包管理器安装的副本可、随包 zsh 副本一律被拦，与路径/权限无关）；**main 域**有系统 `/usr/bin/zsh` 且异步 spawn 可用（登录 shell 快照采集就是在这里跑 `zsh -ilc`）。
→ 因此终端固定走 **Main 中继托管 shell**：main 以 `child_process.spawn` 起 shell（`/usr/bin/zsh -il`；候选系统 zsh → main 落盘的 hint → `/bin/sh`），管道 stdio + 行级回显（无 tty，`\n` 补 `\r`，spec 09 §12.9）；host env（快照 PATH、LD_PRELOAD、TMPDIR）随 spawn 消息下发。没有 native child 或 host 本地管道等其他回退通道；用户看到的 zsh 与 HiShell 里的交互 shell 同源。

**应用域裸 `ssh`/`scp` 不可用（用户报障「HiShell 的其他环境拿不到，比如 SSH」的根因）**
→ 两层断点（真机实证，见 03）：① `/storage/Users` 属主被虚拟化层固定为 20001006，ssh 读默认路径 config 强制「属主==进程 uid」→ `Bad owner or permissions` 退出；HiShell 侧的解法是 rc 里配 `ssh -F ~/.ssh/config` 的 **alias**——alias 不在 env 里，spawn 的子进程永远继承不到。② host rootfs 视图无 `/usr/bin/ssh`。
→ 解法：引导时在 `<realHome>/.zcode/bridge/bin/` 生成 `ssh`、`scp` wrapper（幂等；存在 `~/.ssh/config` 才生成；应用桥接产物目录，与用户自己的 bin 隔离——历史版本曾用 `.zcode/bin`，ensure 时按「内容带生成标记」迁移清理，用户自放文件不动）。候选链 = `/usr/bin` → `/bin` → 运行时 PATH（登录快照，排除 wrapper 自身目录），统一追加 `-F <realHome>/.ssh/config` 跳过属主校验；wrapper 目录**前置**进 PATH（最前，遮蔽系统 ssh）。应用内 `ssh hsl` 与用户 zsh 环境行为对齐；zcode 自身远程连接走 ssh2 库 + `ssh -G -F`（`sshConfigAlias.ts`）不受此坑影响。

**OHOS 不是 Linux：UA 仍报 Linux；main 进程的同步 spawn 仍会终止应用（异步 spawn 按实测限点使用）**
→ 两个表现同源：① 渲染进程按 `navigator.userAgent` 判定平台，OHOS 落入 Linux 分支，设置页因此显示「Computer Use 暂不支持 Linux 桌面环境」；② 远程连接选择 Docker 时，渲染进程经 IPC 让 main 调 `isDockerAvailable()` → `execFile("docker", ["version"])`，主进程随即死亡。
→ **崩溃机制（2026-10-22 模拟器隔离实验）**：不是 Docker、不是动态 import，也不是「找不到二进制」——在 main inspector 里 `execFile("/bin/echo")`、`spawn("/bin/true")`、`execFile("docker")`（缺失目标）结果一致：`execFile(…)` 调用**同步阶段**应用即死（调用后的 JS 不再执行），appspawn 报 `ai.ohpc.zcode with pid … exit with signal:6`，hilog 无 JS 异常、faultlogger 无 cppcrash；只加载 `node:child_process` 不 spawn 则存活。JS 层 `process.on("SIGABRT")` 捕不到（自发 `process.kill(pid,"SIGABRT")` 亦不可捕获），因此进程内无法兜底。崩溃进程 `Seccomp=0`、`CapEff=0`；应用视角 `/usr/bin/zsh` 不存在，所以启动期登录 shell 快照（`captureOhosLoginShellEnv`，异步 spawn）在该模拟器上从未执行。SIGABRT 的具体发送方（内核 `pids.fork_denied` 还是运行时 abort）未取得栈，结论基于信号、时序与隔离实验。**真机修正（2026-10-27，HarmonyOS 7 PC）**：main 域**异步** `spawn` 可用——登录 shell 快照采集与终端 zsh 都依赖它且稳定运行，模拟器上的整体击杀未在真机复现。平台规则与证据一致：普通应用不能自由 fork+exec，进程创建优先 appspawn/native child（Electron 的 `utilityProcess.fork` 承载 host）；异步 spawn 的可用范围按真机实测登记，见下条约束。
→ 影响面与守卫：渲染进程的 OHOS 判定由 preload 同步暴露 `window.zcode.isOhosRuntime`（UA 在 OHOS 上报 Linux，不可用），经 `IPlatformService.isOhos` 进入 UI——电脑控制新增 `local-ohos` 文案分支；远程连接**保留 Docker 入口**，选中后展示「HarmonyOS 设备不支持 Docker 连接，请改用 SSH」并禁用连接按钮（不发起探测）。`desktopRuntimeEnv` 的两个 docker 探测经 `isMainProcessExternalCommandAllowed` 在动态导入前短路；**同样在 main 可达的 `ssh -G` 探测**（`listSSHConfigAliasesFromLocalConfig`，`~/.ssh/config` 存在且含别名时触发）在 OHOS 直接跳过 spawn，改用配置文件解析结果。其余 main 侧 `child_process` 调用点经审计均被平台或功能门禁挡住（macOS Finder/图标/CUA、Windows 菜单、Linux XDG/托盘、Chrome 导入未在 `desktopPlatform` 暴露），并由 `packages/desktop/test/desktopMainChildProcessGuard.test.ts` 做登记制防回归。**约束：OHOS 的 main 进程禁止同步 `child_process`（`spawnSync`、`process.binding("spawn_sync")`、executor 同步路径）；异步 `spawn` 仅限已登记的登录 shell 采集与终端托管，新增调用点先判断平台并登记 `desktopMainChildProcessGuard`。**

**Node 20.18 无 `node:sqlite`，发行包自带绑定有三处缺陷**（写语句 run() 空转、裸命名参数绑 NULL；API 26 起数组整参绑定失效，自检必挂）
→ 自有 NAPI 绑定 `zcode_sqlite.node`（C 源在 `packages/desktop/native/ohos-zcode-sqlite/`，交叉编译，语义对齐 node:sqlite）优先，发行包绑定包装兜底；统一入口 `shared/nodeSqliteCompat.ts`，回归测试 `packages/shared/test/nodeSqliteCompat.test.ts`。约束（issue #1 复盘）：

- 候选路径覆盖两种安装布局（均真机实证）：HNP/electron 物化布局走 `bundle/electron/…`（resfile 副本 + electron/libs）；HarmonyOS 7 PC 上 electron/libs 不物化，HAP 根 `libs/arm64-v8a` 被系统抽取归一化为 `bundle/libs/arm64`。**adapter 与 zcode 候选必须覆盖同一布局集**——只给兜底补路径会让首选后端静默落空、装机即崩。
- 打包必须双份复制（resfile app 根 + HAP libs；utility/host 进程的 `.node` require 有 loader 重定向到 bundle libs，无 libs 副本则 host 进程加载失败）；产物缺失时 build-ohos.mjs 先自动编译（build.sh 自带 CLT clang 探测），失败即硬失败——静默 WARN 降级曾产出装机必崩的 release 包（CI 无编译步骤 + libs 旧二进制入库掩盖）。
- 候选 `existsSync` 落空必须计入最终报错（probed-missing），否则报错里看不到首选后端被跳过的痕迹，误判为后端本身损坏。

**`/dev/ptmx` 对应用域被 SELinux 拒 → 无伪终端**（fork+exec 本身正常）
→ shell 由 main 托管、经专用 MessagePort 与 host 中继（`desktopTerminalPtyRelay.ts` + `ohosTerminalPty.ts`）。没有 pty，stdio 就是管道：换行（`\n` 补 `\r`）与按键回显由应用层补，无 vim/top 全屏（已知代价）。OHOS 不走 node-pty，也不分发它的 OHOS prebuild。

**终端秒退曾把 Host 整体拖死（任务/插件/模型列表永久转圈的根因）**：管道 shell 秒退 → 终端注册表即删 → renderer 晚到的 `terminal.onDynamicData` 订阅在 Host 的 RPC listen 处理器里同步抛 `Terminal not found` → 逃出成 Host `uncaughtException` → dispose + `exit(1)` → 窗口 workspace RPC 无人应答且 main 不重生。
→ 三层修复：`terminalService` 退出后保留短期墓碑（晚到订阅补发退出码、write/resize 幂等丢弃）；`OhosRelayPty` 闩住早于订阅的退出事件；`packages/rpc` 的 `channelServer.onEventListen` 加异常边界（单个事件 getter 同步抛只杀该订阅）。另新增 `PlatformChannels.LocalHostExited`：main 在 Host 意外退出（非主动 dispose）时通知窗口，renderer 弹「重新加载窗口」恢复入口（reload 后 dom-ready 走全新 spawn，旧宿主已从 windowHostProcessMap 摘除）。

**HAP 打包链过滤 resfile 里点开头的文件/目录 → 官方插件在 OHOS 从未可用**（实证：HAP 内 `packages/*/README.md` 等普通文件俱在、`.zcode-plugin/` 与 `.mcp.json` 全部丢失；插件协议以 `.zcode-plugin/plugin.json` 为存在性证据与 seed 清单，全部落空且全程零日志）。另：CLI 进程内 Worker 的 argv/\_\_dirname/cwd 启发式定位本身也不可靠，需宿主显式注入。
→ 双保险：① build-ohos stage 时把点条目平铺成非点副本（`zcode-flat/plugin.json`、`zcode-flat/mcp.json`，打包日志 `glm dot entries flattened` 计数），CLI（bundled-plugins.ts `flatFileCanonicalPath`）反向还原为标准路径——seed 写出的缓存形态跨平台一致；② main 解析资源根（双形态证据）→ `HostInitMessage.bundledResourceDir`（fork env 在 OHOS 传不进 host，见 03）→ host 落 `process.env.ZCODE_BUNDLED_RESOURCE_DIR` → agent spawn env 透传进 Worker → CLI `candidateBaseDirs()` 置顶该目录。seed 源缺失时每进程打一次 warn（带候选目录实际值），此类故障不再无声。验证通道：应用内终端 `echo $ZCODE_BUNDLED_RESOURCE_DIR` 应输出 glm 路径（终端 env 继承 host process.env）。
**`fs/promises.glob` 在 Node 20 ESM 链接期即崩**（命名导入存在性检查）
→ `sshConfigAlias.ts` 改运行时检测 `iterateGlobMatches()`，缺失回退字面量匹配。

**出站平台标识**：服务端不认 `openharmony` key → `isOhosRuntime()` 统一平台分支入口，`mapOutboundPlatformKey()` 对外按 linux 上报；`process.title` 赋值 SIGSEGV、`app.isPackaged` 恒 false → `assignProcessTitle()` 收口 + 显式守卫。

**`shell.openPath(目录)` 在 OHOS 静默失效**——OHOS Electron 把 openPath 映射为 viewData Want（找默认应用打开），目录没有处理器只会弹应用选择器；且适配层 `LaunchHelper` 对 startAbility 失败只记 hilog、同步恒报成功，主进程连失败日志都不会有，表现为「在文件管理器中打开」点击无反应。
→ main 的 `openPathInFileManager`（`desktopMainIpcHelpers.ts`）增加 OHOS 分支改用 `shell.showItemInFolder`：OHOS Electron 将其映射为 `filemanager://openDirectory` appLink（`FileManagerAdapter.openItemInFolder`），系统文件管理器 `com.huawei.hmos.filemanager` 注册了该 scheme/host，可直接定位目录（真机已验证）；UI 侧传入的已是所在目录路径。macOS `open` 与其余桌面平台 `shell.openPath` 分支不变。`shell.openPath(文件)` 的 viewData 语义对文件仍可用（有默认应用或弹打开方式），不受影响。

**「打开方式」下拉在 OHOS 恒空**——mac Finder / win Explorer 以伪编辑器身份进入编辑器列表，OHOS 编辑器 defs 为空；且系统文件管理器是系统 ability，没有可 stat 的应用包路径（路径探测必失败），目录路径也无扩展名、拿不到 UTD 文件图标（`getFileIcon` 链路必失败）。
→ `getEditorDefsForCurrentPlatform()` 增加 OHOS 分支返回 `filemanager` 伪编辑器 def（`openInEditor` 入口的 def 门禁要求 id 必须在列表内）；`getInstalledEditors()` 增加 OHOS 分支跳过路径探测与 `getFileIcon`，直接输出内联常量图标、名称按系统语言（zh「文件管理器」/en「Files」）；`openInEditor()` 增加 `filemanager` 分支复用 `shell.showItemInFolder`（真机验证：传入文件 URI 时文件管理器打开所在目录，语义同 Finder/Explorer）；UI 侧 `openWithEditors.ts` 的 pin 列表加入 `filemanager`（「打开方式」置顶 + 工作区头部快捷按钮）。第三方编辑器（VS Code 等）检测仍为后续项。

## 已知限制

终端无全屏交互（哑终端）；包管理器自身的自更新/自修复命令不可用（依赖 `/proc/self/exe`，其安装的工具不受影响）；无项目即席对话不入任务列表（与桌面版行为待对齐）；「打开方式」在 OHOS 仅内置「文件管理器」伪编辑器，第三方 App（VS Code 等）检测未接入。
