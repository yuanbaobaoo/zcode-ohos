# 02 运行时架构与适配层

移植过程按「遇到的问题 → 解法」记录；平台事实的根因见 [03](./03-平台权限与系统约束.md)。

## 进程模型

```
HAP（ai.ohpc.zcode）
 └─ main（Electron main，ArkTS EntryAbility 拉起）
     ├─ renderer / GPU（Chromium 子进程，XComponent 内 web 内容）
     └─ NodeService host（appspawn 拉起，不继承 main env）
         ├─ host 服务（会话/任务索引/存储）
         │   └─ agent CLI = 进程内 Worker（worker_threads 跑 zcode.cjs）
         └─ 终端会话池在 main（pty-main 中继）
```

## 问题 → 解法（按适配点）

**agent 无法独立进程**（exec 链路受限；随包 HNP 曾报 9568407——官方错误码语义为「native 软件包损坏」，根因是当时手工 zip 打包、未用 SDK `hnpcli pack`，非分发渠道限制）
→ agent 以 host **进程内 Worker** 运行，stdio 管道模拟 ChildProcess；Worker `online` 事件映射为 spawn 事件，是 runtime lifecycle "available" 的触发源（任务列表依赖，勿删）。

**seccomp 拒 io_uring（syscall 425）→ 任一进程首次异步文件 IO 即 SIGSYS**，且 host 由 appspawn 拉起不继承 env、无法用 `UV_USE_IO_URING=0` 注入
→ 构建期对 libelectron.so 做 4 字节×2 二进制补丁禁用 io_uring（`ohos-patch-libelectron.mjs`，内容定位、幂等、纯 Node）。

**沙箱默认禁 RWX → V8 保留 CodeRange 直接 OOM**
→ 各进程入口早期 `loadNodeSqlite()` 触发 JIT 解锁：首选绑定 `zcode_sqlite.node` 模块初始化自带 `prctl(0x6a6974, …)`（选项号 ASCII 即 "jit"，与 adapter 二进制反汇编实证一致）；兼容层在旧二进制（无 prctl）命中时额外加载 adapter 仅取其解锁副作用（过渡兜底，全部产物换新二进制后可移除）。agent 经 host env 继承；Chromium 侧靠 `ALLOW_WRITABLE_CODE_MEMORY` 权限阻止 jitless 注入。

**HOME 对应用常无写权**（首个 logger mkdir 即 EPERM）
→ main 最早引导做**真实落文件**的写权探测（mkdir 成功不代表可写）；可写则以真实 home 为数据根，不可写先落应用沙箱保启动，首窗就绪后弹一次目录授权（ArkTS UriGrantHelper 持久化），授权后迁回。

**GUI 应用继承不到 HiShell 登录环境，agent 的非交互 spawn 不读 rc 文件 → brew 工具全不可见**
→ 共享模块 `services/ohos/ohosUserShellEnv.ts` 解析 `~/.zshenv/.zprofile/.zshrc` 的单行 export（PATH 按文件顺序重放），在 **main 与 host 双入口**各自执行（appspawn env 隔离），agent Worker 与 Bash 子进程经 env 继承；终端由 main 经 pty 中继下发。
静态重放吃不到动态语句（`eval "$(brew shellenv)"`、alias、source 链），harmonybrew 靠前缀兜底救回；其余动态环境由**登录 shell 快照**补齐（见下条）。

**登录 shell 快照：main 采集、落盘、host 合并（补齐 rc 动态环境的唯一正路）**
→ main 引导后异步跑 `/usr/bin/zsh -ilc 'env -0'`（标记对提取防 rc stdout 污染，12s 超时，失败保持静态重放结果），与采集基线（采集时 process.env）做**差集**后落盘 `<realHome>/.zcode/v2/ohos-login-env.json`（v2）——差集只含 rc 新增/改值的键，采集 shell 继承的 main 内部变量（`OHOS_SOCKET_AppSpawn`、`NODE_PATH` 等，真机实证曾泄漏）天然剔除，因此**无需白名单、全量继承**；main/host 双入口在静态重放后读取合并（PATH 用快照整体替换——它是 rc 完整演算结果；其余差集键补缺不覆盖，SKIP_KEYS 防应用管理键）。**采集仅在 main**：host 的 rootfs 视图无 `/usr/bin/zsh`（见 03），且 main **异步** spawn 不触发 clone3 SIGSYS（同步才拦，见 03）。文件即 main→host 传输通道（appspawn env 隔离，跨进程 IPC 无必要）。

```
main 引导 ──静态重放──► 读上次快照合并 ──► 异步采集（zsh -ilc env -0 −基线=差集）──落盘──► v2/ohos-login-env.json
host 引导 ──静态重放──► 读快照合并（PATH=快照；差集键补缺）──► agent Worker / Bash 子进程继承
（快照由 main 每次启动重写；host 启动读到的可能是上一次的——下次启动自愈，可接受）
```

**终端 shell = 系统 zsh 登录交互 shell（终端面板完整复刻 HiShell）**
→ shell 解析在 host（appspawn 视图无 `/usr/bin/zsh`），但实际 exec 在 main 的 pty 中继——main 视图可用（真机实证 zsh 5.9）。**通道注意：`utilityProcess.fork` 的 env 参数在 OHOS 传不进 appspawn 拉起的 host（装机实证 `ZCODE_OHOS_SHELL` 恒缺失，终端因此落 `/bin/sh`）**，改用与快照同目录的 hint 文件：main 引导把 `resolveOhosBundledZshPath()`（候选链系统 zsh 优先，随包 zsh 在 el1 noexec 起不来）的解析结果写 `<realHome>/.zcode/v2/ohos-terminal-shell`，host 的 `resolveTerminalShell` 读取（`ZCODE_OHOS_SHELL` env 仍优先——适配层未来修复 fork env 后自动接管）。spawn 参数：zsh 加 `-l`（pty 正规路径与管道哑终端降级 `spawnPipeShell` 的 `-il` 都是登录+交互）→ 读全部 rc（`.zshenv/.zprofile/.zshrc/.zlogin`），alias、prompt、动态 export 与 HiShell 一致；sh（toybox）保持仅 `-i`。终端 env 仍经 `resolveTerminalEnv` 注入（PATH/wrapper/brew 前置），zsh 的 rc PATH 演算幂等叠加。

**应用域裸 `ssh`/`scp` 不可用（用户报障「HiShell 的其他环境拿不到，比如 SSH」的根因）**
→ 两层断点（真机实证，见 03）：① `/storage/Users` 属主被虚拟化层固定为 20001006，ssh 读默认路径 config 强制「属主==进程 uid」→ `Bad owner or permissions` 退出；HiShell 侧的解法是 rc 里配 `ssh -F ~/.ssh/config` 的 **alias**——alias 不在 env 里，spawn 的子进程永远继承不到。② host rootfs 视图无 `/usr/bin/ssh`。
→ 解法：静态重放时在 `<realHome>/.zcode/bridge/bin/` 生成 `ssh`、`scp` wrapper（幂等；存在 `~/.ssh/config` 才生成；应用桥接产物目录，与用户自己的 bin 隔离——历史版本曾用 `.zcode/bin`，ensure 时按「内容带生成标记」迁移清理，用户自放文件不动），wrapper 内候选链 `brew/bin/ssh → /usr/bin/ssh` 自适应两端 rootfs 视图，统一追加 `-F <realHome>/.ssh/config` 跳过属主校验；wrapper 目录**前置**进 PATH（最前，遮蔽系统 ssh）。应用内 `ssh hsl` 与 HiShell 行为对齐；zcode 自身远程连接走 ssh2 库 + `ssh -G -F`（`sshConfigAlias.ts`）不受此坑影响。

**Node 20.18 无 `node:sqlite`，发行包自带绑定有三处缺陷**（写语句 run() 空转、裸命名参数绑 NULL；API 26 起数组整参绑定失效，自检必挂）
→ 自有 NAPI 绑定 `zcode_sqlite.node`（C 源在 `packages/desktop/native/ohos-zcode-sqlite/`，交叉编译，语义对齐 node:sqlite）优先，发行包绑定包装兜底；统一入口 `shared/nodeSqliteCompat.ts`，回归测试 `packages/shared/test/nodeSqliteCompat.test.ts`。约束（issue #1 复盘）：
- 候选路径覆盖两种安装布局（均真机实证）：HNP/electron 物化布局走 `bundle/electron/…`（resfile 副本 + electron/libs）；HarmonyOS 7 PC 上 electron/libs 不物化，HAP 根 `libs/arm64-v8a` 被系统抽取归一化为 `bundle/libs/arm64`。**adapter 与 zcode 候选必须覆盖同一布局集**——只给兜底补路径会让首选后端静默落空、装机即崩。
- 打包必须双份复制（resfile app 根 + HAP libs；utility/host 进程的 `.node` require 有 loader 重定向到 bundle libs，无 libs 副本则 host 进程加载失败）；产物缺失时 build-ohos.mjs 先自动编译（build.sh 自带 CLT clang 探测），失败即硬失败——静默 WARN 降级曾产出装机必崩的 release 包（CI 无编译步骤 + libs 旧二进制入库掩盖）。
- 候选 `existsSync` 落空必须计入最终报错（probed-missing），否则报错里看不到首选后端被跳过的痕迹，误判为后端本身损坏。

**`/dev/ptmx` 对应用域被 SELinux 拒 → 无伪终端**（fork+exec 本身正常）
→ pty 改由 main 进程创建、经专用 MessagePort 与 host 中继（`desktopTerminalPtyRelay.ts` + `ohosTerminalPty.ts`）；ptmx 仍被拒时降级 stdio 管道 + 应用层行级回显的哑终端（无 vim/top 全屏，已知代价；平台开放后 node-pty 首选路径自动接管）。

**`fs/promises.glob` 在 Node 20 ESM 链接期即崩**（命名导入存在性检查）
→ `sshConfigAlias.ts` 改运行时检测 `iterateGlobMatches()`，缺失回退字面量匹配。

**出站平台标识**：服务端不认 `openharmony` key → `isOhosRuntime()` 统一平台分支入口，`mapOutboundPlatformKey()` 对外按 linux 上报；`process.title` 赋值 SIGSEGV、`app.isPackaged` 恒 false → `assignProcessTitle()` 收口 + 显式守卫。

**`shell.openPath(目录)` 在 OHOS 静默失效**——OHOS Electron 把 openPath 映射为 viewData Want（找默认应用打开），目录没有处理器只会弹应用选择器；且适配层 `LaunchHelper` 对 startAbility 失败只记 hilog、同步恒报成功，主进程连失败日志都不会有，表现为「在文件管理器中打开」点击无反应。
→ main 的 `openPathInFileManager`（`desktopMainIpcHelpers.ts`）增加 OHOS 分支改用 `shell.showItemInFolder`：OHOS Electron 将其映射为 `filemanager://openDirectory` appLink（`FileManagerAdapter.openItemInFolder`），系统文件管理器 `com.huawei.hmos.filemanager` 注册了该 scheme/host，可直接定位目录（真机已验证）；UI 侧传入的已是所在目录路径。macOS `open` 与其余桌面平台 `shell.openPath` 分支不变。`shell.openPath(文件)` 的 viewData 语义对文件仍可用（有默认应用或弹打开方式），不受影响。

**「打开方式」下拉在 OHOS 恒空**——mac Finder / win Explorer 以伪编辑器身份进入编辑器列表，OHOS 编辑器 defs 为空；且系统文件管理器是系统 ability，没有可 stat 的应用包路径（路径探测必失败），目录路径也无扩展名、拿不到 UTD 文件图标（`getFileIcon` 链路必失败）。
→ `getEditorDefsForCurrentPlatform()` 增加 OHOS 分支返回 `filemanager` 伪编辑器 def（`openInEditor` 入口的 def 门禁要求 id 必须在列表内）；`getInstalledEditors()` 增加 OHOS 分支跳过路径探测与 `getFileIcon`，直接输出内联常量图标、名称按系统语言（zh「文件管理器」/en「Files」）；`openInEditor()` 增加 `filemanager` 分支复用 `shell.showItemInFolder`（真机验证：传入文件 URI 时文件管理器打开所在目录，语义同 Finder/Explorer）；UI 侧 `openWithEditors.ts` 的 pin 列表加入 `filemanager`（「打开方式」置顶 + 工作区头部快捷按钮）。第三方编辑器（VS Code 等）检测仍为后续项。

## 已知限制

终端无全屏交互（哑终端）；`brew` 本体命令不可用（依赖 /proc/self/exe，装的工具不受影响）；无项目即席对话不入任务列表（与桌面版行为待对齐）；「打开方式」在 OHOS 仅内置「文件管理器」伪编辑器，第三方 App（VS Code 等）检测未接入。
