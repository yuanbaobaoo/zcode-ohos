# 02 运行时架构与适配层

每条适配都按同样的顺序写：**平台约束 → 我们的做法 → 注意什么**。平台为什么长这样，见
[03](./03-平台权限与系统约束.md)；哪些功能在鸿蒙上直接不可用，见 [21](./21-上游能力可用性清单.md)。

## 进程模型

```
HAP（io.github.yuanbaobaoo.zcode）
 └─ main（Electron main，ArkTS EntryAbility 拉起）
     ├─ renderer / GPU（Chromium 子进程，XComponent 内 web 内容）
     └─ NodeService host（appspawn 拉起，不继承 main env）
         ├─ host 服务（会话/任务索引/存储）
         │   └─ agent CLI = 进程内 Worker（worker_threads 跑 zcode.cjs）
         └─ 终端会话池在 main（shell 由 main 域托管）
```

## 适配点

### 1. agent 跑在 host 进程里

- 约束：exec 链路受限，agent 起不了独立进程。
- 做法：host 里用 `worker_threads` 跑 `zcode.cjs`，stdio 管道模拟 ChildProcess；Worker 的 `online`
  事件映射成 spawn 事件，是 runtime lifecycle "available" 的触发源，任务列表靠它，别删。
- 注意：Worker 的 stdout 是 JSON-RPC 专用通道，能被 agent 加载的模块（`@zcode/shared` 的
  sqlite/compat 链路）一律不准 `console.log`，否则宿主 parse 失败、`protocol_parse_error` 断链，
  还可能引发 agent 无限重生——统一用 `console.error` 或 serviceLogger。
- 注意：worker 的 `exit` 在 stdout 异常关闭时可能不触发，进程回收不能只靠它。transport 异常关闭
  时只落 warn（带帧长度与哈希，不落原始帧内容），worker 的 stderr 实时落 serviceLogger
  （`packages/services/src/zcode-agent/`）。

### 2. seccomp 拒绝 io_uring

- 约束：syscall 425 一被调用就 SIGSYS，任一进程首次异步文件 IO 触发；host 由 appspawn 拉起，
  不继承 env，没法用 `UV_USE_IO_URING=0` 注入。
- 做法：构建期给 `libelectron.so` 打 4 字节 ×2 的二进制补丁，禁用 io_uring
  （`ohos-patch-libelectron.mjs`，按 `UV_USE_IO_URING` 字符串地址反查 adrp/add 引用对做动态锚定，
  幂等，纯 Node）。

### 3. 沙箱默认禁 RWX，V8 CodeRange 直接 OOM

- 做法：各进程入口早期调 `loadNodeSqlite()` 触发 JIT 解锁。首选绑定 `zcode_sqlite.node` 在模块
  初始化里自带 `prctl(0x6a6974, …)`（选项号 ASCII 就是 "jit"）；兼容层在没有 prctl 的绑定上再加载
  adapter 取解锁副作用。agent 经 host env 继承。
- 另：Chromium 侧靠 `ALLOW_WRITABLE_CODE_MEMORY` 权限阻止 jitless 注入。

### 4. HOME 对应用通常不可写

- 约束：首个 logger 的 mkdir 就 EPERM。
- 做法：main 最早引导时做一次真实落文件的写权探测（mkdir 成功不代表可写）。可写就把真实 home
  当数据根；不可写先落应用沙箱保证能启动，首窗就绪后弹一次目录授权（ArkTS `UriGrantHelper`
  持久化），授权后再迁回来。

### 5. 拿不到用户的 zsh 登录环境

- 约束：GUI 应用继承不到登录环境，agent 的非交互 spawn 也不读 rc，工具链不可见。
- 做法：`services/ohos/ohosUserShellEnv.ts` 在 main 和 host 两个入口注入用户 shell 环境。
  唯一来源是「登录 shell 快照 v3」：不静态重放 rc，也不探测或前置任何包管理器前缀。
- 说明：exec shim 只解决脚本执行，不提供 PATH（见第 8 条）。
- 说明：HiShell、HarmonyBrew 只是这个 zsh 环境常见的来源，应用当普通用户配置处理，不识别、
  不特判。

### 6. 登录 shell 快照 v3

- 采集（main）：引导后异步跑 `/usr/bin/zsh -ilc 'env -0'`，和用户终端同一个 shell、同一套 rc；
  用标记对提取防止 rc 的 stdout 污染，12s 超时。`cwd=<realHome>`（rc 里的工具链初始化要求 cwd
  对进程 uid 可读），给一份最小基线 env（`HOME/PATH/LANG/TMPDIR/TERM=dumb`），不继承
  `process.env`。
- 落盘：剔除 `_/SHLVL/PWD/OLDPWD/TERM` 和空值，写到 `<realHome>/.zcode/v2/ohos-login-env.json`，
  格式 v3 = `{version, capturedAt, shell, cwd, env}`。
- 应用（host）：PATH 用快照整体替换，其余键覆盖；`SHELL_EXPORT_SKIP_KEYS` 保护
  HOME/XDG/TMPDIR 这些应用自己管的键。没有快照就保持引导自身的 PATH。
- 时序：main 在首个 Host spawn 前等快照落盘（`awaitRuntimeEnvReady`，4s 超时）。采集只在 main
  做：host 视图里没有 `/usr/bin/zsh`，而 main 的异步 spawn 不会触发 clone3 SIGSYS。

```
main 引导 ── 采集 v3（cwd=realHome, 最小基线） ──落盘──► v2/ohos-login-env.json
host 引导 ── 有快照：PATH 整体替换 + 用户键覆盖；无快照：保持引导 PATH ──► agent Worker / Bash
终端      ── main 域 spawn /usr/bin/zsh -il（env 随 spawn 消息下发：快照 PATH/LD_PRELOAD/TMPDIR）
（快照由 main 每次启动重写；host 启动读到的可能是上一次的，下次启动自愈）
```

### 7. 临时目录与 socket 目录

- TMPDIR：平台 `/tmp` 属主 1076、权限 `0770`，应用 uid 写不了。改用 `<realHome>/.zcode/tmp`——
  和 `/storage/Users` 同一文件系统，临时文件 move 到工作区不会 `EXDEV`；启动时按 `0700` 创建；
  只对 host（agent）和终端生效，main 保持原值；`TMPDIR` 进 `SHELL_EXPORT_SKIP_KEYS`。
- socket：AF_UNIX 路径型 bind 在 `/storage/Users` 被虚拟化层拦（EPERM），所以 socket 不跟 TMPDIR
  走。host 引导另建 `/data/storage/el2/base/files/tmp`，经 `ZCODE_OHOS_SOCKET_DIR` 下发，
  node-repl broker 优先用它；其余 tmpdir 用法还是文件操作，留在真实 home。

### 8. 缺 `/usr/bin/env`：用 exec shim 改写 shebang

- 约束：agent 视图没有 `/usr/bin/env`，包管理器装的 shim 脚本（`#!/usr/bin/env node`）跑不起来。
- 做法：host 引导注入 `LD_PRELOAD=<bundle libs>/libzcode_exec_shim.so`（`native/ohos-exec-shim`），
  Bash / MCP / 插件子进程执行脚本时，把缺失解释器的 shebang 改写为 `/bin/env …` 交给 PATH 解析。
- 说明：解释器存在时透明。

### 9. 终端 shell 由 main 托管

- 约束：native child（nativespawn）域没有 `/usr/bin`，也禁止 exec 非系统 ELF；host 域没有
  `/usr/bin/zsh`；main 域既有系统 `/usr/bin/zsh`，异步 spawn 也可用。
- 做法：main 用 `child_process.spawn` 起 `/usr/bin/zsh -il`（候选：系统 zsh → main 落盘的 hint →
  `/bin/sh`），管道 stdio 加行级回显；host env（快照 PATH、LD_PRELOAD、TMPDIR）随 spawn 消息下发。
  没有 native child 或 host 本地管道回退。用户看到的 zsh 与 HiShell 里的交互 shell 同源。
- 代码：`desktopTerminalPtyRelay.ts`（main 侧中继）+ `ohosTerminalPty.ts`（host 侧接口），两者经专用
  MessagePort 通信。

### 10. 没有 PTY（`/dev/ptmx` 被 SELinux 拒）

- 说明：缺的是 PTY 设备，不是 shell。shell 仍是系统 `/usr/bin/zsh -il`，日常命令、登录环境、
  cwd、别名和历史都正常。fork+exec 本身也没问题。
- 被 PTY 带走的是四件事：
  1. 行规程：内核 echo、DEL、`\r`→`\n`，现在由应用层 `echoTransform` / `#normalizeOutput` 补；
  2. 信号与作业控制：Ctrl-C/Ctrl-Z 不再由终端驱动转 SIGINT/SIGTSTP，`fg`/`bg` 没意义；
  3. `termios` 与窗口尺寸：`isatty()` 为 false、`cols/rows=0`、`resize()` 是空实现；
  4. 依赖前三者的全屏 TUI：vim / top / less 退化成 dumb，或直接报 not a terminal。
- 说明：OHOS 不走 node-pty，也不分发它的 OHOS prebuild。

### 11. 终端秒退会把 Host 拖死

- 现象：管道 shell 秒退 → 终端注册表立刻删 → renderer 晚到的 `terminal.onDynamicData` 订阅在
  Host 的 RPC listen 处理器里同步抛 `Terminal not found` → Host `uncaughtException` →
  dispose + `exit(1)` → 窗口 workspace RPC 无人应答，main 也不会重生。
- 三层防护：`terminalService` 退出后保留短期墓碑（晚到订阅补发退出码，write/resize 幂等丢弃）；
  `OhosRelayPty` 闩住早于订阅的退出事件；`packages/rpc` 的 `channelServer.onEventListen` 加异常
  边界（单个事件 getter 同步抛只杀该订阅）。
- 恢复入口：Host 意外退出时 `PlatformChannels.LocalHostExited` 通知窗口，renderer 弹「重新加载
  窗口」；reload 后 dom-ready 走全新 spawn，旧宿主已从 windowHostProcessMap 摘除。

### 12. 裸 `ssh`/`scp` 不可用，改走 wrapper

- 原因一：`/storage/Users` 属主被虚拟化层固定成 20001006，ssh 读默认路径的 config 时强制
  「属主 == 进程 uid」→ `Bad owner or permissions`；rc 里的 `ssh -F` alias 不在 env 里，
  spawn 出来的子进程继承不到。
- 原因二：host rootfs 视图里没有 `/usr/bin/ssh`。
- 做法：引导时在 `<realHome>/.zcode/bridge/bin/` 生成 `ssh`、`scp` wrapper（幂等；存在
  `~/.ssh/config` 才生成；和用户自己的 bin 隔离；旧位置 `.zcode/bin` 里带生成标记的会被清理，
  用户自己放的文件不动）。候选链 = `/usr/bin` → `/bin` → 运行时 PATH（登录快照，排除 wrapper
  自身目录），统一追加 `-F <realHome>/.ssh/config`；wrapper 目录前置进 PATH，遮蔽系统 ssh。
- 边界：zcode 自身的远程连接走 ssh2 + `ssh -G -F`（`sshConfigAlias.ts`），不受这个坑影响。

### 13. 平台身份与「不能同步 spawn」

- 平台身份：OHOS 的 UA 仍报 Linux，所以渲染进程的判定由 preload 同步暴露
  `window.zcode.isOhosRuntime`，再经 `IPlatformService.isOhos` 进 UI——电脑控制用 `local-ohos`
  文案分支；远程连接保留 Docker 入口，选中后提示「HarmonyOS 设备不支持 Docker 连接，请改用 SSH」
  并禁用（不发起探测）。
- Docker 探测：`desktopRuntimeEnv` 的两个 docker 探测经 `isMainProcessExternalCommandAllowed`
  在动态导入前短路；`ssh -G` 探测（`listSSHConfigAliasesFromLocalConfig`）在 OHOS 直接跳过
  spawn，改用配置文件解析结果。
- 硬约束：OHOS 的 main 进程禁止同步 `child_process`（`spawnSync`、
  `process.binding("spawn_sync")`、executor 同步路径）；异步 `spawn` 只允许已登记的登录 shell
  采集和终端托管。新增调用点先判断平台，再登记到
  `packages/desktop/test/desktopMainChildProcessGuard.test.ts`。

### 14. 没有 `node:sqlite`，用自有 NAPI 绑定

- 约束：Node 20.18 没有 `node:sqlite`；发行包自带的绑定有三个缺陷（写语句 `run()` 空转、裸命名
  参数绑 NULL；API 26 起数组整参绑定失效）。
- 做法：自研 NAPI 绑定 `zcode_sqlite.node`（C 源在 `packages/desktop/native/ohos-zcode-sqlite/`，
  交叉编译，语义对齐 node:sqlite）优先，发行包绑定包装兜底；统一入口
  `shared/nodeSqliteCompat.ts`，回归测试 `packages/shared/test/nodeSqliteCompat.test.ts`。
- 约束一：候选路径要覆盖两种安装布局——HNP/electron 物化布局走 `bundle/electron/…`（resfile
  副本 + electron/libs）；HarmonyOS 7 PC 上 electron/libs 不物化，HAP 根 `libs/arm64-v8a` 会被
  系统抽取归一化成 `bundle/libs/arm64`。adapter 与 zcode 的候选必须覆盖同一套布局，否则首选
  后端静默落空、装机即崩。
- 约束二：打包必须双份复制（resfile app 根 + HAP libs）。utility/host 进程的 `.node` require
  有 loader 重定向到 bundle libs，少了 libs 副本 host 就加载失败；产物缺失时 `build-ohos.mjs`
  会先自动编译（build.sh 自带 CLT clang 探测），失败即硬失败——静默 WARN 降级会产出装机必崩的包。
- 约束三：候选的 `existsSync` 落空要计入最终报错（probed-missing），否则看不到首选后端被跳过。

### 15. 表快照迁移读 BLOB 时 host SIGSEGV

- 现象：迁移备份逐行哈希，`sort_key` 是 BLOB；自有绑定用
  `napi_create_external_arraybuffer(…, NULL finalizer)` 输出 BLOB 会崩（而且内存永久泄漏）。
- 做法：改成 `napi_create_arraybuffer` 加 memcpy，迁移与备份恢复正常。

### 16. HAP 打包会过滤点开头的文件

- 约束：resfile 里 `.zcode-plugin/`、`.mcp.json` 这类点条目会被打包链过滤，官方插件内容因此缺失
  （插件协议以 `.zcode-plugin/plugin.json` 作为存在性证据）。另外 CLI 进程内 Worker 的
  argv/`__dirname`/cwd 启发式定位不可靠，需要宿主显式注入。
- 做法一：build-ohos 在 stage 阶段把点条目平铺成非点副本（`zcode-flat/plugin.json`、
  `zcode-flat/mcp.json`，打包日志里有 `glm dot entries flattened` 计数），CLI
  （`bundled-plugins.ts` 的 `flatFileCanonicalPath`）反向还原成标准路径。
- 做法二：main 解析资源根 → `HostInitMessage.bundledResourceDir`（fork env 在 OHOS 传不进 host）
  → host 落 `process.env.ZCODE_BUNDLED_RESOURCE_DIR` → agent spawn env 透传到 Worker → CLI 的
  `candidateBaseDirs()` 把这个目录置顶。seed 源缺失时每进程打一次 warn，带候选目录的实际值。
- 验证：应用内终端 `echo $ZCODE_BUNDLED_RESOURCE_DIR` 应输出 glm 路径。

### 17. 几个零散的 Node 20 / API 差异

- `fs/promises.glob`：Node 20 在 ESM 链接期就会因为命名导入不存在而崩。`sshConfigAlias.ts`
  改为运行时检测 `iterateGlobMatches()`，缺失时回退字面量匹配。
- 出站平台标识：服务端不认 `openharmony` 这个 key，平台分支统一收口到 `isOhosRuntime()`，
  对外用 `mapOutboundPlatformKey()` 按 linux 上报。
- 进程名：`process.title` 赋值会 SIGSEGV，`app.isPackaged` 恒 false，前者收口到
  `assignProcessTitle()`，后者用显式守卫处理。

### 18. 打开目录、打开方式

- `shell.openPath(目录)` 在 OHOS 静默失效：openPath 映射成 viewData Want，目录没有处理器只会弹
  应用选择器；而 `LaunchHelper` 对 startAbility 失败只记 hilog，同步恒报成功。
- 目录改走 `shell.showItemInFolder`：`openPathInFileManager`（`desktopMainIpcHelpers.ts`）的
  OHOS 分支映射成 `filemanager://openDirectory` appLink（`FileManagerAdapter.openItemInFolder`），
  注册方是系统文件管理器 `com.huawei.hmos.filemanager`，能直接定位；`openPathInDefaultApp` 对目录也转
  `showItemInFolder`。`shell.openPath(文件)` 的 viewData 语义对文件仍然可用。
- 「打开方式」下拉在 OHOS 是空的：mac Finder / win Explorer 是以伪编辑器身份进列表的，OHOS 的
  编辑器 defs 为空（系统文件管理器是系统 ability，没有可 stat 的应用包路径；目录路径也没扩展名，
  拿不到 UTD 图标）。做法：`getEditorDefsForCurrentPlatform()` 的 OHOS 分支返回 `filemanager`
  伪编辑器 def（`openInEditor` 的入口校验要求 id 在列表内）；`getInstalledEditors()` 跳过路径
  探测和 `getFileIcon`，输出内联常量图标、名称按系统语言（zh「文件管理器」/ en「Files」）；
  `openInEditor()` 的 `filemanager` 分支复用 `shell.showItemInFolder`；UI 侧
  `openWithEditors.ts` 的 pin 列表加入 `filemanager`（置顶 + 工作区头部快捷按钮）。
- 尚未做：第三方编辑器（VS Code 等）的检测。

### 19. 通知与退出清理

- 通知：Electron Notification 落成 OHOS 系统通知，生命周期比应用长。适配层
  `NotificationAdapter` 用 `notificationManager.publish` 发布，`tapDismissed:false`（点击不消除），
  点击走 WantAgent 拉起应用；通知归 DistributedNotificationService 所有，进程退出不会自动撤销。
  main 侧 `desktopNotifications.ts` 在超上限逐出旧通知时同步 `close()`，但真正生效的清理在 ArkTS。
- 退出：Electron 的 quit 生命周期在 OHOS 不执行——关窗后进程由系统直接终结，
  `before-quit`/`will-quit`/`exit` 都不跑。依赖它的清理挪到 ArkTS `EntryAbility.onDestroy`
  （系统保证调用）；现行例子是退出时 `notificationManager.cancelAll()`。

### 20. 预装工具链在鸿蒙没有可用目标

- 事实：`packages/desktop/src/preinstalled-tools/catalog.json` 只登记了 darwin/arm64|x64，
  `loadPreinstalledToolsCatalog` 按 `process.platform/arch` 解析后是空的，安装与回收流程走不到，
  main 的预装工具进程也不会去碰 `child_process`。
- UI：帮助菜单的「预装工具」入口按 `platform.isOhos` 置灰（见 [21](./21-上游能力可用性清单.md) 的 B 档），
  等预装与文档转换链路适配好再放出。
- 后续风险：上游补齐 linux 目标后，如果清单里出现 `linux/arm64`，必须先给 main 域的调用点加
  `isOhosRuntime()` 短路，再按 [15](./15-平台适配治理与不变量.md) 的检查清单登记。

### 21. 语音与凭据

- 语音的麦克风权限：入口和桌面保持一致（`platform.supportsVoiceInput`、
  `supportsMicrophoneCapture` 都为 true），识别走 zcode-server 的 ASR realtime。麦克风授权由
  ArkWeb 在 `getUserMedia` 时经适配层 `PermissionManagerAdapter`（`'microphone' →
ohos.permission.MICROPHONE`）触发，应用侧只需在 `module.json5` 声明这个 user_grant 权限。
  失败路径见 [17](./17-语音输入.md)。
- 凭据主密钥：上游用的 `@napi-rs/keyring` 没有 OHOS 产物。Main 是唯一访问者，主密钥存系统资产库
  Asset Store；随包 NAPI 绑定 `ohos_asset_keyring.node` 与 sqlite 同布局、双份复制。资产库不可用时
  回退同目录 0600 私钥文件并打 warn，登录不会因此保存失败。密钥别名按凭据文件路径摘要隔离数据根。
  细节见 [16](./16-凭据安全存储.md)。

### 22. 内置浏览器控制（Browser Use）

- 架构：renderer `<webview>` guest → main `browserGuestManager`（`webContents.debugger` 走 CDP）
  → agent 侧 `node_repl` 的浏览器代理 broker。端口已注册 `BrowserAbility` 与
  `BrowserEmbeddedAbility`（embeddedUI），`<webview>` 可挂载。
- 约束一（socket 目录）：`node_repl` 的浏览器代理监听 `znrb-*.sock`，必须与 `znr`（bootstrap
  broker）、`znrc`（CUA broker）同规则落 `ZCODE_OHOS_SOCKET_DIR`（el2 tmp）。真实 home 上
  AF_UNIX 路径型 bind 被系统拦截（spec 03），固定用 `tmpdir()` 会 bind 失败但内核仍拿到该
  socketPath，浏览器控制只报“连接套接字不存在”（真机实证）。
- 约束二（截图）：CDP `Page.captureScreenshot` 在端口上触发原生 SIGTRAP——Chromium 144 的
  `RenderWidgetHostImpl::GetSnapshotFromBrowser` 两个 `fromSurface` 分支都会崩，page 与 webview
  guest 一致（真机 3/3）。OHOS 截图一律走 main 直读 guest surface（`webContents.capturePage`）：
  viewport 直接读；clip 用 `capturePage(rect)`；fullPage 用**滚动分段 + 行拼接**——按当前
  viewport 高度逐段 `window.scrollTo`，每段 capturePage 一次，在 main 里按 BGRA 行拷进整页
  buffer，再 `nativeImage.createFromBitmap` 出 PNG，最后归一成 CSS 尺寸。
  不沿用 `Emulation.setDeviceMetricsOverride` 或撑高宿主 `<webview>` 的方案：截图 surface
  协调器会在 prepare 后把 surface/metrics 固定回 viewport，手动 resize/metrics 会被覆盖，
  真机表现为“视口内容被拉伸成整页”（底部空白/丢标记）。滚动方案只依赖已稳定的 viewport
  surface，且能触发懒加载；代价是固定头/动画元素会在每段重复。整页按
  `width*height*dpr²` 设设备像素上限，超限明确报错，不截半页。端口升级后需复验 CDP 截图。
- 约束三（插件缓存）：`node-repl-host` 是官方 seed 单元，缓存目录按 `version` 区分且只在
  目标目录不可用时回退旧版本；改其代码必须同步 bump `package.json`、`.zcode-plugin/plugin.json`
  与 `official-plugin-definitions.ts` 中的版本，否则旧缓存被判定可用，修复不会下发（真机实证）。
- 约束四（托盘归属）：状态栏图标只能有一个 owner。ArkTS `EntryAbility.addToStatusBar` 与
  Electron `Tray` 同时注册时，后注册的条目会覆盖端口 tray item：图标还在，但 `Tray` 的
  `click`/context menu 永远收不到（真机实证）。OHOS 已删除 ArkTS 条目，统一由 main 的
  `createDesktopTray` 管理；关闭驻留的 `canHideToTray` 必须放行 `ohos` 且 `desktopTrayReady`。
- 约束五（退出菜单）：鸿蒙状态栏会在 app 菜单末尾自动追加一个“退出”（平台项，真机验证会
  走同一 `app-quit`/`disposeHostProcess` 流程）。托盘模板在 ohos 下不再提供自己的 quit，
  否则菜单出现两个“退出”；win/linux 仍由托盘模板提供。
