# 20 · 真机渲染性能基线

真机 UI「卡」的定位结论与可复测基线。本文只记录**已实测**的事实与判定口径，不含优化承诺；
改动渲染相关行为时先以本文基线为对照。

## 环境

HUAWEI MateBook Pro `HAD-W32` / `2in1` / HarmonyOS 7.0.0.115 / API 26 /
3120×2080 @ 60Hz / 系统缩放 1.9（小数缩放）/ Electron v40.0.1（Chromium 144）。

## 已确认结论

| 维度           | 实测                                                                 | 判定                                      |
| -------------- | -------------------------------------------------------------------- | ----------------------------------------- |
| GPU 合成       | `gpu_compositing=enabled`、`rasterization=enabled`、`webgl2=enabled` | 硬件加速正常，**不是软件渲染**            |
| GPU 进程       | 启动 1 次、无 `Restarting GPU process`                               | 图形栈稳定                                |
| V8 JIT         | `--js-flags` 为空、WASM 可编译                                       | **不是 jitless**                          |
| 空闲帧节奏     | 60.3fps、p95 16.7ms、0 长任务                                        | 空闲管线准时                              |
| 空闲 CPU       | renderer 1.5%、GPU 2.7%、0 个运行中动画                              | 无持续重绘                                |
| 渲染线程优先级 | `nice=-8`                                                            | 未被降级调度                              |
| 纯 JS 计算     | numeric 128.5k / strings 3.5k / objects 386 ops/ms                   | 比 M 系列 Mac **慢 2.4–3.4x**（硬件差）   |
| 12000 节点 DOM | build 99ms、首次 layout **652ms**、滚动最差帧 283ms                  | 比同基准下 Mac（8ms / 47ms）**慢 10–14x** |
| 真实会话首屏   | 890 个 DOM 节点、打开会话 0 长任务                                   | 常规会话**不存在**首屏大布局问题          |

**结论**：管线健康；瓶颈是 Blink 的 style/layout 吞吐（同一份 DOM 比 Mac 慢 10–14x，
其中 2.4–3.4x 由 CPU 解释，其余 3–5x 归因未定，属厂商 Chromium 移植层，本文不给结论）。
显示器 60Hz 是观感上限，应用侧不可改。

## 虚拟滚动现状（勿重复实现）

会话列表**已有**虚拟滚动：`packages/ui/src/v4/ConversationTimeline.tsx` 以
`ConversationTurnRenderUnit`（一轮）为虚拟单位，`@tanstack/react-virtual`，
`ROW_OVERSCAN = 2`，动态高度经 `measureElement` 回写。详见
[docs/ui/chat-virtual-scroll.md](../../docs/ui/chat-virtual-scroll.md)。

因此「首屏一次性挂载整段历史」不成立，**不要再引入第二套虚拟化**。

## 残余风险

单轮内部（一条 assistant 回复里的全部 tool 块）不再虚拟化，元素量随工具调用数线性增长。
这是唯一可能触发 652ms 量级布局的形态。上线前若要治理，**另开 spec**：需明确单轮挂载上限、
折叠/分页的交互契约与 E2E，不能在 OHOS 分支里单独做（违反「平台差异只在适配层」）。

## 复测方法

真机 CDP（`9229` = renderer，见 [01](./01-构建与打包.md)）就绪后：

```bash
hdc fport tcp:9229 tcp:9229
node packages/desktop/scripts/ohos-device-cdp.mjs info
```

- GPU/JIT/显示器：main 里 `app.getGPUFeatureStatus()`、`screen.getPrimaryDisplay()`、
  renderer 里 `new WebAssembly.Module(...)`；
- 布局吞吐：在 renderer 注入固定 DOM 规模的前后对比基准，量 `offsetHeight` 强制 layout 与
  rAF 帧间隔；对照必须在同规模、同窗口宽度下进行。

验收口径：常规会话打开时不应出现 >50ms 长任务；出现即回到本文定位残余风险。
