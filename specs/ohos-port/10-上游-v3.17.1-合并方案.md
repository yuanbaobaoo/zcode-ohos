## 0. 摘要

本次上游是 3.16.2 → 3.17.1 的整包同步（单条 squash），表面规模巨大（5231 文件，+216,552/−611,504），但 **−61 万行的主要成分是上游测试体系自我重构**（App 单测退役、e2e 目录扁平化），业务增量本身可控。merge-tree 实际演练只有 **27 个冲突**（12 个内容冲突 + 15 个 modify/delete），且 09 §14 的全部接缝文件要么未被动、要么自动合并成功。

真正的三项核心工作（按危险度排序）：

1. **OHOS 定制单测全部"退役失效"**：上游删除了 `packages/*/test/` 下的业务单测并改为「明确清单制」（`scripts/engineering-test-files.json`，157 条）。OHOS 修改过的 14 个单测与新增的 16 个单测在合并后**不再被任何 Vitest 配置执行**，09 §14 的"接缝被冲掉时 CI 直接失败"兜底承诺整体落空。必须把这 ~30 个测试迁入 engineering 清单（详见 §5，含完整映射表）。
2. **pre-push / affected 基线改造搬迁**：`scripts/affected-unit-tests/` 改名 `scripts/engineering-tests/`（R085/R087，git 自动合并成功），但上游新代码**仍硬编码 `origin/staging`**——OHOS 的 `origin/main` 首推基线改造（50caa665）必须确认落位到新文件；`verify:pre-push` 整链重写并新增 3 个门禁，AGENTS.md 命令表需同步。
3. **Electron 44 类型 vs OHOS Electron 40 运行时代差**：上游升级到 Electron 44.7.0（docs/electron/electron-44-upgrade.md），OHOS 运行时是 Electron 40.1 / Chromium 144 / Node 24.11.1。typecheck（用 44 的类型）全绿不代表运行时（40）可用，需按 §7.3 冒烟清单验证。

**迁移机制已核实可行**：`scripts/lib/retired-app-unit-evidence.mjs` 的 `isAppUnit` 判定是「`packages/` 前缀 && 非 e2e/browser && **不在 engineeringTests 集合**」——把文件路径加入 `engineering-test-files.json` 即豁免退役门禁，且 `test:engineering:affected` 会把它们纳入 affected 选择。迁移映射表见 §5。

附带核对：`retired-app-unit-evidence` 会扫描文档中对 `packages/**/test/*.test.ts` 的引用（未入清单且未标 `retired:` 即报错）。合并后跑一次 `pnpm test:architecture`，若 OHOS 文档（含本 specs 与 AGENTS.md）中的引用被点名，同步登记或改标。

### 4.2 P0：affected 基线搬迁（scope.mjs 仍硬编码 staging）

上游架构侧已泛化默认分支（`scripts/architecture/default-branch.mjs`：`origin/staging` → `origin/HEAD` → `origin/main` → …），architecture:check 的基线在 OHOS（无 origin/staging）会自然落到 main。但 **engineering 的 `scope.mjs:35` 仍硬编码 `origin/staging`**——OHOS 必须在新路径重放 50caa665 的改造（集成分支 `origin/main`），并同步其 CLI 测试。rename 自动合并大概率已带过去，但以逐行核对为准。

### 4.3 P0：pre-push 新门禁对 OHOS 工作流的影响

新链路 = `check-push-worktree`（要求工作区干净）+ `check:e2e-remote-targets` + lint + `docs:stale-phrases:check`（陈旧措辞检查）+ db:schema + test:architecture + architecture:check --changed + engineering affected。逐项处理：

- `check-push-worktree`：合并解冲突完成即 commit，再 push；不能再带未提交改动推送。
- `check:e2e-remote-targets` / `docs:stale-phrases:check`：OHOS 首跑观察，若对 fork 场景误报，按上游脚本参数语义最小化调整并记录。
- AGENTS.md「命令与仓库结构」表与 `docs/testing/pre-push-hook.md` 同步：`test:unit:affected` → `test:engineering:affected`、全量 `pnpm test` → `pnpm test:engineering`；affected 输出合同叙述对齐上游新文。

### 4.4 P1：Electron 44 类型 vs Electron 40 运行时

- typecheck 用 electron 44.7 类型编译，OHOS 运行时 40.1——编译通过不等于运行可用。按 `docs/electron/electron-44-upgrade.md` 列出的 API 变化清单，对照 main/preload/renderer 新增调用逐面冒烟（重点：utilityProcess、session/webContents 新方法、protocol、BrowserWindow 新选项、Chromium 145+ 前端特性）。
- `__ZCODE_TELEMETRY_REPORT_ENDPOINT__` 成为构建期 define（上游 vitest 与 `scripts/build-time-config.mjs` 注入）。核对 OHOS 的 `tsup.config.ts` / `packages/desktop/scripts/bundle.mjs` / agent bundle 构建链是否同样注入，缺失时运行时 ReferenceError。
- electron-builder 26.17 只影响上游桌面安装包，HAP 管线（`bundle:desktop:ohos`）不受影响；但 `bundle.mjs`/`stage-agent-bundle.mjs` 双方都改过且自动合并，需确认 OHOS 打包逻辑与上游新资产结构共存。

### 4.5 P1：其余核对项

- `node:sqlite`（23 处）/ `Promise.withResolvers`（46 处）新增引用：Node 24.11.1 原生支持；确认新增文件没有绕开构建期重写的动态形态（`createRequire(...)("node:sqlite")` 由 `Module._load` 钩子兜底，静态 import 由 tsup 重写覆盖）。

### 11.2 设备实测发现并修复的 P0：Electron 44 具名导出在 E40 上崩溃

**现象**：v3.17.1 HAP 在模拟器上安装成功但启动黑屏 + 原生弹窗「A JavaScript error occurred in the main process」。

**根因（实证）**：`packages/desktop/src/main/pluginSandbox/host.ts` 从 `electron` 静态具名导入 `ClipboardItem`（上游 v3.17.1 为 Electron 44 迁移引入）。OHOS 运行时是 Electron 40（`v40.0.1-release`），没有该导出，ESM 在**实例化阶段**即抛 `SyntaxError: The requested module 'electron' does not provide an export named 'ClipboardItem'`，main bundle 整体加载失败 → 无 Renderer、无应用日志、窗口黑屏。取证方式：inspector 早期注入 `uncaughtException` 钩子并把堆栈写入 `/data/storage/el2/base/files/`（hilog 对长行按 200 字符截断，拿不到完整栈）。

**修复**：新增 `packages/desktop/src/main/pluginSandbox/clipboardImage.ts` 薄适配——命名空间访问 + 加载期能力探测：有 `ClipboardItem` + `clipboard.write` 走 E44 异步路径；否则回退 E40 仍保留的同步 `clipboard.writeImage`；两者都缺时显式抛错。`host.ts` 只保留一行调用接缝 `await writePngToClipboard(cropped.toPNG())`，不再导入 `ClipboardItem`。单测 `packages/desktop/test/clipboardImage.test.ts` 三条（E40 回退 / E44 Blob 路径 / 双缺失报错）通过并登记进 engineering 清单。

**同类风险核对**：合并后 main/preload 新增的 electron 具名导入仅 `BrowserWindow`、`ipcMain`（E40 均有）；`clipboard.readImage`（E44 移除）在仓库内无使用；renderer 侧的 `ClipboardItem` 是 Chromium 全局（Chromium 144 有），且已有 `typeof` 守卫。

### 11.4 终端在模拟器上的平台边界（与本次合并无关，需决策）

**现象**：登录后点击终端按钮，主进程约 0.3s 后以 `signal:6`（SIGABRT）退出，全部子进程随之 `exit code:0`，无 faultlogger/cppcrash 记录。

**隔离实验**（同一模拟器，v3.17.1 进程内）：通过 main inspector 直接执行
`process.getBuiltinModule("node:child_process").spawn("/bin/echo", ["SPAWN_PROBE_OK"])` → 调用返回后应用整体消失。**证明击杀点是 main 域 spawn 一个真实存在的可执行文件**，与终端业务代码无关。

**与历史记录的一致性**：

- `specs/ohos-port/03`：应用进程不能自行 fork+exec，进程创建须走 appspawn/native child。
- `specs/ohos-port/09 §12.6`：v40 模拟器上 main 域 spawn 会击杀应用；§12.7 记录当时改用 `OH_Ability_StartNativeChildProcess`（不 fork）后模拟器可用。
- `84c7f379`（2026-10-27）删除 native child 通道，终端改为 main 域托管系统 zsh，**仅在 HarmonyOS 7 PC 真机验证**；该提交之后模拟器未再覆盖终端。
- 由此解释「同一模拟器上旧 HAP 终端可用、新代码不可用」：旧 HAP 走 native child，新代码走 main spawn。

**附带发现**：`[ohos-bootstrap] login shell snapshot v3 captured=false` —— 快照采集 spawn 的 `/usr/bin/zsh` 在模拟器视图不存在（ENOENT 属正常错误事件），因此启动不崩；而终端 spawn 的 shell 路径存在，触发沙箱拒绝。这也解释了为什么启动正常、只有点终端才崩。
