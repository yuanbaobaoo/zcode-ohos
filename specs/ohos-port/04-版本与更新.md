# 04 版本与更新

鸿蒙版不能自更新。应用走 HAP 分发，桌面端那套 electron-updater（AppImage / deb）在 OHOS 沙箱里
既没有 APPIMAGE 环境，也没有可以替换的安装通道。

所以策略是「**查询 + 引导外部下载**」：

- 应用内查 GitHub 最新 release；
- 发现新版本弹窗展示更新日志；
- 点「前往下载」用系统浏览器打开发布页，用户自己下载 HAP、签名、安装。

## 版本号规则

### Tag 语法

保持既有惯例，不做迁移：

```
v3.14.3                 上游基线同步
v3.14.3-ohos-fix2       移植早期修复
v3.14.3-ohos-patch7     移植补丁序列（常态发版）
```

不认识的 tag（比如 `v3.14.3-dev`）按 semver 基线参与排序，见
`shared/ohosReleaseVersion.ts` 的 `parseOhosReleaseVersion`。

### 排序规则（`compareOhosReleaseVersions`）

1. 先比 semver 基线 `X.Y.Z`，按标准 semver 比大小；
2. 基线相同，比后缀等级：**base = dev(0) < fix(1) < patch(2)**；
3. 等级相同，比数字（数值比较，`fix10 > fix2`、`patch10 > patch7`，避免字典序错序）。

这么排是因为本仓库的发版时序就是 `v3.14.3-dev` → `v3.14.3` → `fix2` → `patch1..N`，patch 是常态
序列，排序和发布顺序对得上。

### HAP 的 versionName 与 versionCode

| 项          | 规则                                                                                                                                                                                                       |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| versionName | 完整的 tag 版本去掉 `v` 前缀（如 `3.14.3-ohos-patch7`）。由 `bundle-ohos.mjs` 从 `app.template.json5` 生成 `AppScope/app.json5`，模板模式同 `build-profile.template.json5` 先例，生成的 `app.json5` 不入库 |
| versionCode | `(major*10000 + minor*100 + patch) * 1000 + seq`；seq 取值：base/dev = 0，fix = N（1–499），patch = 500+N（501–999）                                                                                       |
| 单调性      | `3.14.3-ohos-patch7` = 31,403,507 < `3.14.4` = 31,404,000，跨基线恒增；int32 范围内（major ≤ 214）                                                                                                         |
| 解析优先级  | `GITHUB_REF_NAME`（CI tag 构建）> `git describe --tags --match 'v*' --exact-match`（本地正好在 tag 上）> `null`（开发态）。实现见 `build-metadata.mjs` 的 `ohosReleaseVersion`                             |
| 开发态      | `dev:ohos` 装机的 versionName 用 git describe 的结果，取不到就是 `0.0.0-dev`                                                                                                                               |

### 客户端当前版本

main 进程运行时从 `out/metadata/build-meta.json` 的 `ohosReleaseVersion` 读（`about.ts` 的
`readBuildMetadata()` 是现成模式），**不用 `app.getVersion()`**——OHOS 的 Electron 移植层对这个
值的行为没验证过。

值为 null（开发态）时更新检查直接禁用；调试想强制一个版本，用 `ZCODE_OHOS_UPDATE_DEV_VERSION`。

## 更新检查

| 项         | 值                                                                                                                              |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 数据源     | `GET https://api.github.com/repos/yuanbaobaooo/zcode-ohos/releases/latest`                                                      |
| 请求头     | `Accept: application/vnd.github+json` 加 `User-Agent`（GitHub API 必需）                                                        |
| 超时与上限 | 10s / 响应体 1MiB（对齐 forceUpdateGuard 的做法）                                                                               |
| 节奏       | 启动查一次，之后每小时轮询（复用 `AUTO_UPDATE_POLL_INTERVAL_MS`）                                                               |
| 字段映射   | `tag_name` → 版本，`body` → 更新日志 markdown，`published_at` → 发布日期，`html_url` → 「前往下载」目标                         |
| 判定       | `compareOhosReleaseVersions(latestTag, 本地版本) > 0`，且这个版本没被用户跳过                                                   |
| 通道       | GitHub latest 只返回最新正式 release（自动排除 draft / prerelease），单通道；跳过记录存 `skippedElectronUpdateVersions["ohos"]` |

### 状态与事件

所有者是 desktop main 的 `autoUpdater.ts`：

```
启动 → initAutoUpdater (production flavor)
 └─ OHOS 分支（替代 electron-updater 注册）
      ├─ 启动检查 + 每小时轮询，三级数据源依次降级：
      │    ① api.github.com /releases/latest（含更新日志）
      │    ② github.com /releases.atom（tag+日期，无日志正文）
      │    ③ gitcode.com 镜像 /info/refs?service=git-upload-pack（仅 tag 探测；
      │       git smart-http 纯协议无限流，镜像无 release 内容）
      │    所有源的跳转地址（htmlUrl）一律指向 GitHub release 页——镜像只做版本探测。
      │    ├─ 有新版且未跳过 → menuState = update-available
      │    │    { version, channel:"ohos", releaseNotes, externalDownload:true, downloadUrl }
      │    │    ├─ renderer 弹窗（复用 UpdateStatusDialog，仅 before-download 相位）
      │    │    │    「前往下载」→ IPC DownloadUpdate → main shell.openExternal 打开系统默认浏览器
      │    │    │    「跳过此版本」→ IPC SkipUpdateVersion → settings["ohos"] = tag
      │    │    └─ 打开成功 → 广播 idle（弹窗收口，入口消失）
      │    ├─ 无新版 → idle；手动检查回 up-to-date
      │    └─ 三源全失败：轮询仅 warn 日志（静默）；手动检查回 UpdateCheckResult error
      └─ 永不进入 download-progress / update-downloaded / quitAndInstall（OHOS 无自更新）
```

互斥复用现有的 `checkForUpdatesInFlight` / generation 机制，轮询只在 idle 或 update-available 态
进入。

顺带记一条上游行为：electron-updater 的 Linux 系统包路径（AppImage 之外的 deb / 原生通道）会用
`sudo -n -v` 探授权，这是 v4.0.0 新增的。该调用在鸿蒙上会触发 main 的 libuv spawn 崩溃，所以
`isLinuxSystemPackageUpdate()` 里加了 `isOhosRuntime()` 短路；它本来还要求 `app.isPackaged`
（OHOS 恒 false），两道检查之后不可达。

### 真机实证的平台事实（HAD-W32 / HarmonyOS 7）

1. **net.request 只认单参 options 形式**。写成 `net.request(url, {headers})` 会触发
   `TypeError: "listener" argument must be function`；必须写成
   `net.request({url, headers, session})`。
2. **更新请求必须直连**。main 从用户 zsh 环境（登录快照）拿到代理变量后，Chromium net 栈经代理访问
   api.github.com 会被 404 拒绝；改用独立 partition 的 direct session（`setProxy({mode:"direct"})`）
   走 TUN 直连就正常。
3. **api.github.com 的匿名配额常态超限**。代理共享出口 IP，每小时 60 次的配额基本恒为 403
   `rate limit exceeded`，所以常态路径是降级到 `github.com/.../releases.atom`：网页端点没有 API 限额，
   取首个 entry 的 tag 和时间，无更新日志正文。本仓库 CI 从不发 prerelease，首 entry 和 latest 语义一致。
4. **GitHub 整站不可达时用镜像兜底**。GitCode 镜像（gitcode.com/yuanbaobaoo/zcode-ohos）只有 tag
   没有 release；它的 Gitee 风格 API 匿名配额不可靠（429），tags 页面是 SPA 空壳；可靠的探测端点是
   git smart-http 公告 `/.git/info/refs?service=git-upload-pack`（纯协议、无限流，含全部 refs/tags，
   注解 tag 的 `^{}` peeled 行要跳过）。镜像只用来探版本，弹窗跳转和下载仍然走 GitHub。
5. **外链统一用系统浏览器**。`shell.openExternal` 拉起默认浏览器，「前往下载」「问题上报（GitHub
   issues）」都走 `platform.openExternal` → main `shell.openExternal`，不用应用内窗口承载外部网站。

## 与桌面更新流的差异

| 能力                  | Win / mac / Linux                    | OHOS                                             |
| --------------------- | ------------------------------------ | ------------------------------------------------ |
| 查询源                | zcode.z.ai manifest（YAML）          | GitHub latest API，失败降级 atom                 |
| stable / preview 通道 | 设置项 + API 参数                    | 没有（单通道），设置项隐藏                       |
| 自动下载              | `autoDownloadAndInstallUpdates` 设置 | 不适用，设置项隐藏                               |
| 下载安装              | 应用内下载 → 重启安装                | 系统浏览器打开发布页，用户手动装                 |
| 强更 gate             | client/configs 的 minimalVersion     | **跳过**（官方阈值指上游桌面版，对 OHOS 没意义） |

## 验收场景

| 场景         | 预期                                                                                                                                                                                                                                          | 状态                                                        |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| 版本同步     | CI 打 tag 构建后，`hdc shell bm dump -n io.github.yuanbaobaoo.zcode` 的 versionName 等于 tag 版本，versionCode 按公式递增                                                                                                                     | 已验证：v3.14.3-ohos-patch5 → 3.14.3-ohos-patch5 / 31403505 |
| 发现更新     | 真机装旧 tag 版本，启动或手动「检查更新」，弹窗显示新版本号与日期；点「前往下载」由系统浏览器打开 release 页，弹窗收口、更新入口消失                                                                                                          | 已验证：patch5 检出 patch7 全链路                           |
| 跳过版本     | 点「跳过此版本」后，轮询不再提示该版本；手动检查清除跳过记录后重新可见                                                                                                                                                                        | —                                                           |
| 已是最新     | 装最新 tag，手动检查提示已是最新                                                                                                                                                                                                              | —                                                           |
| 失败韧性     | 断网时轮询静默（只记日志），手动检查弹错误提示，应用功能不受影响                                                                                                                                                                              | —                                                           |

| dev 装机版本 | `dev:ohos` 全量装机的 versionName 是 `0.0.0-dev`、versionCode 是 1e9（同一身份内覆盖安装不受版本比较阻碍）。dev 包已是独立 bundleName（`….zcode.dev`，见 [19](./19-开发包身份.md)），和正式包互不覆盖、可同机共存，版本比较只发生在同一身份内 | —                                                           |

## 帮助菜单与 About 定制

帮助入口（问号菜单）和 About 弹窗按 zcode-ohos 的产品形态定制：

| 入口             | 行为                                                                           |
| ---------------- | ------------------------------------------------------------------------------ |
| 用户社群         | 不提供（上游社群渠道和 zcode-ohos 无关）                                       |
| 给产品提需求     | 不提供（站内反馈表单指向上游渠道）                                             |
| 问题上报         | `openExternal` 用系统浏览器打开 GitHub issues（常量 `OHOS_GITHUB_ISSUES_URL`） |
| 前往下载（更新） | 同一条链路，`shell.openExternal` 打开 release 页（见上「真机实证」第 5 条）    |

About 弹窗（`about.ts` / `aboutWindow.ts`）三条规则：

1. **版本与 HAP 的 versionName 同源**：`resolveOhosAboutVersion(buildMeta)` 优先取
   `ohosReleaseVersion`（tag 构建去掉 `v` 前缀），开发态（null）回退 `0.0.0-dev`。原因是 OHOS 上
   `app.getVersion()` 返回的是移植层占位符（实测 `0.0.0-no-git-tag-found`），不是任何真实版本。
2. **不显示版权行**：版权声明指向上游主体，zcode-ohos 不展示。
3. **仓库行**：meta 区展示 `Github：<仓库地址>`（`OHOS_GITHUB_REPO_URL`，中英文都显示）。前缀和地址各占一行，
   地址用 `white-space: nowrap` 强制单行；卡片宽度 `ABOUT_DIALOG_WIDTH`（320px）按地址在 13px 下的实测字宽
   （SF Pro 约 273px、HarmonyOS Sans 约 260px）加上内容区余量反推，`BrowserWindow` 直接用同一常量，
   不再单独写死窗口宽度。旧的 256px 卡片（内容区 222px）放不下地址，而地址只在连字符处有折行机会，
   于是被拆成两行且行尾溢出内容区。验收：`help-menu-about.test.ts` 读真实窗口里 `.github-link` 的
   `getClientRects().length`，必须为 1。

图标另有一条：HAP 打包时会把 `build/icon.png` staged 到 resources 根，而 OHOS 上 `app.isPackaged`
恒 false，所以 About 与窗口图标改用 `isOhosRuntime()` 选择 packaged 路径。
