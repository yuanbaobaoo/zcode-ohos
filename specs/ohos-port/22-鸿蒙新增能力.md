# 22 鸿蒙新增能力

本文只记上游没有、为了在鸿蒙上落地才加的东西。和 [21](./21-上游能力可用性清单.md) 的分工很简单：

- 把适配层整个删掉，上游功能会缺一块 → 记在 21（受限、或换了做法）。
- 删掉之后上游照旧、只是鸿蒙这边少了点什么 → 记在这里。

纯粹换实现、但没多出新能力的（比如终端从 pty 改管道），不在本文，去 21 的 C2 看。

## 用户能用到

| 能力                     | 是什么                                                             | 为什么需要                                                                 | 出处    |
| ------------------------ | ------------------------------------------------------------------ | -------------------------------------------------------------------------- | ------- |
| 碰一碰投送               | 手机碰一碰或分享文件到电脑，直接变成输入框附件                     | 上游没有这个入口；鸿蒙的分享通道落在应用沙箱外，得自己建收件箱把文件搬进来 | spec 05 |
| 全盘文件权限引导         | 引导页说明、一键跳系统设置、桥文件把授权状态回传                   | 鸿蒙按权限授予目录访问，应用也不能自己弹系统授权框                         | spec 08 |
| Desktop 目录按需授权     | 全盘和 Desktop 两类目录各自按需申请，授权后迁回真实 home           | 首次启动时 home 往往不可写，不授权就只能待在沙箱里                         | spec 18 |
| 系统栏主题跟随           | 浅色 / 深色 / 跟随系统三态，最大化时系统栏跟着变                   | 端口的 `nativeTheme` 是空转的，系统栏由 ArkTS 绘制                         | spec 07 |
| 电脑控制的权限门禁       | 辅助操作和截屏两项权限聚合，缺一个就禁用，并在设置页给引导         | 鸿蒙的注入和截图不是点一下就有，要先拿系统权限                             | spec 13 |
| 语音输入的权限桥         | ArkWeb 采集时向系统申请麦克风权限                                  | 端口的 `systemPreferences` 没实现，上游那套授权在鸿蒙拿不到麦克风          | spec 17 |
| 模拟器检测与软件渲染降级 | 识别模拟器、切 ANGLE + SwiftShader，设置页留三态兜底               | 模拟器的 GPU 直通撑不住 Chromium EGL，会直接黑屏                           | spec 06 |
| 开发包独立身份           | dev 包名、桌面名、窗口标题带后缀，独立调试签名，和正式包同机共存   | 同一台机器既要装正式包，又要装自己构建的包                                 | spec 19 |
| 设备通道                 | 随包的 `hdc-direct` CLI 加内置 skill，agent 能自己连设备、跑 shell | 官方 hdc server 在应用沙箱里起不来                                         | spec 11 |

## Agent 与开发者向

| 能力                             | 是什么                                                                                   | 为什么需要                                           | 出处                                                     |
| -------------------------------- | ---------------------------------------------------------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------- |
| 鸿蒙环境事实卡与 `ohos-dev` 技能 | 内置 skill，告诉 agent 这台机器是鸿蒙、能用哪些命令                                      | 上游 agent 对鸿蒙一无所知，容易照着 macOS 的经验做事 | `apps/zcode-cli/packages/bundled-skills/skills/ohos-dev` |
| 开发自测的 uitest 豁免           | 调试自己构建的应用时，允许在 `hdc shell` 里用 uitest、snapshot_display                   | 产品级控制只走 CUA，但开发环总得能自己点自己         | spec 11、spec 15                                         |
| 真机 CDP 自动化                  | 一个脚本连真机页面：枚举元素、求值、点击、截图；9229 给 renderer，9330 给 main inspector | 鸿蒙没有 Chromedriver，上游那套 E2E 跑不了           | `packages/desktop/scripts/ohos-device-cdp.mjs`、spec 01  |
| 快速迭代环 `dev:ohos`            | 改完一键重装；小改动可走 hqf 增量热推                                                    | 鸿蒙装机比桌面上重，全量装一次几十秒                 | spec 01                                                  |
| 真机渲染性能基线                 | 实测帧率与卡顿的判定口径、可复测步骤                                                     | 上游的性能结论在鸿蒙不成立，得有自己的基线           | spec 20                                                  |

## 工程与发布

| 能力                  | 是什么                                                                    | 为什么需要                                                  | 出处                             |
| --------------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------- | -------------------------------- |
| HAP 构建与发布流水线  | push `v*` tag 自动构建未签名 HAP，发布 Release（带 latest 别名和 sha256） | 上游发的是 mac/win/linux 包，鸿蒙产物只能自己出             | `.github/workflows/ohos-hap.yml` |
| 版本号与 HAP 版本规则 | tag 语法 `v{上游版本}-ohos-patchN`，versionName / versionCode 的换算      | 鸿蒙的 versionCode 必须单调递增，上游 semver 直接映射不够用 | spec 04                          |
| 原生绑定构建链        | 交叉编译 sqlite、asset keyring 等 `.node`，并自动拷进 HAP 的两个位置      | 上游没有这些原生模块，鸿蒙的 loader 布局又特殊              | spec 02、spec 16                 |

补一条判断口径，免得以后混淆：新增能力指的是用户在鸿蒙上能做、在 mac/win 上做不了的事（或在鸿蒙上必须多做一步才能做的事）。
如果只是"同一件事换了实现"，哪怕代码是新写的，也算 21 的 C2，不算这里。
