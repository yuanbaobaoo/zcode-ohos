# 17 语音输入

Composer 麦克风输入在 HarmonyOS PC 上的可用化。产品语义（点击开始/停止、语音文字写入、
用户接管即结算、不自动发送）沿用 [composer-voice-input](../../docs/chat/composer-voice-input.md)，
本文只记录 OHOS 的差异面与权限流程。

## 范围

- 仅桌面本机（`enabled: !isWebRemoteControl`），手机远控与 Web 不显示入口——沿用上游。
- 识别走 zcode-server 的 ASR realtime 接口（ticket + WebSocket），**不引入离线引擎**。
  理由：与 macOS/Windows 同一实现与同一失败语义，不做第二套识别协议。
- 采集在 renderer：`getUserMedia` + `AudioWorklet`，16kHz 单声道 PCM16、每 100ms 一块。
  OHOS Electron（ArkWeb）复用同一 Chromium 媒体管线，不在 ArkTS 侧另写采集。

## OHOS 差异面

| 关注点 | 现状（改前） | 目标 |
| --- | --- | --- |
| 平台开关 | `supportsMicrophoneCapture: isOhosRuntime !== true`（[desktopPlatform.ts]） | OHOS 也置 true，入口从「置灰」转为「可用」 |
| 权限声明 | `module.json5` 无 `ohos.permission.MICROPHONE` | 声明为 `user_grant`，带 reason 与 usedScene |
| 权限申请 | main 只有 darwin/win32 分支，OHOS 落 `unsupported` | OHOS 走文件桥请求 ArkTS `requestPermissionsFromUser` |
| 设置页 | `MICROPHONE_SETTINGS_URLS` 只有 darwin/win32 | OHOS 跳本应用信息页（`application_info_entry`） |
| 失败提示 | `voiceInputFailure` 的 OS 只有 mac/win/linux | OHOS 单独归类，引导文案与「去开启」一致 |

## 权限流程

```text
点击麦克风
  └─ useComposerVoiceInput.start
       └─ platform.microphone.ensureAccess()
            └─ main: OHOS 没有 systemPreferences 接口 → 返回 unsupported（不阻断）
       └─ voiceInputService.start()（服务端 ticket + WS）
       └─ getUserMedia → ArkWeb PermissionManagerAdapter
            └─ requestPermissionsFromUser(['ohos.permission.MICROPHONE'])
                 └─ 系统弹窗：允许 → 开始采集；拒绝 → getUserMedia 抛 NotAllowedError
```

- **入口可见性属于上游门禁，不在本迭代改**：`visible = enabled && hasEntry && hasService && isLoggedIn`。
  未登录时按钮隐藏（真机实测：登出后入口消失、登录时出现）；会话 attachment 不可用时 Composer
  还会再被 `remoteAvailable` 挡一层。排查「按钮不见了」时先看登录态与 attachment，不要改语音代码。
- OHOS 的 `ensureAccess` 返回 `unsupported`，`useComposerVoiceInput` 只拦截 `denied`，因此流程继续到
  `getUserMedia`；系统授权弹窗由 ArkWeb 适配层触发，不在 main 里预检。
- 权限声明在 `entry/src/main/module.json5`（`user_grant`，reason `$string:microphone_reason`）。
- 不做「应用启动即弹授权」：只有用户点击麦克风才触发系统授权（spec 03 的平台纪律）。
- 后续若要「拒绝后一键跳设置页」，需要补 OHOS 的 `microphone.openSettings`（跳应用信息页）；
  当前 OHOS 走 toast，不提供引导浮层。

## 端到端行为

- 已登录、在会话 Composer 点击麦克风 → 系统弹「允许"ZCode"访问你的麦克风？」，副文案正是
  `$string:microphone_reason`（「录制语音以使用输入框语音输入」）→ 点「允许」后 Composer
  进入录音胶囊态（波形 + 停止按钮），系统栏出现麦克风指示。
- 点停止 → `finish` 后回到空闲态，无错误提示（静音输入没有文字）。
- **ASR 端到端**：录音期间设备麦克风采集现场语音，停止后服务端识别出
  整段中文并写入 Composer（随后被发送进会话）。说明 `getUserMedia → PCM16 → voice-input WS →
  zcode-server ASR → 语音文字` 全链路在 OHOS 上成立。
  - 识别结果不自动发送：需要用户确认后才会进入会话。

## 失败语义

沿用 `domain/voiceInputFailure.ts` 的分类，OHOS 只补两处映射：

| 现象 | 归类 | 提示 |
| --- | --- | --- |
| `ensureAccess` 返回 denied / 超时 | permission-denied | 「麦克风权限未开启」+「去开启」 |
| `getUserMedia` 抛 `NotAllowedError` | permission-denied | 同上（ArkWeb 直接拒绝时的兜底） |
| `getUserMedia` 抛 `NotFoundError`/`NotReadableError` | device-unavailable | 「未找到可用麦克风」 |

401 仍由全局登录失效处理，本功能不提示（与上游一致）。

## 不变量

1. 语音文字只有编辑器 handle 一份；`useComposerVoiceInput` 不保存第二份。
2. 每次录音一个 attemptId，旧 attempt 的事件与异步回调丢弃。
3. 录音中用户修改输入框 / 发送，与点击停止同一流程：flush 尾块 + finish + 等最终结果。
4. 不加客户端超时，依赖服务端；等待期间切换会话或卸载则中止发送。
5. 只有用户点击麦克风才请求系统权限；启动与状态回流不弹窗。

## 验收场景（真机）

1. **登录态**是前提：登录后主 Composer 出现麦克风；未登录时不出现（真机已确认两种状态各一次）。
2. 首次点击麦克风 → 系统弹「ZCode 使用麦克风」→ 允许 → 进入录音态，波形随输入变化。
3. 说话 → 输入框出现语音文字并随识别更新 → 再次点击停止 → 等 `completed` 后变为普通文本。
4. 拒绝授权 → 回到空闲，toast 提示失败；再次点击会重新触发系统授权。
5. 录音中打字 / 点发送 → 与点击停止行为一致；最终文本替换语音文字，用户追加内容保留。
6. 手机远控与 Web 不显示入口。

## 待真机确认

- 运行时侧已有音频输入实现：`entry/libs/arm64-v8a/libelectron.so` 内含
  `OH_AudioCapturer_Start/Stop/Release`（OHOS 原生采集 API）与 Chromium `AudioInputDevice`，
  说明 ArkWeb 的 `getUserMedia` 不是空实现（`strings` 取证）。
- 仍缺**真机授权 + 采集**的端到端证据：需要在登录态下点击一次麦克风，确认系统弹窗与录音态。
  若 ArkWeb 直接拒绝且不弹系统授权，本迭代停在「权限已声明、入口可用、采集不可用」，
  另一个方向是在 ArkTS 侧采集后经文件桥把 PCM 送 renderer。
- 拒绝授权后的「去开启」引导：需要 OHOS 版 `microphone.openSettings`（跳应用信息页），
  当前只提示不引导。
