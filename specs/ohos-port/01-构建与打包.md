# 01 构建与打包

构建机用 macOS；Linux 走 CI 验证过，同样可用。真机接 USB 或网络 hdc 都行。

## 环境要求

| 项                      | 说明                                                                                                                      |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Node 24.14 + pnpm 10.33 | 仓库标准工具链（mise 管版本），装依赖跑 `pnpm install`                                                                    |
| OHOS command-line-tools | 唯一额外要装的东西，提供 hvigorw / ohpm / hdc，从[华为开发者下载页](https://developer.huawei.com/consumer/cn/download/)取 |
| Electron v40 运行时     | 不入库，构建时从 GitHub Release 取华为官方原包并校验 sha256                                                               |
| 签名材料                | 可选。没有就只出未签名 HAP，签名方式见下一节                                                                              |

不需要 DevEco Studio，也不需要 devecocli 和 python3。

### 怎么找到 command-line-tools

二选一：

- 设 `DEVECO_CLI_CLT_PATH`（devecocli 的标准变量，推荐写进 `.env`，样例见 `.env.example`）；
- 或者把 `bin/`（也可以 `sdk/default/openharmony/toolchains`）加进 PATH，hvigorw 或 hdc 都能反过来
  推出根目录。

解析逻辑只有一处：`packages/desktop/scripts/ohos-env.mjs`。它和 tesslo 的解析链（`scripts/ohos-common.ts`）对齐，但不含那边的
`.toolchain/` 落点——本仓库不做 CLT 自动下载，也不去探测 `~/command-line-tools` 这类机器路径。

### Electron 运行时从哪来

`fetch-ohos-runtime.mjs` 从 GitHub Release `tools` 下载 `electron-ohos-v40.0.1.20260928.2.zip`
（华为官方原包，368MB，解开后里面还有一层 `libelectron_144.tar.gz`），校验 sha256 后解出
`libelectron.so` / `libadapter.so` / `libffmpeg.so`、启动器，以及 resfile 的 pak、icudtl、快照、
locales、vulkan。首次构建或 `dev:ohos` 会自动跑；想换源用 `ZCODE_OHOS_ELECTRON_URL`。

### dev 装机签名

正式 HAP 一律出未签名包（CI 也一样），签名由使用者自己处理，仓库不维护正式签名材料。下面这些只服务
`pnpm dev:ohos` 的 dev 包——装机必须有签名。

- 方式一（AGC 手动）：在 developer.huawei.com 申请 debug 证书和 Profile，把
  `build-profile.template.json5` 复制成 `packages/desktop/ohos/build-profile.json5`（机器相关，
  不入库），替换 `signingConfigs.material` 里的 certpath / .p7b / .p12 和密码。没有签名材料时，
  hvigor 的 SignHap 会自动跳过，只出 `*-unsigned.hap`；`build-profile.json5` 缺失时
  `bundle-ohos.mjs` 会自动复制模板。
- 方式二（devecocli 捷径，外部 npm 工具，不是本项目依赖）：在 `packages/desktop/ohos/` 下跑
  `devecocli auth login`（浏览器登录华为账号，一次性），再跑
  `devecocli signature generate --product dev`，它会申请含受限 ACL 的 debug 证书，更新
  `build-profile.json5` 的 `dev` 条目并指向 `~/.ohos/config` 的材料。

两个坑要知道：

- **Profile 和包名强绑定**。debug Profile 的 `bundle-info.bundle-name` 必须等于被打 product 的
  bundleName。dev 包的包名是 product `dev` 派生的（`….zcode.dev`，见 [19](./19-开发包身份.md)）；
  `dev:ohos` 缺签名时会自动调 devecocli 生成（已登录且有设备的前提下），只检查维护 `dev_*.p7b`。
  包名对不上时 `assembleHap` 停在 SignHap，报 **00303074**，只产出 `*-unsigned.hap`。
- devecocli 读的是 `AppScope/app.json5` 的 bundleName，不认 product 级覆盖，所以生成 dev 签名前后
  会临时改写再还原，规则见 [19](./19-开发包身份.md)。

### CI 用的工具链

CI 配置在 `.github/workflows/ohos-hap.yml`，要点：

- command-line-tools 用 Linux 版 26.0.0.851 官方原包，分卷托管在 [GitCode ohos-tools Release v26.0](https://gitcode.com/yuanbaobaoo/ohos-tools/releases/v26.0)
  （`commandline-tools-linux-x64-26.0.0.851.zip.part1/part2`，`cat` 合并），sha256 锁定校验；
  `OHOS_CLT_URL` 可以覆盖成任意整包直链。
- 同一个 Release 里还托管了 HarmonyOS(aarch64)、mac、windows 的 CLT 分卷（例如
  `commandline-tools-harmonyos-26.0.0.201.tar.gz.part00/part01`）。直链必须是
  `.../ohos-tools/releases/download/v26.0/<资产>` 这种形态；`.../releases/v26.0/download/<资产>`
  返回的是前端壳，下不了。
- Electron 运行时同样从 GitHub Release `tools` 取，新 clone 和 CI 每次全量下 368MB（含未裁剪的
  调试库），这是选官方原包的既定代价。
- amd64 容器要 `apt install libgl1 libx11-6`：HMS 工具链的 `libimage_transcoder_shared.so` 运行时
  依赖它们，缺了 CompileResource 会失败。io_uring 补丁是纯 Node 实现，不需要 python3。

## 什么进仓库、什么不进

`pnpm install`、`pnpm dev:ohos`、`pnpm bundle:desktop:ohos` 能生成的产物一律不入库。

**不入库**

| 类别            | 内容                                                                                                                                            |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 依赖与缓存      | `node_modules/`、`dist/`、`out/`、`oh_modules/`、`.hvigor/`、`build/`、`hnp/`                                                                   |
| 机器相关配置    | 根 `build-profile.json5`（含签名材料；只入库 `build-profile.template.json5`）、`AppScope/app.json5`                                             |
| 组装产物        | `web_engine/src/main/resources/resfile/resources/`                                                                                              |
| Electron 运行时 | 三件 .so、启动器、`chrome_*.pak`、`icudtl.dat`、`resources.pak`、快照、`locales/*.pak`、`vulkan/`；`hnp/lib/arm64-v8a/` 下的 .so 副本由脚本同步 |
| HAP 资源        | `config/`、`glm/`、`tools/`、`icon.png` 由 build-ohos 硬校验后 staged，缺 glm/tools 直接失败（`--skip-agent` 只跳 glm），免得产出装机不可用的包 |
| 原生适配产物    | `zcode_sqlite.node`、`libzcode_exec_shim.so`，由 build-ohos.mjs 按需编译并拷进 HAP libs                                                         |

**入库**：源码与模板（`build.sh`、`.cpp`、`build-profile.template.json5`、字体与 OFL 等），
锁文件（`pnpm-lock.yaml`、`oh-package-lock.json5`）保留以保证可复现。

**例外**：模块级的 `<module>/build-profile.json5`（`entry`、`web_engine`）不含机器信息，hvigor 在工程
配置阶段又强制要求，缺了报 `00304056 Not Found`，所以必须入库。忽略规则因此只锚定根目录的
`/build-profile.json5`。

## 常用命令

```bash
pnpm bundle:desktop:ohos      # 打包，产物落 packages/desktop/dist/（未签名 + 可选签名版）
pnpm dev:ohos                 # 默认全量：dev HAP 装到 hdc 能看到的设备并启动（~30s，覆盖已装版本）
pnpm dev:ohos -- --build      # 全量闭环（~120s）：desktop 生产构建 + agent CLI 一起重建
pnpm dev:ohos -- --agent      # 只重建 agent CLI 包（改 apps/zcode-cli 后用）
pnpm dev:ohos -- --hqf        # 增量热推（单设备，要 --device 指定）：签名 hqf → quickfix → 重启（~8s）
                              # 无基线 / 未安装 / 有删除 / 变更超阈值时自动回退全量
```

`--build` 必须隐含 agent 重建：glm 默认是从 `bundled-agents` 的旧产物 stage 的，漏掉这一步会把
`apps/zcode-cli` 的改动静默撤掉（官方插件会整体消失）。

手动分步（正式身份，product=default）：

```bash
node packages/desktop/scripts/build-ohos.mjs              # 构建产物 + 组装 resfile
cd packages/desktop/ohos && hvigorw assembleHap --mode module -p product=default -p buildMode=debug --no-daemon
hdc install -r packages/desktop/ohos/entry/build/default/outputs/default/electron-default-signed.hap
hdc shell "aa start -a EntryAbility -b io.github.yuanbaobaoo.zcode"
```

手动分步（开发身份，product=dev，产物名和目录都带 dev，身份表见 [19](./19-开发包身份.md)）：

```bash
cd packages/desktop/ohos && hvigorw assembleHap --mode module -p product=dev -p buildMode=debug --no-daemon
hdc install -r packages/desktop/ohos/entry/build/dev/outputs/dev/electron-dev-signed.hap
hdc shell "aa start -a EntryAbility -b io.github.yuanbaobaoo.zcode.dev"
```

开发包和正式包可以同机共存。CI 方面：push `v*` tag 会自动构建未签名 HAP 并发到 GitHub Release。

## 常见坑

| 现象                                | 原因与处理                                                                                                                                   |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| "1 秒构建成功"，装上还是旧包        | hvigor 增量不感知 resfile 变化。手动装机前清 `packages/desktop/ohos/{.hvigor,entry/build,web_engine/build}`，bundle/dev 脚本已自动处理       |
| `aa start` 报 10106102              | 设备锁屏。developer mode 不会自动解锁，手动解锁后重试                                                                                        |
| 看不到应用日志                      | console.log 进 hilog（tag `Electron`），默认缓冲几十秒就被系统日志滚没。先 `hdc shell "hilog -G 16M"`，再 `hdc shell "hilog -x -T Electron"` |
| HAP libs 里 .node/.so 的 md5 对不上 | hvigor 会 strip 去符号，正常现象。对账用行为验证，别按 md5 判旧产物                                                                          |

### 调试端口（两个，别混）

| 端口 | 归谁                                                                          | 怎么用                                                                                                                                                              |
| ---- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 9229 | renderer 的 Chromium DevTools（main 早期设的 `--remote-debugging-port=9229`） | `hdc fport tcp:9229 tcp:9229` 后开 `chrome://inspect`，能取 DOM 和 Performance trace；仓库的真机 UI 自动化（`ohos-device-cdp.mjs` 的 `ZCODE_CDP_BASE`）默认连这个口 |
| 9330 | main 进程的 Node inspector（厂商默认参数 `--inspect=9330`）                   | 需要调试 main 时单独 fport                                                                                                                                          |

历史坑：厂商默认参数原来是 `--inspect`（默认 127.0.0.1:9229），会抢占 9229，导致
`remote-debugging-port` 绑定失败，`chrome://inspect` 里只能看到 `node.js/…` 的 Node target，
`ohos-device-cdp.mjs` 报 `no page target`（真机实测确认）。所以 `--inspect` 固定在 9330，9229 留给
renderer。

真机 UI 自动化的用法见 `packages/desktop/scripts/ohos-device-cdp.mjs` 头注。
