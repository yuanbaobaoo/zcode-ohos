# 01 构建与打包

macOS / Linux / Windows 三个平台的开发者流程完全一致：`pnpm install` 装依赖 →
`pnpm ohos:setup` 备齐三类构建输入 → `pnpm ohos:run` / `pnpm ohos:bundle`。
构建命令只校验输入，不再自己下载。
平台差异只存在于脚本内部（见「Windows 原生构建」），
不要求开发者按平台换命令、加变量或手工准备工具链。真机接 USB 或网络 hdc 都行。

## 环境要求

| 项                      | 说明                                                                                                                                                                                                                                                                                                    |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Node 24.14 + pnpm 10.33 | 仓库标准工具链（mise 管版本），装依赖跑 `pnpm install`                                                                                                                                                                                                                                                  |
| OHOS command-line-tools | 提供 hvigorw / ohpm / hdc（含 SDK）。**用 `pnpm ohos:setup` 获取**（约 2.1–2.7GB，按平台取官方原包，缓存到 `packages/desktop/.cache/ohos-clt/` 并回写 `.env`）；也可自行下载后写进 `.env`。已装过的机器走发现链，不重复下载。Windows 版入口是 `bin\hvigorw.bat` / `bin\ohpm.bat`，需要 PATH 上有 `node` |
| 系统库（仅 Linux）      | `libgl1` / `libx11-6`：HMS 工具链 `CompileResource` 的运行时依赖，缺了编译资源阶段失败                                                                                                                                                                                                                  |
| Electron v40 运行时     | 不入库，由 `pnpm ohos:setup` 取华为官方原包并校验 sha256；构建期只做存在性校验                                                                                                                                                                                                                          |
| 签名材料                | 可选。没有就只出未签名 HAP，签名方式见下一节                                                                                                                                                                                                                                                            |

构建与打包都不需要 DevEco Studio，也不需要 devecocli 和 python3（devecocli 只在 `ohos:run` 的自动
签名路径里被调用，见「dev 装机签名」）。

### 怎么找到 command-line-tools

四步链，三平台同一实现；前两步是“已经装好了”的快路径，后两步是“让命令直接可用”：

1. `DEVECO_CLI_CLT_PATH`（devecocli 标准变量，可写 `.env`，样例见 `.env.example`）；
2. PATH 反推：`bin/`（或 `sdk/default/openharmony/toolchains`）在 PATH 里，hvigorw 或 hdc 反推根目录；
3. 项目缓存 `packages/desktop/.cache/ohos-clt/<版本>/command-line-tools/`；
4. 都没有则按平台下载：分卷来自 GitCode `ohos-tools` Release（与 CI 同源），逐分卷校验 sha256、
   合并解压后进入缓存，**并把最终路径回写 `.env`**。

第 4 步只有一个触发点：`pnpm ohos:setup`。构建命令（`dev-ohos` / `bundle-ohos` / `build-ohos`）
调用 `requireCommandLineTools()`，只走第 1–3 步；找不到就报错指向 `pnpm ohos:setup`，
不会在构建中途开始下载 2GB 级工具链。另外两类输入（Electron 运行时、原生编译输入）同一规则：
`ohos:setup` 取，构建期只校验。

发现逻辑（第 1–2 步）在 `packages/desktop/scripts/ohos-env.mjs`，与 tesslo 的解析链
（`scripts/ohos-common.ts`）对齐；缓存与下载（第 3–4 步）在 `ohos-clt.mjs`。不做 `~/command-line-tools`
这类机器路径猜测——没有生产者的落点只会误导。

### `.env` 与工具链脚手架

`.env`（不入库）是 CLT 路径的唯一落盘处。[scripts/ohos-env-setup.mjs](../../scripts/ohos-env-setup.mjs)
把「判断」和「获取」拆成两个入口，职责不重叠：

| 触发                                          | 行为                                                                                                |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `pnpm install` 的 `postinstall`（check 模式） | **只判断**三类输入（CLT / 运行时 / 原生编译输入）；缺了就打印下一步命令。不写盘、不下载，永远退出 0 |
| `pnpm ohos:check`（check + strict）           | 同一套判断，缺任一输入时退出 1；供 CI / 预检当门禁，不写盘、不下载                                  |
| `pnpm ohos:setup`（install 模式）             | 逐项探测 → 缺什么补什么（CLT 写进 `.env`）；失败退出 1，并给出自行下载的指引                        |

`ohos:setup` 的规则（三平台一致且幂等）：

1. 显式环境变量 `DEVECO_CLI_CLT_PATH` 有效 → 只报告，不改写 `.env`；
2. `.env` 里已有有效路径 → 只报告；
3. PATH / 项目缓存里能找到 → 写入 `.env`（`.env` 不存在时先从 `.env.example` 生成）；
4. 都没有 → 按平台下载（先打印版本、体积、缓存目录），完成后写入 `.env`。

自行下载 command-line-tools 的人不需要跑任何下载命令：把根目录写进 `.env` 的
`DEVECO_CLI_CLT_PATH`（或 export 同名变量）。脚本只做存在性校验——找不到 `bin/hvigorw` 的旧值会被
告警并继续走后面的探测，不会把人引到空目录。

CI（存在 `CI` 变量）只跳过 `postinstall` 的检查：CI 的工具链由 workflow 自己准备，本地脚手架不碰
工作区。`ohos:check` / `ohos:setup` 是显式命令，在 CI 里调用照常执行。

为什么不按 TTY 决定“要不要问”：pnpm 生命周期脚本的 TTY 取决于父进程——实测 pnpm 10.33.2 在真终端下
stdin/stdout 都是 TTY，被 agent / IDE 的管道接管时都不是。按 TTY 判断会在半自动环境里挂住，
而 `CI` 是流水线通用约定（GitHub Actions 自动 `CI=true`，`Dockerfile.desktop-e2e` 显式 `ENV CI=1`）。

缓存目录会被写一个 `{"type":"commonjs"}` 的 `package.json` 标记：仓库根 `"type": "module"`，
而 CLT 的 `hvigorw.js` / `pm-cli.js` 是 CJS，没有这层标记时 Node 会把它们当 ESM 解析并报
`require is not defined in ES module scope`（复用旧缓存时脚本会自动补写）。

写盘只发生在 `ohos:setup`；构建命令只读 `.env` / 环境变量 / 缓存，不写入。

### Windows 原生构建

**开发者看到的流程与 macOS/Linux 完全一样**：`pnpm install` → `pnpm ohos:setup` →
`pnpm ohos:run` / `pnpm ohos:bundle`。三类输入（CLT、运行时、原生编译输入）都由
`ohos:setup` 取到本地，构建命令只校验。不需要 WSL、DevEco Studio 或额外环境变量。下面只记录脚本内部按平台分流的地方，
编译参数仍然只有一份。

| 环节                | POSIX                                                                  | Windows                                                                                                                                            |
| ------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| CLT 工具入口        | `bin/hvigorw`、`bin/ohpm`（sh 脚本）                                   | `bin/hvigorw.bat`、`bin/ohpm.bat`；`.bat` 不能直接执行，统一经 `cmd.exe /d /s /c` 且命令本身加引号（CLT 常解压到含空格路径）                       |
| CLT 探测            | `sh -c "command -v hvigorw"`                                           | `where.exe hvigorw`（同样的语义，遵守 PATHEXT）                                                                                                    |
| 原生交叉编译        | 用 `aarch64-unknown-linux-ohos-clang` 包装器（自带 target 与 sysroot） | SDK 里的同名包装器**在 Windows 包内仍是 sh 脚本、不可执行**，改直调 `clang.exe -target aarch64-linux-ohos --sysroot=<native>/sysroot -fuse-ld=lld` |
| Electron 运行时解包 | `unzip` + `tar` + `cp` + `chmod`                                       | 没有 `unzip`/`cp`/`chmod`：外层 zip 用系统自带 bsdtar（`tar -xf`，Win10 1803+），复制用 `fs.copyFileSync`，不设 POSIX 权限位                       |

实现落点（改行为只改这些地方）：

- `ohos-env.mjs`：CLT 根与工具入口解析（`resolveCltTool` / `resolveCltHdc`）、跨平台 spawn（`spawnCltTool`）；
- `ohos-clt.mjs`：CLT 的「已装 > 项目缓存」发现链（`requireCommandLineTools`）与下载实现
  （`ensureCommandLineTools`，只由 `pnpm ohos:setup` 调用），三平台同一实现；
- `build-ohos-native.mjs`：`zcode_sqlite.node` / `ohos_asset_keyring.node` / `libzcode_exec_shim.so` 的**唯一**编译实现，
  `native/*/build.sh` 退化为 POSIX/CI 的薄入口，避免两套参数漂移；
- `ohos-native-deps.mjs`：原生编译输入（Node 头文件 / sqlite 融合源）的缓存与获取，见下节；
- `fetch-ohos-runtime.mjs`：运行时 zip 的解包与复制；
- `bundle-ohos.mjs` / `build-ohos.mjs` / `dev-ohos.mjs`：编排，只调用上面几个模块。

命令分组：OHOS 相关 pnpm 脚本统一用 `ohos:<动作>`（`ohos:setup` / `ohos:check` / `ohos:run` /
`ohos:bundle`），不再使用 `<动作>:…:ohos` 形式。

命名口径（新增脚本按此选名）：`<动作>-ohos.mjs` 是**命令入口**，与 pnpm 脚本对应
（`ohos:run` → `dev-ohos.mjs`、`ohos:bundle` → `bundle-ohos.mjs`），并登记到 `knip.json` 的 `entry`；
`ohos-<主题>.mjs` 是**被入口 import 的适配模块**（env / clt / native-deps / version / dev-identity），
没有 CLI 入口。`build-ohos-native.mjs`、`fetch-ohos-runtime.mjs` 同样是入口，保持"动作在前"。

### 原生编译输入从哪来（Node 头文件 / sqlite 融合源）

三个原生产物要编译，但有两样输入仓库**不收录**：`sqlite3.c`（被 `native/ohos-zcode-sqlite/.gitignore`
排除）和 `node_api.h`（属于本机 Node 安装内容）。为它们新增环境变量是不可接受的——打包命令没法表达，
`.env` 也不该堆机器路径。现在由 `ohos-native-deps.mjs` 统一处理：

| 输入          | 查找顺序                                                                                                                                         | 缺失时                                                                                                                |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| Node 头文件   | 本机 Node 安装（Windows `<root>/include/node`，POSIX `<prefix>/include/node`）→ `packages/desktop/.cache/ohos-native/node-headers/node-v<版本>/` | 从 npmmirror（失败退 nodejs.org）下载 `node-v<版本>-headers.tar.gz`，用官方 `SHASUMS256.txt` 校验 sha256 后解包进缓存 |
| sqlite 融合源 | `packages/desktop/native/ohos-zcode-sqlite/sqlite3.c`（历史手工放置/上次 staging 的拷贝）→ `.cache/ohos-native/sqlite-amalgamation-3530400/`     | 下载官方 `sqlite-amalgamation-3530400.zip`，按锁定 sha256 校验后解包进缓存                                            |

`.cache` 已被仓库 `.gitignore` 覆盖，所以这些下载物永远不入库；缓存命中即跳过，不重复联网。
获取入口是 `pnpm ohos:setup`（内部调 `ensureNodeHeaders` / `ensureSqliteSources`）；构建期用
`requireNodeHeaders` / `requireSqliteSources` 只做校验，不联网。
CI 仍可用位置参数指定融合源（`native/ohos-zcode-sqlite/build.sh <目录>`，等价 `--sqlite-src`），
其余情况一律走上面的默认链。手工预热缓存：`node packages/desktop/scripts/ohos-native-deps.mjs`。

未验证项（Windows 只做了构建机侧的脚本级验证，装机行为仍需真机确认）：

- HAP 内 `electron` 启动器的**可执行位**：NTFS 没有 POSIX 权限位，解包时无法 `chmod +x`，该位最终由 hvigor
  打包阶段决定。实测 HAP 的 zip 条目里没有任何 unix 权限位（`bsdtar` 对所有 libs 条目统一显示
  `-rw-rw-r--`），说明执行位本来就不由宿主文件系统决定，Windows 解包不做 `chmod` 不改变打包结果；
  真机上 `utilityProcess` 经它 re-exec 是否正常仍需装机确认。
- `SignHap`（有签名材料时）在 Windows 上的行为；正式包不签名，不受影响。
- `pnpm ohos:run` 的装机链路：工具解析与 hdc 调用已在 Windows 验证到“设备列表为空”这一步
  （说明 CLT/hdc 正常、只是没有设备），真机装机与启动未验证。其中 dev 自动签名会 `spawnSync("devecocli")`，
  npm 全局安装在 Windows 上是 `.cmd` shim，这条调用在 Windows 上未验证（没装 devecocli、也没设备）。

### Windows 环境实测记录（2026-11，CLT Windows x64 26.0.0.865）

- CLT 由 `ohos-clt.mjs` 自动获取：GitCode `ohos-tools` Release `v26.0` 的
  `commandline-tools-windows-x64-26.0.0.865.zip.part1` / `.part2`（各 1298MB），逐卷 sha256 校验后流式
  合并、解压到 `packages/desktop/.cache/ohos-clt/26.0.0.865/`。
- Windows 包与 POSIX 包的**目录事实**不同，适配依据就在这里：`bin/` 只有 `.bat`（没有无扩展名的
  `hvigorw`/`ohpm`），`sdk/default/openharmony/native/llvm/bin` 里唯一可执行的是 `clang.exe`
  （同名目标包装器是无扩展名的 171 字节 `#!/bin/sh` 脚本，Windows 上不可执行），`native/sysroot` 与
  `libasset_ndk.z.so` 齐全，`toolchains/hdc.exe` 存在，`tool/node/node.exe` 供 hvigor 使用。
- 全链路实测通过：workspace 构建 → desktop tsup+vite → agent bundle → 三个原生产物（均 ELF64
  AArch64，`e_machine=0xB7`）→ `hvigorw assembleHap`（4 分 05 秒 / 3 分 31 秒 / 4 分 01 秒三次实测）
  → `dist/ZCode-4.0.0-ohos-arm64-unsigned.hap`（523MB）+ `artifact-name.txt`。
- 原生编译输入由缓存自动补齐：该机 Node 安装没有 `include/node`，首次构建自动下载 Node 24.9.0 头文件与
  sqlite 融合源到 `packages/desktop/.cache/ohos-native/`，之后复用；全程没有为输入设置任何环境变量。
- 2026-11-25 清空环境实测：删 `.env` 与两个 cache 后跑 `pnpm ohos:setup` → 获取 CLT（**9 分 06 秒**，
  含下载/校验/解压）并回写 `.env`；随后 `pnpm ohos:bundle` → `BUILD SUCCESSFUL 4 分 01 秒`，
  sha256 `024ea443…303cf8`。全过程只靠 `.env`，没有 export 任何 OHOS 变量。

### Electron 运行时从哪来

`fetch-ohos-runtime.mjs` 从 GitHub Release `tools` 下载 `electron-ohos-v40.0.1.20260928.2.zip`
（华为官方原包，368MB，解开后里面还有一层 `libelectron_144.tar.gz`），校验 sha256 后解出
`libelectron.so` / `libadapter.so` / `libffmpeg.so`、启动器，以及 resfile 的 pak、icudtl、快照、
locales、vulkan。获取入口是 `pnpm ohos:setup`（也可单独跑该脚本）；构建命令只做存在性校验，
缺了报错指向 `ohos:setup`。想换源用 `ZCODE_OHOS_ELECTRON_URL`。

### dev 装机签名

正式 HAP 一律出未签名包（CI 也一样），签名由使用者自己处理，仓库不维护正式签名材料。下面这些只服务
`pnpm ohos:run` 的 dev 包——装机必须有签名。

- 方式一（AGC 手动）：在 developer.huawei.com 申请 debug 证书和 Profile，把
  `build-profile.template.json5` 复制成 `packages/desktop/ohos/build-profile.json5`（机器相关，
  不入库），替换 `signingConfigs.material` 里的 certpath / .p7b / .p12 和密码。没有签名材料时，
  hvigor 的 SignHap 会自动跳过，只出 `*-unsigned.hap`；`build-profile.json5` 缺失时
  `bundle-ohos.mjs` 会自动复制模板。
- 方式二（devecocli 捷径，外部 npm 工具，不是本项目依赖）：在 `packages/desktop/ohos/` 下跑
  `devecocli auth login`（浏览器登录华为账号，一次性），再跑
  `devecocli signature generate --product dev`，它会申请含受限 ACL 的 debug 证书，更新
  `build-profile.json5` 的 `dev` 条目并指向 `~/.ohos/config` 的材料。

两个坑要知道：

- **Profile 和包名强绑定**。debug Profile 的 `bundle-info.bundle-name` 必须等于被打 product 的
  bundleName。dev 包的包名是 product `dev` 派生的（`….zcode.dev`，见 [19](./19-开发包身份.md)）；
  `ohos:run` 缺签名时会自动调 devecocli 生成（已登录且有设备的前提下），只检查维护 `dev_*.p7b`。
  包名对不上时 `assembleHap` 停在 SignHap，报 **00303074**，只产出 `*-unsigned.hap`。
- devecocli 读的是 `AppScope/app.json5` 的 bundleName，不认 product 级覆盖，所以生成 dev 签名前后
  会临时改写再还原，规则见 [19](./19-开发包身份.md)。

### CI 用的工具链

CI 配置在 `.github/workflows/ohos-hap.yml`，要点：

- command-line-tools 用 Linux 版 26.0.0.851 官方原包，分卷托管在 [GitCode ohos-tools Release v26.0](https://gitcode.com/yuanbaobaoo/ohos-tools/releases/v26.0)
  （`commandline-tools-linux-x64-26.0.0.851.zip.part1/part2`，`cat` 合并），sha256 锁定校验；
  `OHOS_CLT_URL` 可以覆盖成任意整包直链。CI 自己装好 CLT 并设 `DEVECO_CLI_CLT_PATH`，
  所以 `postinstall` 的环境检查在 CI 里跳过（`CI` 变量），流水线不会重复下载。
- 同一批资产也是本地自动获取的来源：`ohos-clt.mjs` 里按平台 pin 了 windows-x64（26.0.0.865）、
  linux-x64（26.0.0.851）、darwin-arm64（26.0.0.865）的分卷名与 sha256。**升级 CLT 时这两处
  （CI workflow 与 `ohos-clt.mjs`）必须一起改**，否则本地/CI 会取到不同版本。
- 同一个 Release 里还托管了 HarmonyOS(aarch64) 的 CLT 分卷（例如
  `commandline-tools-harmonyos-26.0.0.201.tar.gz.part00/part01`），仅归档、未纳入自动获取清单
  （鸿蒙 PC 是部署目标，不是构建机）。直链必须是
  `.../ohos-tools/releases/download/v26.0/<资产>` 这种形态；`.../releases/v26.0/download/<资产>`
  返回的是前端壳，下不了。
- Electron 运行时同样从 GitHub Release `tools` 取：新 clone 跑一次 `pnpm ohos:setup` 要下 368MB
  （含未裁剪的调试库），CI 每次无缓存时也要下，这是选官方原包的既定代价；本地之后命中已解出的
  `ohos/` 资源，不再重复下。
- amd64 容器要 `apt install libgl1 libx11-6`：HMS 工具链的 `libimage_transcoder_shared.so` 运行时
  依赖它们，缺了 CompileResource 会失败。io_uring 补丁是纯 Node 实现，不需要 python3。

## 什么进仓库、什么不进

`pnpm install`、`pnpm ohos:run`、`pnpm ohos:bundle` 能生成的产物一律不入库。

**不入库**

| 类别                 | 内容                                                                                                                                                                                         |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 依赖与缓存           | `node_modules/`、`dist/`、`out/`、`oh_modules/`、`.hvigor/`、`build/`、`hnp/`                                                                                                                |
| 工具链与编译输入缓存 | `packages/desktop/.cache/`：`ohos-clt/`（CLT，下载包 2.1–2.7GB、解压后约 7.5GB）、`ohos-native/`（Node 头文件 + sqlite 融合源，约 69MB）。仓库 `.gitignore` 的 `.cache` 规则覆盖，命中即复用 |
| 机器相关配置         | `.env`（CLT 路径）、根 `build-profile.json5`（含签名材料；只入库 `build-profile.template.json5`）、`AppScope/app.json5`                                                                      |
| 组装产物             | `web_engine/src/main/resources/resfile/resources/`                                                                                                                                           |
| Electron 运行时      | 三件 .so、启动器、`chrome_*.pak`、`icudtl.dat`、`resources.pak`、快照、`locales/*.pak`、`vulkan/`；`hnp/lib/arm64-v8a/` 下的 .so 副本由脚本同步                                              |
| HAP 资源             | `config/`、`glm/`、`tools/`、`icon.png` 由 build-ohos 硬校验后 staged，缺 glm/tools 直接失败（`--skip-agent` 只跳 glm），免得产出装机不可用的包                                              |
| 原生适配产物         | `zcode_sqlite.node`、`ohos_asset_keyring.node`、`libzcode_exec_shim.so`，由 build-ohos.mjs 按需编译并拷进 HAP libs                                                                           |

**入库**：源码与模板（`build.sh`、`.cpp`、`build-profile.template.json5`、字体与 OFL 等），
锁文件（`pnpm-lock.yaml`、`oh-package-lock.json5`）保留以保证可复现。

**例外**：模块级的 `<module>/build-profile.json5`（`entry`、`web_engine`）不含机器信息，hvigor 在工程
配置阶段又强制要求，缺了报 `00304056 Not Found`，所以必须入库。忽略规则因此只锚定根目录的
`/build-profile.json5`。

## 常用命令

`pnpm ohos:setup` 一次备齐三类输入：CLT（下载 2.1–2.7GB、解压后约 7.5GB，落在
`.cache/ohos-clt/`）、Electron 运行时（368MB，落到 `ohos/` 资源目录）、原生编译输入（Node 头文件 +
sqlite 融合源，约 13MB，落到 `.cache/ohos-native/`）。构建命令只校验，缺了会提示先跑它；之后都命中本地。

```bash
pnpm ohos:bundle          # 打包，产物落 packages/desktop/dist/（未签名 + 可选签名版）
pnpm ohos:run             # 默认全量：dev HAP 装到 hdc 能看到的设备并启动（~30s，覆盖已装版本）
pnpm ohos:run -- --build  # 全量闭环（~120s）：desktop 生产构建 + agent CLI 一起重建
pnpm ohos:run -- --agent  # 只重建 agent CLI 包（改 apps/zcode-cli 后用）
pnpm ohos:run -- --hqf    # 增量热推（单设备，要 --device 指定）：签名 hqf → quickfix → 重启（~8s）
                          # 无基线 / 未安装 / 有删除 / 变更超阈值时自动回退全量
```

`--build` 必须隐含 agent 重建：glm 默认是从 `bundled-agents` 的旧产物 stage 的，漏掉这一步会把
`apps/zcode-cli` 的改动静默撤掉（官方插件会整体消失）。

手动分步（正式身份，product=default）。手动步骤里的 `hvigorw` / `hdc` 取自 `.env` 指向的 CLT
（`<CLT>/bin/hvigorw`、`<CLT>/sdk/default/openharmony/toolchains/hdc`；Windows 是 `hvigorw.bat` / `hdc.exe`），
所以先把这两个目录加进 PATH，或直接写绝对路径：

```bash
node packages/desktop/scripts/build-ohos.mjs              # 构建产物 + 组装 resfile
cd packages/desktop/ohos && hvigorw assembleHap --mode module -p product=default -p buildMode=debug --no-daemon
hdc install -r packages/desktop/ohos/entry/build/default/outputs/default/electron-default-signed.hap
hdc shell "aa start -a EntryAbility -b io.github.yuanbaobaoo.zcode"
```

手动分步（开发身份，product=dev，产物名和目录都带 dev，身份表见 [19](./19-开发包身份.md)）：

```bash
cd packages/desktop/ohos && hvigorw assembleHap --mode module -p product=dev -p buildMode=debug --no-daemon
hdc install -r packages/desktop/ohos/entry/build/dev/outputs/dev/electron-dev-signed.hap
hdc shell "aa start -a EntryAbility -b io.github.yuanbaobaoo.zcode.dev"
```

开发包和正式包可以同机共存。CI 方面：push `v*` tag 会自动构建未签名 HAP 并发到 GitHub Release。

## 常见坑

| 现象                                                                         | 原因与处理                                                                                                                                                                               |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| "1 秒构建成功"，装上还是旧包                                                 | hvigor 增量不感知 resfile 变化。手动装机前清 `packages/desktop/ohos/{.hvigor,entry/build,web_engine/build}`，bundle/dev 脚本已自动处理                                                   |
| `aa start` 报 10106102                                                       | 设备锁屏。developer mode 不会自动解锁，手动解锁后重试                                                                                                                                    |
| 看不到应用日志                                                               | console.log 进 hilog（tag `Electron`），默认缓冲几十秒就被系统日志滚没。先 `hdc shell "hilog -G 16M"`，再 `hdc shell "hilog -x -T Electron"`                                             |
| HAP libs 里 .node/.so 的 md5 对不上                                          | hvigor 会 strip 去符号，正常现象。对账用行为验证，别按 md5 判旧产物                                                                                                                      |
| 报「没有 `<平台>` 的 command-line-tools 自动获取源」                         | 当前平台/架构不在自动获取清单里（清单见 `ohos-clt.mjs`）。手动装 CLT 后设 `DEVECO_CLI_CLT_PATH` 或把 `bin/` 加进 PATH                                                                    |
| 构建报「Electron 运行时或 resfile 资源缺失」                                 | 构建期只校验不下载：先跑 `pnpm ohos:setup`（或单跑 `fetch-ohos-runtime.mjs`）                                                                                                            |
| 构建报「未找到 Node 头文件 / sqlite 融合源」                                 | 同上：`pnpm ohos:setup` 一并备齐原生编译输入（约 13MB），也可手工预热 `ohos-native-deps.mjs`                                                                                             |
| 报 `require is not defined in ES module scope`（`hvigorw.js` / `pm-cli.js`） | CLT 缓存目录缺 CJS 标记：仓库根是 `"type":"module"`。删掉 `packages/desktop/.cache/ohos-clt` 重跑，或在 `<版本>/package.json` 写 `{"type":"commonjs"}`（脚本会自动补，手工拷贝的包不会） |
| `pnpm ohos:setup` 后多出 `.env`                                              | 预期行为：脚手架生成/回写 CLT 路径。`.env` 已 gitignore，不要提交                                                                                                                        |
| Windows 报「未找到 command-line-tools（hvigorw）」                           | 手工准备过 CLT 但位置不对：`DEVECO_CLI_CLT_PATH` 要指向 `bin/` 的上一级（Windows 包入口是 `bin\hvigorw.bat`）。不设也行——`pnpm ohos:setup` 会取                                          |
| Windows 报「未找到 OHOS SDK clang」                                          | Windows 版 SDK 的目标包装器是 sh 脚本，脚本只用 `clang.exe`。确认 `sdk\default\openharmony\native\llvm\bin\clang.exe` 存在，且 `DEVECO_CLI_CLT_PATH` 指向的是 CLT 根（`bin/` 的上一级）  |
| Windows 报「无法获取 Node 头文件」                                           | 本机 Node 安装不带 `include/node`，且从 npmmirror / nodejs.org 取头文件失败。可手工把 `include/node/node_api.h` 放进 `packages/desktop/.cache/ohos-native/node-headers/node-v<版本>/`    |

### 调试端口（两个，别混）

| 端口 | 归谁                                                                          | 怎么用                                                                                                                                                              |
| ---- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 9229 | renderer 的 Chromium DevTools（main 早期设的 `--remote-debugging-port=9229`） | `hdc fport tcp:9229 tcp:9229` 后开 `chrome://inspect`，能取 DOM 和 Performance trace；仓库的真机 UI 自动化（`ohos-device-cdp.mjs` 的 `ZCODE_CDP_BASE`）默认连这个口 |
| 9330 | main 进程的 Node inspector（厂商默认参数 `--inspect=9330`）                   | 需要调试 main 时单独 fport                                                                                                                                          |

历史坑：厂商默认参数原来是 `--inspect`（默认 127.0.0.1:9229），会抢占 9229，导致
`remote-debugging-port` 绑定失败，`chrome://inspect` 里只能看到 `node.js/…` 的 Node target，
`ohos-device-cdp.mjs` 报 `no page target`（真机实测确认）。所以 `--inspect` 固定在 9330，9229 留给
renderer。

真机 UI 自动化的用法见 `packages/desktop/scripts/ohos-device-cdp.mjs` 头注。
