# 15 平台适配治理与不变量

平台适配最容易腐化的不是代码，而是**边界**：同一能力出现两条通道、平台身份靠猜、桥路径各自拼。
本文固定这些边界与不变量；改适配层前先对照。

## 背景：三个问题

1. **两条控制通道并存**：原型期 `ohos_hdc` 有 `ui_input`/`dump_layout`/`screenshot`（dev 档、依赖
   开发者模式），产品化 CUA 又走 ArkTS 桥。同一能力两套语义、两套审批、两套失败模式。
2. **平台身份是隐式全局**：`process.platform === "ohos"` 只在 Electron 拉起的进程里成立；MCP
   子进程跑在用户环境的 Linux node 里，平台判定失效 → CUA 退化为占位实现。
3. **适配面没有边界**：文件桥路径、状态所有者、请求协议散落在多文件，改一处漏一处。

## 决策

| 决策 | 内容 |
| --- | --- |
| **D1 单控制通道** | 删除 dev 档控制动作（`ui_input`/`dump_layout`/`screenshot`），控制只保留 CUA → ArkTS 桥；`ohos_hdc` 只留 list/shell/file/install |
| **D2 平台身份显式化** | `ZCODE_OHOS_RUNTIME=1` 为权威信号（host 引导注入、env 继承）；`isOhosRuntime()` 只做加法，缺省判定不变 |
| **D3 一个事实源** | 路径、状态、请求协议各有唯一所有者；main 只读/写请求，ArkTS 只写状态；路径常量由契约测试钉住 |

## 目标架构

```text
控制（唯一通道）
  Renderer ──IPC──▶ main ──文件桥──▶ ArkTS ──▶ 系统能力
  设备调试（旁路，不控制）
  ohos_hdc / devecocli ──hdc-direct──▶ hdcd
```

- **控制**：CUA runtime（`packages/zcode-cua/ohos-computer-use.js`）编排，ArkTS 执行；
  审批沿用 CUA 既有流程。
- **调试**：`ohos_hdc` 与 devecocli 只做 list/shell/file/install/设备信息，不提供 UI 控制。

## 不变量

| # | 不变量 | 钉住方式 |
| --- | --- | --- |
| 1 | 控制动作只在 ArkTS 桥实现；`ohos_hdc` 不含控制动作 | 契约/单测 + code review |
| 2 | 平台身份以 env 信号为准，缺省行为与旧版逐字一致 | `ohosRuntimeIdentity.test.ts` |
| 3 | 桥路径唯一来源 `ohos/paths.ts`；ArkTS 与 Node 常量一致 | `ohosBridgePathsContract.test.ts` |
| 4 | `status.json` 只由 ArkTS 写；main 只读并推送 | `desktopOhosComputerControlPermission.test.ts` |
| 5 | 权限门禁 = `controlDevice && screenCapture` 两权限；缺一不放行 | `computerUseAvailability.test.ts` + 设置页 gate 测试 |
| 6 | 启动不弹任何授权框；只有用户点「去开启」才跳设置页 | 冷启动真机日志 |
| 7 | 权限丢失且插件仍启用 → 自动关闭并提示 | `ohosCuaPermissionReconcile.test.ts` |
| 8 | 截图唯一路径 `@ohos.screenshot`；失败如实 `unavailable` | CUA 测试 + 真机日志 |
| 9 | manual_settings 权限只用 `openPermissionOnSetting`，不用 `requestPermissionOnSetting` | 03 的 API 契约 |
| 10 | 文件桥原语（原子写、坏文件 fail-closed）集中在 `fileBridge.ts` | `ohosFileBridge.test.ts` |

## 门禁

- `pnpm architecture:check -- --changed`：OHOS 适配文件必须在 policy 例外清单内；新文件需登记。
- `ohosPlatformReadGuard.test.ts`：禁止 main 在 OHOS 读非白名单路径。
- `desktopMainChildProcessGuard.test.ts`：main 的同步 spawn 必须登记；异步只允许登录 shell/终端两条路径。
- 测试文件必须登记 `scripts/engineering-test-files.json`，否则被 `retired-app-unit-evidence` 判退役。
- 文档中的测试引用需与清单一致（`test:architecture` 会扫）。

## 移除清单（已删除，不要复活）

| 项 | 原因 |
| --- | --- |
| `ohos_hdc` 的 `ui_input`/`dump_layout`/`screenshot` | dev 档控制动作，单一控制通道 |
| native `desktopCapturer` / hdcd 取屏回退 / main shots 子通道 | 被 `@ohos.screenshot` 取代；厂商端口不可用 |
| `CUSTOM_SCREEN_RECORDING` 声明与门禁 | 录屏走截屏帧流；权限不再需要 |
| `requestPermissionOnSetting` 请求 manual_settings | 恒 `12100014`，API 用错 |
| `pollJsonRequests` 与 shots 目录 | 随 shots 通道删除 |

## 验收

1. `ohos_hdc` 只有 5 个调试动作；任意 UI 控制调用不存在。
2. `isOhosRuntime()` 在 Linux node 子进程里仍返回 true（env 信号）。
3. 桥路径契约测试通过；ArkTS 与 main 目录名完全一致。
4. 两权限齐 → 开关可开；缺一 → 锁定 + 对话框列出缺项。
5. 冷启动零授权弹窗；撤销权限后启动自动关插件。
6. `pnpm architecture:check -- --changed` 与相关单测全绿。
