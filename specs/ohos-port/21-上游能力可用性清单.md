# 21 上游能力可用性清单

**用途**：上游代码合并 ≠ 鸿蒙可用。本文登记每一项「已合入但被阻断 / 隐藏 / 降级 / 待确认」的能力，
避免下次同步（或排查问题时）把"代码在"当成"功能在"。

维护规则：

1. 每次上游同步后，对照上游新增能力逐项确认状态；新增阻断必须同时在这里登记。
2. 状态分四档：**A 完全不可用（阻断）**、**B 入口在但不可用/降级**、**C 仅部分场景不可用**、
   **D 已适配但不是原样复刻（替代 / 曲线实现）**。
3. **"适配过"不等于"原样复刻"**：只要鸿蒙上的实现不是上游那份代码/进程/协议原封不动地跑，必须登记到 D 档，
   写清上游做法、鸿蒙做法与两者的差异（代价、边界），避免下次同步把它当等价复刻改坏。
4. 每条必须给依据（代码位置或 spec 编号）与验证方式；拿不到证据的写"待确认"，不猜。
5. 平台原因写在「原因」列，不写在上游代码里；上游代码只允许"薄包装 + 早退"（spec 15）。

## D · 已适配但不是原样复刻（替代 / 曲线实现）

这一档**功能是能用的**，但实现路径与上游不同：没有原样复刻，而是用另一套机制绕过平台限制。
每条登记「上游怎么做 / 鸿蒙怎么做 / 与上游的差异（代价与边界）」，避免下次同步上游时把曲线实现
当成"等价复刻"去改，也避免误以为可以直接删掉这段适配。

> 判定口径：只要鸿蒙上的实现不是上游那份代码/进程/协议原封不动地跑，就属于本档；纯"入口禁用/隐藏"
> 属于 B 档，不在这里。

### D1 终端：node-pty → main 托管 zsh + 三条管道

- **上游**：host 进程用 `node-pty` 的 `forkpty` 开真 PTY，前端接 xterm.js。
- **鸿蒙**：应用域被 SELinux 拒 `/dev/ptmx`、`/dev/pts`，改为 main 域 `spawn('/usr/bin/zsh', ['-il'])`，
  `stdio: ["pipe","pipe","pipe"]`，经专用 MessagePort 中继给 host 的 `ohosTerminalPty.ts`。
- **差异**：没有内核行规程（内核 echo、退格、`\r`→`\n` 改由 `echoTransform`/`#normalizeOutput` 补）；
  没有作业控制与 Ctrl-C 中断；`isatty()` 为 false、`cols/rows=0`、`resize()` 空实现；vim/top/less 全屏不可用。
- **依据**：spec 02:135-144；spec 03:64；`packages/desktop/src/main/desktopTerminalPtyRelay.ts`。
- **验证**：`ohosTerminalPtyRelayGuard.test.ts`；真机在终端里跑 `tty` / `vim`（见 C 档）。

### D2 系统钥匙链：`@napi-rs/keyring` → 自建 Asset Store 绑定 + 私钥文件回退

- **上游**：主密钥存系统钥匙链（`@napi-rs/keyring`），Host 经凭据桥向 Main 要加解密。
- **鸿蒙**：自写 NAPI 绑定 `ohos_asset_keyring.node`（`libasset_ndk.z.so`），别名 = `ZCode Credential Encryption:<sha256(凭据文件绝对路径)>`；
  组件缺失时回退同目录 0600 私钥文件，凭据以 `enc:v2:env:` 落盘。
- **差异**：没有桌面原生包；密钥归属改成"按数据根隔离的系统资产条目"；回退来源不同（`env` 而非 `os`）。
- **依据**：spec 16 决策表 D1–D5；`packages/desktop/src/main/ohos/ohosAssetKeyStore.ts`、`ohosCredentialBootstrap.ts`。
- **验证**：spec 16「验收」；真机删资产绑定后启动应见回退 warn 且仍能保存登录。

### D3 数据库：Node 内置 `node:sqlite` → 自研 NAPI 绑定 + 兼容层

- **上游**：直接 `import "node:sqlite"` 的 `DatabaseSync`/`StatementSync`。
- **鸿蒙**：运行时是 Node 20，没有该内置模块；`nodeSqliteCompat` 提供同形 API，底层是 `zcode_sqlite.node`
  （`packages/desktop/native/ohos-zcode-sqlite`，模块初始化顺带 `prctl(jit)`）。
- **差异**：写语句把参数内联进 SQL 文本再走 `exec()`（native 的 `run()` 对写语句是空操作）；
  `backup()` 用 `VACUUM INTO` 等效；**>2^53 的 INT64 返回 BigInt**，而 Node 内置会抛 `ERR_OUT_OF_RANGE`
  —— 这个语义差是「会话索引 BigInt」待确认项的嫌疑根因。
- **依据**：spec 02:121-133；`packages/shared/src/nodeSqliteCompat.ts`；`ohos-zcode-sqlite/zcode_sqlite.c`。
- **验证**：`packages/shared/test/nodeSqliteCompat.test.ts`；`node:sqlite` 被 tsup 重写到 shim（`tsup.config.ts`）。

### D4 agent 进程形态：独立子进程 → host 进程内 Worker

- **上游**：Host 以独立子进程跑 `zcode.cjs`，stdio 管道承载 JSON-RPC。
- **鸿蒙**：appspawn 隔离下 exec 链路受限，agent 改为 host 里的 `worker_threads` Worker，用管道伪装 ChildProcess，
  Worker `online` 映射成 spawn 事件（runtime lifecycle "available" 的触发源）。
- **差异**：`console.log` 会污染协议管道（OHOS 侧模块只能用 `console.error`/serviceLogger）；worker `exit`
  在 stdout 异常关闭时可能不触发，进程回收不能只靠 exit。
- **依据**：spec 02「agent 以 host 进程内 Worker 运行」；`packages/services/src/zcode-agent/`。
- **验证**：`ohosRuntimeIdentity.test.ts`、agent 生命周期相关工程测试；真机 agent 会话。

### D5 用户 shell 环境：继承登录 shell → 采集快照 v3 再合并

- **上游**：GUI 进程直接继承用户 shell 环境（macOS/Windows 由系统注入）。
- **鸿蒙**：GUI 继承不到 zsh 登录环境、appspawn 不继承 main env。main 跑 `/usr/bin/zsh -ilc 'env -0'` 采集快照，
  落盘 `<realHome>/.zcode/v2/ohos-login-env.json`（v3 格式），host 引导时合并：PATH 整体替换、其余键覆盖。
- **差异**：只有"登录 shell 快照"一个来源，不重放 rc；剔除 `_/SHLVL/PWD/OLDPWD/TERM` 与空值；
  首窗等快照有界 4s；`SHELL_EXPORT_SKIP_KEYS` 保护 HOME/XDG/TMPDIR 等应用管理键。
- **依据**：spec 02「登录 shell 快照 v3」；`packages/services/src/ohos/ohosUserShellEnv.ts`。
- **验证**：`ohosSpawnCompat.test.ts`、`ohosTmpDirAndSpawnCwd.test.ts`；真机 agent 能看到工具链。

### D6 缺失的 `/usr/bin/env`：LD_PRELOAD exec shim 改写 shebang

- **上游**：脚本型工具直接依赖 `#!/usr/bin/env node` 等 shebang。
- **鸿蒙**：agent 视图没有 `/usr/bin/env`；host 注入 `LD_PRELOAD=<bundle libs>/libzcode_exec_shim.so`，
  在 `execve` 时把缺失解释器的 shebang 改写成 `/bin/env …` 交给 PATH 解析。
- **差异**：只在 agent 视图生效；解释器存在时透明；不提供 PATH 本身（PATH 仍来自 D5 快照）。
- **依据**：spec 02「agent 命令无缝：LD_PRELOAD exec shim」；`packages/desktop/native/ohos-exec-shim`。
- **验证**：真机在 agent 里执行 npm/包管理器 shim 脚本。

### D7 临时目录与 socket 目录：`/tmp` → `~/.zcode/tmp`；AF_UNIX → el2 目录

- **上游**：用系统 `/tmp`（`os.tmpdir()`）与工作区内的 socket 路径。
- **鸿蒙**：平台 `/tmp` 属主 1076、`0770`，应用不可写 → `TMPDIR=<realHome>/.zcode/tmp`（同文件系统，move 到工作区不 EXDEV），
  只在 host（agent）与终端生效，main 保持原值；AF_UNIX 路径型 bind 在 `/storage/Users` 被拦 → host 另建
  `/data/storage/el2/base/files/tmp` 并以 `ZCODE_OHOS_SOCKET_DIR` 下发。
- **差异**：两套目录、两种作用域；node-repl broker 优先用 socket 目录，其余 tmpdir 用法仍是文件操作。
- **依据**：spec 02「TMPDIR = `~/.zcode/tmp`；socket 目录单独走 el2」。
- **验证**：`ohosTmpDirAndSpawnCwd.test.ts`、`ohosSpawnCompat.test.ts`。

### D8 io_uring：seccomp 拒 syscall 425 → 构建期二进制补丁 + env 保险带

- **上游**：直接用 libuv 默认异步 IO（io_uring）。
- **鸿蒙**：任一进程首次异步文件 IO 即 SIGSYS；构建期对 `libelectron.so` 做 4 字节×2 二进制补丁禁用 io_uring
  （`ohos-patch-libelectron.mjs`，用 `UV_USE_IO_URING` 字符串反查 adrp/add 引用对动态锚定，幂等）；
  host 入口再加 `UV_USE_IO_URING=0` 兜底（仅在 env 恰好可达时生效）。
- **差异**：补丁是"改别人的二进制"，升级 Electron 端口后必须重新锚定；宿主不继承 main env 时兜底无效。
- **依据**：spec 02「seccomp 拒 io_uring」；`packages/desktop/scripts/ohos-patch-libelectron.mjs`。
- **验证**：构建日志的补丁命中信息；真机启动无 SIGSYS。

### D9 可写可执行内存：V8 CodeRange OOM → 用原生绑定副作用解锁 JIT

- **上游**：桌面沙箱允许 RWX，不处理。
- **鸿蒙**：沙箱默认禁 RWX，V8 保留 CodeRange 会直接 OOM。各进程入口早期 `loadNodeSqlite()` 触发
  `zcode_sqlite.node` 模块初始化里的 `prctl(0x6a6974)`（ASCII "jit"），顺带解锁 JIT；agent 经 host env 继承。
- **差异**：解锁动作**寄生在 sqlite 绑定里**，不是独立能力；Chromium 侧靠 `ALLOW_WRITABLE_CODE_MEMORY` 权限阻止 jitless 注入。
- **依据**：spec 02「沙箱默认禁 RWX」；`packages/shared/src/ohosNodeRuntimeCompat.ts`。
- **验证**：`desktopOhosRenderCompatBootstrap.test.ts` 相关链路；真机重负载 JS 不 SIGSEGV。

### D10 电脑控制：macOS Helper.app/TCC → ArkTS 文件桥 + `@ohos.screenshot`

- **上游**：macOS 由签名 Helper 进程 + broker socket + TCC 授权做截图/输入注入。
- **鸿蒙**：没有 Helper、没有 broker socket；runtime 运行在 agent 进程内，用独立的非敏感标记
  `isOhosCuaRuntimeEnabled` 启用，截图走 `@ohos.screenshot`，输入注入走 ArkTS 注入桥，权限门禁是
  `controlDevice && screenCapture` 两权限聚合。
- **差异**：没有独立进程与 broker；不能借用 broker socket 键（会被 env 清洗剔除）；manual_settings 只用
  `openPermissionOnSetting`；录屏走截屏帧流，不申请 `CUSTOM_SCREEN_RECORDING`。
- **依据**：spec 13、spec 15 不变量；`apps/zcode-cli/packages/node-repl-host/src/server.ts` 的 `captureComputerUseRuntimeFromEnvironment`。
- **验证**：`computerUseAvailability.test.ts`、`computerUseOhosPermissionGate.test.ts`、`ohosCuaPermissionReconcile.test.ts`；真机截图/输入。

### D11 设备通道：官方 hdc server → 随包 `hdc-direct` CLI

- **上游**：用系统 `hdc`（官方 server）连设备。
- **鸿蒙**：官方 hdc server 在沙箱里起不来；改为随 HAP 打 `hdc-direct` CLI，直连设备 hdcd（TCP target），

- **依据**：spec 11；`packages/desktop/scripts/bundled-hdc-direct-assets.mjs`、`packages/services/src/ohos*`。
- **验证**：`bundledHdcDirectAssets.test.ts`、`ohosHdcTarget.test.ts`；真机设备列表与 shell。

### D12 更新：electron-updater → GitHub Release 三级探测 + 浏览器下载

- **上游**：electron-updater 查 manifest → 下载 → `quitAndInstall`。
- **鸿蒙**：整条链路禁用（见 A 档），改为 main 侧查 GitHub Release：`api.github.com /releases/latest` →
  `releases.atom` → gitcode 镜像 `/info/refs?service=git-upload-pack` 三级降级，"前往下载"用系统浏览器发布页。
- **差异**：无自动下载/安装/重启；更新请求必须直连（代理会被 404）；api.github.com 匿名配额常态超限，
  所以三级降级是常态路径；跳过版本存 `skippedElectronUpdateVersions["ohos"]`。
- **依据**：spec 04「更新检查」「状态与事件」。
- **验证**：spec 04 验收；真机检查更新。

### D13 目录 / 全盘文件授权：macOS TCC → ArkTS UriGrantHelper + 桥文件回流

- **上游**：macOS 用 TCC 授权目录访问，系统弹窗一次。
- **鸿蒙**：HOME 对应用常无写权（首个 logger mkdir 即 EPERM）→ 引导期做"真实写权探测"，不可写先落应用沙箱保启动，
  首窗就绪后弹一次目录授权（ArkTS `UriGrantHelper` 持久化），授权后迁回真实 home；全盘/Desktop 两类权限
  状态经桥文件回流 main 再推 renderer。
- **差异**：启动路径与数据根可能先后变化（先沙箱后迁移）；授权是"按需一次"，不是每次启动都弹；不与 macOS TCC 等价。
- **依据**：spec 08、spec 18；`packages/desktop/src/main/desktopOhosFullDiskAccess.ts`、`desktopOhosHomeGrant.ts`。
- **验证**：`desktopOhosFullDiskAccess.test.ts`、`ohosFullDiskAccessPrompt.test.ts`；真机首次启动。

### D14 系统栏主题：`nativeTheme` → `setColorMode` 三态 + 窗口主题桥文件

- **上游**：`nativeTheme.themeSource` 控制窗口/系统栏深浅。
- **鸿蒙**：`nativeTheme.themeSource` 在 libelectron 内空转；改为 ArkTS `setColorMode` 三态跟随（浅/深/跟随系统），
  窗口主题经桥文件 `window-theme.json` 同步给 ArkTS 侧。
- **差异**：只能三态深浅，不随窗口内容自适应；标题栏/系统栏由 ArkTS 绘制。
- **依据**：spec 07；`packages/desktop/src/main/desktopOhosWindowTheme.ts`。
- **验证**：spec 07 验收；真机切换深浅色。

### D15 打开目录：`shell.openPath` → `shell.showItemInFolder`

- **上游**：`shell.openPath` 打开任意路径（含目录）。
- **鸿蒙**：端口的 `openPath(目录)` 没有处理器且恒报成功；目录改走 `shell.showItemInFolder` 定位（文件仍走 openPath）。
- **差异**：目录从"打开"变成"在文件管理器里定位"。

### D16 麦克风权限：`systemPreferences` → ArkWeb `getUserMedia` + PermissionManagerAdapter

- **上游**：main 的 `systemPreferences.askForMediaAccess` / `tccutil` 管理麦克风授权。
- **鸿蒙**：没有 `systemPreferences`；main 的 `ensureAccess` 恒返回 `unsupported`（**不阻断**），
  真正授权由 ArkWeb 在 `getUserMedia` 时经 `PermissionManagerAdapter` 调 `requestPermissionsFromUser(['ohos.permission.MICROPHONE'])`。
- **差异**：授权时机从"点按钮前"挪到"采集时"；拒绝后没有"去设置"引导（缺 OHOS 版 `microphone.openSettings`）。

- **验证**：spec 17 验收；真机点麦克风看系统弹窗。

### D17 进程标题：`process.title`/`app.setName` → 共享 guard + 跳过 `setName`

- **上游**：用 `process.title`、`app.setName` 设置进程名/窗口名。
- **鸿蒙**：Electron 的 `process.title` setter 会触发 `uv_set_process_title` memset 下溢并 SIGSEGV 整进程；
  统一走 `assignProcessTitle` 共享 guard（OHOS 下跳过 setter），`app.setName` 在 OHOS 直接不调用。
- **差异**：进程名不按原逻辑设置；需要一个新的共享 helper 承载"设名"语义。
- **依据**：`packages/shared/src/process-names.ts` 的 `assignProcessTitle`；`packages/desktop/src/main/index.ts`；`apps/zcode-cli/packages/cli/src/process-name.ts`。
- **验证**：`ohosRuntimeIdentity.test.ts` 相关；真机启动不崩。

### D18 资源路径判定：`app.isPackaged` → `app.isPackaged || isOhosRuntime()`

- **上游**：用 `app.isPackaged` 区分打包/开发态资源路径。
- **鸿蒙**：`app.isPackaged` 恒 false，但 HAP 已把图标等资源 staged 到 resources 根 → 判定改为
  `packagedResources = app.isPackaged || isOhosRuntime()`，图标/资源从 resourcesPath 取。
- **差异**：OHOS 上"开发态"也走打包路径；docs 里的开发态资源分支在鸿蒙不生效。
- **依据**：`packages/desktop/src/main/index.ts` 的 `packagedResources`。
- **验证**：真机窗口图标/About 图标正常。

### D19 版本号来源：`app.getVersion()` → `build-meta.json` 的 `ohosReleaseVersion`

- **上游**：`app.getVersion()` 取应用版本。
- **鸿蒙**：端口对该值行为未验证，改为读 `out/metadata/build-meta.json` 的 `ohosReleaseVersion`（HAP versionName = tag 版本）；
  开发态为 null 时禁用更新检查，可用 `ZCODE_OHOS_UPDATE_DEV_VERSION` 覆盖。
- **差异**：版本号唯一事实源从 `package.json`/Electron 内置改为构建元数据；tag 语法与 versionCode 另有规则。
- **依据**：spec 04「版本号规则」「客户端当前版本」。
- **验证**：`ohos-version.test.mjs`、`ohosReleaseVersion.test.ts`。

### D20 退出清理：`before-quit`/`will-quit` → ArkTS `EntryAbility.onDestroy`

- **上游**：在 Electron 退出钩子里做清理（撤销通知等）。
- **鸿蒙**：关窗后进程由系统直接终结，Node/Electron 的 quit 钩子不跑；依赖 quit 生命周期的清理移到
  ArkTS `EntryAbility.onDestroy`（系统保证调用），现行例是退出时撤销任务通知。
- **差异**：清理时机与 owner 都变了；在 main 里挂 `before-quit` 的清理在鸿蒙**永远不执行**（新增清理逻辑必须同时看 ArkTS 侧）。
- **依据**：spec 02「Electron 的 quit 生命周期在 OHOS 不执行」；`ohos/web_engine/.../EntryAbility.ets`。
- **验证**：真机退出后无残留通知（历史日志 + spec 02 记录）。

### D21 剪贴板图片：Electron 44 `ClipboardItem` → 回退 `writeImage`

- **上游**：`clipboard.write([new ClipboardItem(...)])`（Electron 44 线）。
- **鸿蒙**：运行时是 Electron 40，没有 `ClipboardItem`；写图回退 `clipboard.writeImage`，避免具名导入让主进程起不来。
- **差异**：`writeImage` 在端口上是否可用**尚未验证**（见「待确认」第 2 项），失败时抛 `Clipboard image write is unavailable`。
- **依据**：`packages/desktop/src/main/pluginSandbox/clipboardImage.ts`；C 档同项。
- **验证**：真机插件"复制图片"→ 粘贴到系统应用。

### D22 模拟器渲染：GPU 直通 → 模拟器判据 + ANGLE/SwiftShader 三态

- **上游**：直接走 GPU 加速渲染。
- **鸿蒙**：模拟器的 GPU 直通撑不住 Chromium EGL（黑屏）；启动早期（app ready 前）按设备判据切 ANGLE + SwiftShader，
  判据缺失一律按真机处理（绝不误降级真机），设置页给三态兜底。
- **差异**：模拟器上走软件渲染（性能代价）；判据来自设备 profile/桥文件，而不是 Chromium 自检。
- **依据**：spec 06；`packages/desktop/src/main/desktopOhosRenderCompatBootstrap.ts`。
- **验证**：`desktopOhosRenderCompatBootstrap.test.ts`；模拟器启动不黑屏。
