# 23 预装工具与文档环境适配（不排期）

Status: not-planned
最后更新：2026-11-24

## 1. 决策

**2026-11-24 决定：鸿蒙端暂不适配预装工具链与文档转换，当前不排期。**

具体不做的范围：

- 不新增 OHOS 的 catalog 目标、资源 recipe、CDN 资源；
- 不做 OHOS Python/Pandoc/qpdf/Poppler/LibreOffice 的预装打包；
- 不接 `selfsign` 到预装安装链路；
- 不修改 `platform.isOhos` 的帮助菜单置灰；
- 不修改预装进程、安装记录、入口、下载/回收逻辑；
- 不修改四个文档插件的调用逻辑或 env_check。

本文只是**调研与决策记录**，不是实施 ticket。后续不要按本文旧版本里的 P0–P4 计划直接开工。

## 2. 对产品的影响

保持现状：

- 帮助菜单「预装工具」继续置灰；
- 文档技能的创建/编辑/转换仍按现有逻辑报「预装未就绪」；
- 不新增半可用的文档 UI，也不做「部分工具可用」的假象；
- 如果用户自己通过 Harmonybrew 装了 Python/工具，插件的系统回退逻辑可能仍然可用，但**不是产品承诺**，也不做验收。

## 3. 为什么不做

这不是“技术上完全不可能”，而是**产品化成本与收益不匹配**：

1. **上游没有 OHOS 目标**  
   catalog/platform、资源 recipe、安装记录、签名都要新增 OHOS 分支；上游同步时还要持续维护，容易变成长期分叉。

2. **不是“补五个资源”就结束**
   - Python 资源要按上游 `python/` + `overlay/` + `constraints.txt` 重做，不能用 brew venv 代替；
   - matplotlib 在 OHOS 没有 musllinux aarch64 wheel，必须源码构建；
   - qpdf/Poppler CLI 有 OHOS 制品，但依赖/打包仍需验证；
   - LibreOffice headless 有制品，但 filter/版式未验证；
   - ELF 还要接 `selfsign`，HAP 签名与 ELF 签名边界要长期维护。

3. **半成品会误导用户**  
   只放开入口、或只支持 docx/xlsx/pptx 而转换不可用，会让用户以为文档能力已完整适配；不如保持现状和明确报错。

4. **当前优先级不支持**  
   这项适配跨 catalog、构建、签名、Python 资源、LibreOffice 和插件验收，属于独立项目，不适合在当前版本里顺手做。

## 4. 调研摘要（仅供未来重启评估）

以下结论来自 2026-11-24 真机/资料调研，**不代表当前要做**：

| 资源        | 结论                                                                         |
| ----------- | ---------------------------------------------------------------------------- |
| Python      | OHOS 有 3.12/3.13/3.14/3.15；3.15 真机可跑，musllinux wheel 可安装并自动签名 |
| Python 包   | 文档常用包大多可用；matplotlib 没有 musllinux aarch64 wheel                  |
| Pandoc      | 有 OHOS 预编译包/PyPI 二进制；`selfsign` 后真机可运行                        |
| selfsign    | 可执行文件和 `.so` 均可签名，`.so` 可 `dlopen`                               |
| qpdf        | 有 OHOS bottle/库；pikepdf 内置 qpdf 库                                      |
| Poppler     | 有 OHOS 预编译构建；没有 brew formula，CLI 打包未验证                        |
| LibreOffice | 有 `soffice 1.0.1` headless 制品；转换 filter/版式未验证                     |
| 与上游距离  | 即使资源可用，也要重做 Python 资源布局、CLI 入口、签名和版本锁；不是直接复用 |

## 5. 什么情况下重启

只有满足至少一项，再重新评估：

1. 上游正式支持 OHOS/linux-arm64 预装目标，并提供资源 recipe/签名钩子；
2. 产品明确要求鸿蒙端文档转换，且接受独立项目成本；
3. OHOS Python/LibreOffice 端口达到可长期维护的稳定度，matplotlib 有可用的 wheel 或稳定构建；
4. 只需要“用户自己装工具”的开发者路径，不需要产品化预装/UI。

重启时先重新核对上游合同（catalog → manifest → installation.json → bin/PATH → 插件），不要直接恢复旧方案。
