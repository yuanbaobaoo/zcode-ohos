# 13 本机电脑控制

ZCode 在 HarmonyOS 本机上执行 Computer Use：截图、点击/拖拽/滚动、输入、按键、窗口与应用状态、
跨应用拉起、帧流录屏。执行端是随包的 **ArkTS 服务**，不经 hdcd / 开发者模式；只要用户授予
「辅助操作 + 截屏」两个系统权限即可工作。

## 目标与非目标

**目标**：复用上游 CUA 的工具面与调用链，只在 runtime 实现层接一个 OHOS 后端；设置页可门控、
状态可回流、权限丢失可回收。

**非目标**：不做审批 UI（沿用 CUA 既有授权流程）；不恢复 dev 档 hdcd 控制动作；不实现原生
AVScreenCapture 录屏（需 manual_settings + 指纹，三方不可代劳）。

## 架构

```text
Renderer（CUA 插件 / 设置页）
  │  IPC：desktop:computer-control:status / request（preload → main）
  ▼
main（desktopOhosComputerControlPermission.ts）
  │  读 status.json、watch 目录；写 permission.request
  ▼
文件桥 <haps>/electron/files/computer-control/
  │  token.json / status.json / permission.request / cmd-*.json / ack-*.json
  ▼
ArkTS ComputerControlService（EntryAbility 内，1s 轮询）
  │  screenshot.capture、inputEventClient、bundleManager、startAbility
  ▼
系统能力
```

- **唯一写入方**：ArkTS 写 `status.json`；main 只读并通过目录 watch 推给 renderer。
- **命令协议**：main/Node 侧写 `cmd-<id>.json`（带 token），ArkTS 校验 token、执行、写
  `ack-<id>.json`；文件即协议，不依赖 socket（沙箱对 UDS bind 有限制）。
- **路径单一来源**：`packages/desktop/src/main/ohos/paths.ts`（`OHOS_BRIDGE_PATHS`），
  ArkTS 侧用同样的目录名，契约测试钉住。

## 权限门禁

`status.json` 一次性回传两个权限与聚合结果：

```json
{ "apiAvailable": true, "permission": "granted",
  "permissions": { "controlDevice": true, "screenCapture": true },
  "capture": "...", "recordings": "...", "updatedAt": 0 }
```

- `granted`（main 推导 + UI 再判）恒等于 `controlDevice && screenCapture`；
  缺任一 → 设置页开关锁定、点击弹授权对话框并列出缺项（`listMissingOhosPermissions`）。
- **授权入口**：`openPermissionOnSetting` 直接打开该权限的系统设置页；不可用时回退应用信息页
  （`application_info_entry`）。`requestPermissionOnSetting` 只接受 user_grant，传 manual_settings
  必报 `12100014`，不再使用（见 [03](./03-平台权限与系统约束.md)）。
- **启动不弹任何授权框**：应用启动、状态回流、权限变化都不弹窗；只在用户点「去开启」时跳设置页。
- **权限丢失回收**：`useOhosCuaPermissionReconcile` 在 App 挂载时读一次状态；权限缺一且插件仍
  启用 → `setEnabled(false)` + toast，开关回到关闭。权限恢复不自动重开。
- **录屏不需要第三个权限**：帧流复用截屏权限；`CUSTOM_SCREEN_RECORDING` 已删除声明。

## 截图

- 唯一产品路径：`@ohos.screenshot.capture({ displayId })` → `PixelMap` → `image.createImagePacker()`
  编码 JPEG（quality 80）→ 落 `computer-control/shots/` → ack 返回路径。
- runtime 读文件转 base64，`provider: "arkts-screenshot"`；失败直接报 `unavailable`，
  不降级到 native/hdcd（历史回退已删除）。
- 真机：3120×2080，单张约 380–540KB，耗时数百毫秒。

## 录屏（帧流）

- `record_start`（fps 1–5，maxFrames 默认 300）→ ArkTS 定时截图落
  `computer-control/recordings/<id>/frame-*.jpg`；`record_stop` 返回
  `{ id, frames, bytes, dir }`，runtime 以 JSON 结果回给模型。
- 这是当前唯一三方可用、无需生物识别的录屏实现；原生 AVScreenCapture 需要 manual_settings
  的「屏幕共享」+ 指纹确认，不作为产品路径。

## 工具面

沿用上游 CUA 的工具与语义：`request_access`、`stop_computer_control`、`list_apps`、
`list_windows`、`get_app_state`、`left_click`、`left_click_drag`、`scroll`、`type`、`paste`、
`key`、`perform_action`、`set_value`、`select_text`，以及 OHOS 接入的 `record_start` /
`record_stop`。

- **拉起**：`get_app_state({ app: { bundle_id } })` 先 `startAbility` 再取状态；拉起失败把错误
  交给模型，不静默截图。
- **元素目标**：无辅助功能树时返回 `element_unavailable` 并指引用坐标；AX 相关动作按契约降级。
- **paste**：只发一个 paste op（文本进剪贴板 + ctrl+v 由 ArkTS 执行），避免逐字符注入。

## 失败模式

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| 工具返回 `not_authorized` | 辅助操作/截屏未授予 | 设置页「去开启」→ 系统设置页 |
| `unavailable`（截图） | 权限被撤销 / 截屏 API 失败 | 检查 `checkScreenCapturePermission` 日志与权限状态 |
| 点击无反应 | 坐标基于旧布局 / 目标窗口失焦 | 先 `get_app_state` 重新取布局 |
| 拉起无效 | bundle/ability 不匹配 | 用 `launch` 校验 bundle 与 EntryAbility 名 |
| `helper_unavailable` | 桥 token 缺失 / ArkTS 未启动 | 重启应用；确认 `bridge ready` 日志 |
| 录屏 0 帧 | 截屏失败 / 权限撤销 | 先验证单张截图 |

## 安全边界

- 桥目录在应用沙箱内，只有应用自身可读写；token 每次启动重新生成，ArkTS 校验后才执行。
- `ohos_hdc` 的控制动作已删除；CUA 是唯一能改设备状态的产品通道（[15](./15-平台适配治理与不变量.md)）。
- 截图/录屏产物落在应用沙箱，模型只拿到当次 base64 或路径。

## 验收

| 场景 | 期望 | 证据 |
| --- | --- | --- |
| 两权限齐 → 开电脑控制 | 开关可开、插件启用 | `bridge ready: api=true permission=granted` |
| 缺截屏 → 开电脑控制 | 开关锁定、对话框列出「截屏」、跳权限设置页 | `openPermissionOnSetting resolved` |
| 撤销权限 → 重启 ZCode | 开关自动关闭并 toast | `permissions refreshed` 两字段变化 |
| 截图 | 3120×2080 JPEG | `screenshot ok: 3120x2080 <bytes>` |
| 录屏 | N 帧、字节数 | `record stopped: frames=5 bytes=…` |
| 拉起 | 目标进程出现 | `launch dispatched: <bundle>` + `ps` |
| 启动 | 不弹任何授权框 | 冷启动日志无权限请求 |
