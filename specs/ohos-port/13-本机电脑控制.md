# 13 本机电脑控制

ZCode 在 HarmonyOS 本机上执行 Computer Use：截图、点击/拖拽/滚动、输入、按键、窗口与应用状态、
跨应用拉起、帧流录屏。执行端是随包的 **ArkTS 服务**，不经 hdcd / 开发者模式；只要用户授予
「辅助操作 + 截屏」两个系统权限即可工作。

## 目标与非目标

**目标**：复用上游 CUA 的工具面与调用链，只在 runtime 实现层接一个 OHOS 后端；设置页可门控、
状态可回流、权限丢失可回收。

**非目标**：不做审批 UI（沿用 CUA 既有授权流程）；不恢复 dev 档 hdcd 控制动作；不实现原生
AVScreenCapture 录屏（需 manual_settings + 指纹，三方不可代劳）。

## 架构

```text
Renderer（CUA 插件 / 设置页）
  │  IPC：desktop:computer-control:status / request（preload → main）
  ▼
main（desktopOhosComputerControlPermission.ts）
  │  读 status.json、watch 目录；写 permission.request
  ▼
文件桥 <haps>/electron/files/computer-control/
  │  token.json / status.json / permission.request / cmd-*.json / ack-*.json
  ▼
ArkTS ComputerControlService（EntryAbility 内，1s 轮询）
  │  screenshot.capture、inputEventClient、bundleManager、startAbility
  ▼
系统能力
```

- **唯一写入方**：ArkTS 写 `status.json`；main 只读并通过目录 watch 推给 renderer。
- **命令协议**：main/Node 侧写 `cmd-<id>.json`（带 token），ArkTS 校验 token、执行、写
  `ack-<id>.json`；文件即协议，不依赖 socket（沙箱对 UDS bind 有限制）。
- **路径单一来源**：`packages/desktop/src/main/ohos/paths.ts`（`OHOS_BRIDGE_PATHS`），
  ArkTS 侧用同样的目录名，契约测试钉住。

## 权限门禁

`status.json` 一次性回传两个权限与聚合结果：

```json
{
  "apiAvailable": true,
  "permission": "granted",
  "permissions": { "controlDevice": true, "screenCapture": true },
  "capture": "...",
  "recordings": "...",
  "updatedAt": 0
}
```

- `granted`（main 推导 + UI 再判）恒等于 `controlDevice && screenCapture`；
  缺任一 → 设置页开关锁定、点击弹授权对话框并列出缺项（`listMissingOhosPermissions`）。
- **授权入口**（按缺失项分流，2026-11-16 真机修正）：
  - 缺截屏 → 应用信息页（`application_info_entry`）：该页同时有「截屏」「辅助操作」开关；
    PC 上 `requestPermissionsFromUser` 对截屏秒拒，`openPermissionOnSetting` 也不为它弹面板。
  - 只缺辅助操作（manual_settings）→ `openPermissionOnSetting` 专用设置页；不可用时回退应用信息页。
  - 截屏已授权时旧实现仍去开辅助操作页，`SelectedResult.GRANTED=1` 不弹任何界面，
    用户观感是「点击无反应」；分流后必定落到有开关的页面。
  - `requestPermissionOnSetting` 只接受 user_grant，传 manual_settings 必报 `12100014`，不再使用
    （见 [03](./03-平台权限与系统约束.md)）。
- **启动不弹任何授权框**：应用启动、状态回流、权限变化都不弹窗；只在用户点「去开启」时跳设置页。
- **权限丢失回收**：`useOhosCuaPermissionReconcile` 在 App 挂载时读一次状态；权限缺一且插件仍
  启用 → `setEnabled(false)` + toast，开关回到关闭。权限恢复不自动重开。
- **录屏不需要第三个权限**：帧流复用截屏权限；`CUSTOM_SCREEN_RECORDING` 已删除声明。

## 工具面适配（P0，2026-11-16）

真机会话 `sess_d642b25a…`（桌面 tttt）暴露了四处断链，按下面规则修：

- **`app_ref` 才是 SDK 字段**：解析顺序 `app_ref` → `app` / `app_id` / `target_app`；`{name}`
  允许走内置别名（default browser / browser / 浏览器 → `com.huawei.hmos.browser`）。
  之前只读 `app` 系列，拉起路径从未执行，`get_app_state` 永远落到伪桌面。
- **拉起用 launcher want**：`{bundleName, action:"ohos.want.action.home",
entities:["entity.system.home"]}`；失败再回退显式 `EntryAbility`。真机实证：浏览器
  `com.huawei.hmos.browser` 用显式 `EntryAbility` 报 ability not found，launcher want 成功。
- **不枚举应用**：公开 SDK 没有 bundle 列表 API（`getAllBundleInfo` 不存在，
  `getVisibleWindowInfo` 需 `VISIBLE_WINDOW_INFO` → 201）。`list_apps` 返回伪桌面 + 内置候选
  （浏览器/Chromium/设置/文件/记事本/计算器）并明示“非完整列表”；不编造应用。
- **文本输入默认走剪贴板**：`type` 与 `paste` 同样落 `paste` op（pasteboard + KEYCODE_PASTE，Ctrl+V 兜底），
  ASCII 也不例外——KeyCode 注入必被输入法截获（真机实证：地址栏只落下 `wwwbai`，候选
  `bai'du'com`）。只有显式 `strategy:"event"` 才逐字符发 KeyCode。
- **键名兼容 mac 写法**：`Control_L` / `Shift_L` / `Alt_L` / `Meta_L` / `Cmd_L` 归一化为
  `ctrl_left` / `shift_left` / `alt_left` / `meta_left`；`Return`/`Esc`/`Del` 同样归一。
- **无 AX 也返回可动作状态**：`get_app_state` 恒返回 visual mode + 截图，附带 `display`、
  `windows`（窗口矩形）与 `target_window`；`getApp()` 不再因缺 elements/window 被客户端拒绝。
- **状态真实值**：`bridge_alive` 读 token/status 文件；`screen_recording` 用最近一次截图结果；
  截图结果补 `width`/`height`。

**发布注意**：CUA 工具面实际由 `node-repl-host` 插件的 `dist/mcp/server.js` 携带
（`@zcode/zcode-cua` 在构建时被打进该 bundle）。只改 `packages/zcode-cua` 不会进入 HAP，
必须同时重建 `@zcode/node-repl-host`；而已安装设备会复用旧插件缓存——发布时要同时 bump
`apps/zcode-cli/packages/node-repl-host/package.json` 与
`bootstrap/src/app/official-plugin-definitions.ts` 里 `node-repl-host` 的 `version`
（`0.7.0 → 0.7.1`），让 seed marker 版本不匹配后重新 seed（真机实证 2026-11-16）。

## 单应用前台会话（P1，2026-11-16）

鸿蒙三方应用无法创建虚拟屏、无法后台输入、也无法读其它应用的 AX。P1 用“单应用前台”
逼近 mac/win 的 PiP 隔离：

1. `get_app_state(app_ref)` 拉起目标应用，由系统把它前置；ZCode 留在后面（不最小化，
   避免异常退出后窗口不恢复）。
2. `window_layout` 桥命令返回 `window.getAllWindowLayoutInfo(0, {excludeSystemWindows:true})`
   的矩形与自身窗口矩形；排除自身后取面积最大的窗口作为 `target_window`。
   真机实证（API 26）：该 API 三方可用；`supportsFocus` 之外的 `getVisibleWindowInfo` 不可用。
3. 截图为**整屏**，坐标仍是全屏坐标——不做裁剪/偏移，避免 frame 状态丢失导致点击错位；
   `target_window` 只作为诊断与视觉参照返回给模型。
4. `stop_computer_control` 清理会话缓存；下一次 `get_app_state` 重新取窗口矩形。
5. 只有“移除自身窗口 + 目标窗口是最大窗口”这一条启发式，判定失败时 `target_window` 缺省，
   模型按整屏坐标操作（fail-open 到整屏，不误加偏移）。

## 后续：虚拟屏（HarmonyOS 26.1）

用户 2026-11-16 提示：鸿蒙 26.1 起支持创建虚拟屏幕，可用来做真正的隔离。当前 SDK
（API 26）已可见以下公开接口，记录备查，**本期不实现**：

- `display.createVirtualScreen(config)`（since API 16，`@ohos.display`）→ `Promise<screenId>`；
  `display.setVirtualScreenSurface(screenId, surfaceId)`、`display.destroyVirtualScreen(screenId)`。
- `VirtualScreenConfig`：`name`、`width`、`height`、`density`、`surfaceId`、`supportsFocus?`（22+）。
- 权限：`ohos.permission.ACCESS_VIRTUAL_SCREEN`（system_basic / system_grant / 可 ACL 跨级），
  与现有受限权限一样需要在 AGC Profile 申请 ACL。
- 配套：`startAbility(want, { displayId })` 把目标应用拉到虚拟屏（`StartOptions.displayId` 公开）；
  `screenshot.capture({ displayId })` 可直接截虚拟屏。
- 未验证：`inputEventClient` 注入事件没有 `displayId` 参数，虚拟屏上的窗口能否收到全局输入
  取决于 `supportsFocus` 与输入路由，需 26.1 真机验证；若不可注入，只能做“只读观测/演示”。

## 截图

- 唯一产品路径：`@ohos.screenshot.capture({ displayId })` → `PixelMap` → `image.createImagePacker()`
  编码 JPEG（quality 80）→ 落 `computer-control/shots/` → ack 返回路径。
- runtime 读文件转 base64，`provider: "arkts-screenshot"`；失败直接报 `unavailable`，
  不降级到 native/hdcd（历史回退已删除）。
- 真机：3120×2080，单张约 380–540KB，耗时数百毫秒。

## 录屏（帧流）

- `record_start`（fps 1–5，maxFrames 默认 300）→ ArkTS 定时截图落
  `computer-control/recordings/<id>/frame-*.jpg`；`record_stop` 返回
  `{ id, frames, bytes, dir }`，runtime 以 JSON 结果回给模型。
- 这是当前唯一三方可用、无需生物识别的录屏实现；原生 AVScreenCapture 需要 manual_settings
  的「屏幕共享」+ 指纹确认，不作为产品路径。

## 工具面

沿用上游 CUA 的工具与语义：`request_access`、`stop_computer_control`、`list_apps`、
`list_windows`、`get_app_state`、`left_click`、`left_click_drag`、`scroll`、`type`、`paste`、
`key`、`perform_action`、`set_value`、`select_text`，以及 OHOS 接入的 `record_start` /
`record_stop`。

- **拉起**：`get_app_state({ app: { bundle_id } })` 先 `startAbility` 再取状态；拉起失败把错误
  交给模型，不静默截图。
- **元素目标**：无辅助功能树时返回 `element_unavailable` 并指引用坐标；AX 相关动作按契约降级。
- **paste**：只发一个 paste op（文本进剪贴板 + ctrl+v 由 ArkTS 执行），避免逐字符注入。

## 失败模式

| 症状                      | 原因                          | 处理                                               |
| ------------------------- | ----------------------------- | -------------------------------------------------- |
| 工具返回 `not_authorized` | 辅助操作/截屏未授予           | 设置页「去开启」→ 系统设置页                       |
| `unavailable`（截图）     | 权限被撤销 / 截屏 API 失败    | 检查 `checkScreenCapturePermission` 日志与权限状态 |
| 点击无反应                | 坐标基于旧布局 / 目标窗口失焦 | 先 `get_app_state` 重新取布局                      |
| 拉起无效                  | bundle/ability 不匹配         | 用 `launch` 校验 bundle 与 EntryAbility 名         |
| `helper_unavailable`      | 桥 token 缺失 / ArkTS 未启动  | 重启应用；确认 `bridge ready` 日志                 |
| 录屏 0 帧                 | 截屏失败 / 权限撤销           | 先验证单张截图                                     |

## 安全边界

- 桥目录在应用沙箱内，只有应用自身可读写；token 每次启动重新生成，ArkTS 校验后才执行。
- 设备调试工具（`ohos_hdc`）已移除，改由 agent 经 `hdc` CLI 调试；CUA 仍是唯一能改设备状态的产品通道（[15](./15-平台适配治理与不变量.md)）。
- 截图/录屏产物落在应用沙箱，模型只拿到当次 base64 或路径。
