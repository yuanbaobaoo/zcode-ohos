# 上游 ZCode v3.16.1 合并方案

- 状态：已完成（2026-10-21 分层提交：上游基线 `aac8e891`，OHOS 层 `66d81f66`）
- 日期：2026-10-19
- 范围：把上游 `0a1fc56d279fd1001f78387bd81aec1c26767411`（ZCode v3.16.1）合入 ZCode-ohos
- 原则：业务架构跟随上游；鸿蒙平台面与运行环境完整保留；兼容层薄、集中、可测试

## 0. 摘要

这次合并不能按普通 Git 合并处理。上游是 v3.15.1 → v3.16.1 的整包同步，包含 Project-first、远程 R3、Relay V2、Office viewer、ToolSearch、存储迁移和架构治理等大改；同时默认运行在 Node 24 / 标准桌面 Electron 环境。ZCode-ohos 运行在 OHOS Electron / Node 20.18.1，并有一整套必须保留的平台适配：关于页、引导页、帮助菜单裁剪、全盘权限、HiShell、brew 环境、终端 PTY、系统浏览器、碰一碰、更新检查、文件管理器、HAP 构建等。

方案的核心判断是：

> 业务语义、数据模型、状态所有权、协议、迁移规则全部跟随上游；
> 鸿蒙平台面与运行环境全部保留；
> “轻量兼容层”指实现方式要薄、集中、可替换，不指删掉鸿蒙定制。

最优先的三项工作：

1. 用集中式 `node:sqlite` shim 解决 Main/Host/Agent 启动崩溃；
2. 用 polyfill 解决 Node 20 缺少 `Promise.withResolvers`；
3. 按“上游终端逻辑 + OHOS PTY 中继/墓碑 + 上游 buffered output”合并 `terminalService`，并保证全盘权限提示、关于页、引导页、帮助菜单裁剪不被上游结构变化吞掉。

### 1.1 提交事实

- 提交：`0a1fc56d279fd1001f78387bd81aec1c26767411`

### 1.2 上游主要变化

| 领域      | 变化                                                                                    |

### 1.3 为什么不能直接 merge

merge-tree 演练结果：19 个文本冲突。但真正危险的是自动合并成功的静默破坏：

- 新增文件直接 `import "node:sqlite"`，绕过 OHOS 的 `loadNodeSqlite()`；
- 新代码使用 `Promise.withResolvers`，Node 20.18.1 没有；
- 上游终端服务无条件加载 node-pty，与 OHOS PTY 中继冲突；
- 上游删除 Toast 的 `bottom-right`，OHOS 全盘权限提示会编译失败或静默消失；
- Office MCP server 构建 target 是 node24，OHOS Electron 是 Node 20；
- 新进程路径需要重新确认 brew/HiShell 环境继承；
- 数据根切换、项目迁移、旧远控配对失效需要单独处理。

## 3. 风险与后果

### 3.1 P0：不处理会启动失败或核心功能不可用

#### 3.1.1 新文件绕过 `node:sqlite` 兼容层

新增文件：

- `packages/services/src/onboarding/localUsageEvidence.ts`
- `packages/shared/src/sqlite-migrations/backup.ts`
- `packages/shared/src/sqlite-migrations/restore.ts`
- `packages/services/src/session/controllerRemoteIdentityMigration.ts`
- `packages/services/src/session/sourceServerWorkspaceAliasRepo.ts`

它们被以下模块在顶层加载：

- `packages/services/src/node.ts`
- `packages/services/src/session/tasksDatabase/migrations.ts`
- `apps/zcode-cli/packages/adapters/src/storage/session-store/migration-runner.ts`

后果：

- Main 早期 bootstrap 导入 `@zcode/services/node` 时加载 `localUsageEvidence`，直接触发 `node:sqlite` 缺失；
- Host 导入 `services/node.ts` 时加载远程迁移 repo；
- CLI migration runner 导入共享 `sqlite-migrations` 时加载 `backup/restore`；
- 可能出现 `ERR_UNKNOWN_BUILTIN_MODULE`，应用在窗口创建前崩溃。

已确认：

- fork 之前改过的 `taskIndexRepo`、`automationRepo`、`offPeakTaskRepo`、`sqlite-session-store`、`project-storage/startup` 在 merge-tree 中保留了 `loadNodeSqlite`；
- 问题集中在**本次新增文件**。

#### 3.1.2 `Promise.withResolvers`

`packages/services/src/zcode-agent/zcodeAgentProcessManager.ts:1121` 新增该 API，位于每次 spawn Agent 的路径上。Node 20.18.1 没有 `Promise.withResolvers`（Node 22 才加入），仓库没有 polyfill。后果是每次新建会话/启动 Agent 抛 TypeError。

已有相同风险：

- `apps/zcode-cli/packages/core/src/tool/executor/permission-request.ts:39`
- `apps/zcode-cli/packages/bootstrap/src/zcode-protocol/interaction-broker.ts:71`

#### 3.1.3 终端服务合并

`packages/services/src/terminal/terminalService.ts` 是冲突文件：

- 上游新增 `createBufferedTerminalOutputEmitter()`，修复远端终端首批输出丢失；
- 上游在 `create()` 里无条件执行 `loadNodePtyModule()` / `ensureNodePtySpawnHelperExecutable()`；
- 上游 `getTerminal()` 对未知 id 直接抛错；
- OHOS 走 `dependencies.ptyTransport`，由 Main 进程中继 PTY，并保留 tombstone 防止晚到订阅拖死 Host。

如果直接取上游：

- OHOS 会尝试 node-pty 路径，绕过 PTY 中继；
- 终端秒退/晚到订阅可能重新导致 Host 崩溃；
- 之前修复的“终端空白”可能回归。

如果只保留 fork：

- 丢失上游 buffered output 修复。

#### 3.1.4 全盘权限提示被 Toast 结构变化吞掉

上游 `toast.tsx` 删除 `"bottom-right"` 和对应 stack。OHOS `OhosFullDiskAccessPrompt.tsx:41` 仍使用：

```ts
position: "bottom-right";
```

后果：

- TypeScript 编译失败；
- 即使绕过类型，ToastHost 不再渲染 bottom-right，提示静默消失；
- 违反 `specs/ohos-port/08` 的右下角一次性提示要求。

### 3.2 P1：数据、平台面与构建

- 数据根在授权后切换，沙箱与真实 home 可能出现两套数据库；
- 3.15.1 用户升级，项目迁移读不到旧 settings 时会出现“项目消失”的感知；
- 旧远程工作区、旧 Web 远控配对在 R3/Relay V2 下失效；
- 新的 `selectDirectories` 多选与 OHOS 系统选择器能力不匹配；
- Office viewer 的 MCP server 构建 target 是 node24，OHOS Electron 是 Node 20；
- 上游删除 `prepare-prebuilds`，远程资源入口改到 `@zcode/server-cli`；
- 根 `prepare` 新增 `build:cua`，typecheck/pre-push 增加新门禁；
- 架构治理新增 `unmanaged-new-file` / 上游快照准入，OHOS 平台代码需要登记。

### 3.3 P2：UI 与发布

- 新 Project 侧栏替换旧 Workspace 侧栏，旧 workspace tab/视图偏好需要验证；
- 帮助菜单/关于/引导页/设置页结构变化，需要重新接线；
- 插件市场新增 UI surface、社区分段、项目级覆盖；
- Office viewer 首次进入 HAP，体积、内存、插件沙箱需要验证；
- CUA 占位、更新提示、分享接收、文件管理器需要回归。

## 4. 兼容层设计

### 4.1 Node 20 运行时 shim

目标：上游业务代码零改动，所有 `node:sqlite` 和 Node 22 API 在 OHOS 自动落到兼容实现。

#### 4.1.1 `node:sqlite` 构建期重写

- 在 `apps/zcode-cli/packages/cli/scripts/build.mjs` 和 `packages/desktop/tsup.config.ts` 增加 OHOS 构建插件/alias。
- 把所有静态 `node:sqlite` import/require 重写到 `@zcode/shared/ohos/node20/sqliteShim`。
- shim 导出 `DatabaseSync`、`backup`、`version`，内部调用 `loadNodeSqlite()`。
- 对 `createRequire(...)("node:sqlite")`、`require("node:sqlite")`，在 Main/Host/Agent 早期 bootstrap 用 `Module._load` 钩子拦截。

#### 4.1.2 `Promise.withResolvers` polyfill

- 在 Main、Host、Agent CLI 的最早 bootstrap 注入。
- 不修改 `zcodeAgentProcessManager` 等业务调用点。

#### 4.1.3 Node 20 API 守卫

- CI 扫描 `node:sqlite`、`Promise.withResolvers`、`fs/promises.glob` 等高风险 API。
- 新增文件若直接使用，必须显式登记或走 shim。

#### 4.1.4 验收

- OHOS 上 Main 启动、Host 加载、Agent spawn、CLI migration 均不出现 `ERR_UNKNOWN_BUILTIN_MODULE` / `withResolvers is not a function`。

### 4.2 终端与 HiShell/brew

原则：`terminalService` 业务逻辑跟上游，OHOS 只保留 transport 与可靠性适配。

合并方式：

- 保留 `dependencies.ptyTransport` 分支；
- 保留 `OhosRelayPty`、`desktopTerminalPtyRelay`、早退闩锁/tombstone；
- 引入上游 `createBufferedTerminalOutputEmitter()`；
- 非 OHOS 才执行 `loadNodePtyModule()` / `ensureNodePtySpawnHelperExecutable()`；
- `getTerminal` 的未知 id 行为在 OHOS 保持 fork 的容错，避免 Host 退出。

HiShell/brew 环境链：

```text
main early bootstrap
  → 重放登录 shell env
  → host 入口再次重放（host 不继承 main env）
  → agent spawn 继承
  → terminal 使用 shell hint + relay
  → MCP 子进程继承 agent env
```

新增进程路径核对：

| 新路径                           | 环境风险                                               | 处理                                     |
| -------------------------------- | ------------------------------------------------------ | ---------------------------------------- |
| `database-startup` worker        | worker_threads 继承 env                                | 验证 sqlite shim 与 brew PATH            |
| 官方插件 MCP（Office viewer）    | 上游改为 `process.execPath` + `ELECTRON_RUN_AS_NODE=1` | 不依赖 brew node；验证 Node 20 兼容      |
| Office server 构建               | target 是 node24                                       | OHOS 构建 target 调到 node20，或实测兼容 |
| Source Server 本地/远程进程      | 远程用远端 shell；本地 spawn 需确认 env                | 补充环境传递                             |
| `provider refresh` / 其他 Worker | 继承 Host env                                          | 验证                                     |
| 非官方 MCP `command: "node"`     | 依赖 PATH                                              | 确认 `buildMcpStdioEnv` 保留 brew PATH   |

验收：

- 有 brew：agent 能执行 `git`、`node`、`java`；终端能起 zsh；MCP 能起；Office viewer 能打开。
- 无 brew：agent/terminal 回退 `/bin/sh` 或内置 zsh；Office viewer 走 `process.execPath` 仍可用；错误提示可理解。
- 授权/重启后：登录 shell 快照更新，PATH 仍正确。
- 终端秒退不会拖死 Host。

### 4.3 全盘权限与产品面

#### 4.3.1 全盘提示

- 不恢复上游 Toast 的 `bottom-right` 业务；
- 把 `OhosFullDiskAccessPrompt` 改成自包含平台组件：自己渲染固定定位卡片、常驻/关闭/操作，不依赖上游 Toast 位置栈；
- 保留 `specs/ohos-port/08` 的右下角行为、一次性标记、设置开关、引导第 4 步。

#### 4.3.2 引导页

- 保留 `OnboardingOsPermissionStep`、第 4 步、跳过语义；
- 适配上游新的 `useOnboardingTrigger`（不再用 settings 兜底）；
- 验证新用户首启、老用户升级、已授权用户、拒绝后再次进入。

#### 4.3.3 帮助/关于

- 保留帮助菜单裁剪（社群/提需求不回来，问题上报走 GitHub）；
- 检查上游新增的帮助菜单挂载点（头部、SettingsPage 两处）；
- 保留 About 入口（帮助菜单 + 应用菜单）；
- 保留 `about.ts` 的 `ohosReleaseVersion`、GitHub 行、去版权行；
- 外链继续走系统浏览器。

### 4.4 数据根与项目迁移

问题：`desktopOhosHomeGrant` 在首窗后切换数据根，不复制沙箱数据，Host 可能已经用沙箱库启动。

方案：

1. 业务服务启动前确定数据根；
2. 如果授权会改变数据根：
   - 暂停 Host/Agent，关闭 SQLite 连接；
   - 把沙箱 `.zcode` 数据树复制到真实 home（平台级数据搬迁，不是业务迁移）；
   - 切换 env/dataBaseDir；
   - 重启应用；
3. 旧绝对路径（例如沙箱 `workspace` 下的项目 cwd）继续可读；不重写业务路径；
4. 上游项目迁移在最终数据根上执行一次；
5. 不做 fork 专属的项目/workspace 迁移逻辑。

验收：3.15.1 数据 → 授权 → 重启 → 项目/会话/设置可见；不出现两套库。

### 4.5 目录选择与平台服务

- 保留 OHOS 系统文件选择器体验；
- 上游新增 `selectDirectories`：
  - 支持多选则实现平台 adapter；
  - 不支持则不暴露能力，让上游 ProjectEditor 自动回退 Host 目录浏览；
- 不在 ProjectEditor 加 OHOS 专属业务分支；
- 全盘权限错误映射为可操作提示。

### 4.6 更新、浏览器、分享、文件管理器

- 更新：保留 OHOS GitHub tag 版本线、跳过上游 force update；对齐上游更新 UI，不 fork 流程。
- 系统浏览器：保留统一 `openExternal`；帮助/关于/更新/登录链接继续走。
- 分享：保留 `desktopOhosShareInbox`；上游 attachment/root effects 变化后重测。
- 文件管理器：把 `OHOS_EDITOR_DEFS` 作为上游 `fileApplications` 的 provider 接入。

- 业务/协议/项目/远程/UI 结构：上游；

#### 12.1.1 崩溃三方向探查结论（2026-10-20，faultlogger 实证）——**后被证伪，见 §12.1.2**

~~对 host（NodeService）V8 `CollectGarbage` SIGABRT 崩溃，三个修复方向逐一探查：~~

- **方向 3：agent 改独立子进程——不可行（此架构事实不变）**。OHOS 的 MAC 拦「应用域 exec 二进制」，`child_process.spawn` 任意外部 ELF 被拒（`resolveOhosWorkerZCodeAgentCommand` 注释实证：「HNP execPath ENOENT」「child_process.spawn 不可用」，当初因此改进程内 Worker）；设备无独立 node 二进制，唯一 node 运行时是 Electron 自身（`process.execPath`），spawn 它同样被拦。agent 只能走 Worker。终端 spawn shell 可用是走了 main 进程管道/PTY，不是 spawn 外部 ELF。
- **方向 2：降包体积——不治本（当时分析保留）**。host bundle 30M（纯 JS 10.2M）、agent zcode.cjs 14.5M，比 3.15.1 涨约 1/3，但大头是 zod schema + services 业务代码；运行期内存压力来自运行期对象而非纯 bundle 大小。
- **方向 1：平台层——根因在此。此结论错误**：当时把崩溃栈顶 `Heap::CollectGarbage` 当作平台 GC 缺陷，实为 OOM 落点（崩溃时 RSS 4.3GB / 23s 生命周期是当时未注意到的决定性证据）。真实根因与三方向无关，是 stdout 协议污染引发的 agent 重生循环（§12.1.2）。

教训：**崩溃栈顶是「死亡姿势」不是「病因」；faultlogger 的 `Process Memory(Rss)` 与 `Process life time` 应先于栈帧被分析**——4.4GB/23s 直接指向「内存被快速吃光」，而非「GC 配置缺陷」。

#### 12.1.2 崩溃根治与运行时基线更新（2026-10-20，同一模拟器实证闭环）

**根因链（全链路实证）**：agent 是 host 进程内 stdio 协议 Worker（zcode.cjs）。Worker 加载 sqlite 后端时 `console.log` 打 `[ohos-sqlite] backend loaded`——**console.log 落 stdout，与 JSON-RPC 协议帧共用一个管道**；宿主 `ZCodeStdioTransport.handleStdoutFrame` 对该行 `JSON.parse` 失败 → `fireClose(protocol_parse_error)` → 协议客户端关闭 → 进程管理器重生 agent → 旧 Worker 的 `exit` 事件在 OHOS worker_threads 上不触发（装机实证：stdout close/exit 探针均未见 exit），旧 isolate 不被回收 → 每 ~0.6s 一轮新 Worker（150MB+）→ 23s 内 RSS 冲到 4.4GB → V8 `Allocation failed` abort。

**修复**（三处，全部必要）：

1. `nodeSqliteCompat.ts` 两处 `console.log` → `console.error`（协议 stdout 只承载 JSON-RPC 帧；stderr 是诊断通道）。
2. `build-ohos.mjs`：`patchOhosNodeSqliteStaticImports` 调用顺序从 stageApp **之前**移到**之后**（stageApp 会 rm 重建 appDir，先打补丁必被清空——合并期引入的顺序回归，当日直接导致 main 进程 `ERR_UNKNOWN_BUILTIN_MODULE` 弹窗）；shim 写出增加内容校验（`join("\\n")` 转义错误曾把 shim 写成单行巨型注释，构建期现在硬失败）。
3. 诊断补强：`ZCodeStdioTransport.fireClose` 对异常关闭（有 reason/非零 code/有 signal）落 warn 日志并带 `frameHead`（此前 close reason 完全不可见）；agent Worker stderr 实时落 serviceLogger（此前只在非预期退出时随 stderrTail 落盘）。

**运行时基线顺带更新**：排查期间发现 `electron-ohos-runtime@1.0.0`（npm，华为鸿蒙团队 Chromium 132 构建的社区分发，文件时间 2026-10-01，比此前 v34.5.4-20250918.1 日构建多一年 OHOS 补丁），同为 Chromium 132.0.6834.161 / V8 13.2.152.36 / Node 20.18.1，实测与现有 pak/icudtl/v8_context_snapshot 资源、启动器、NAPI 绑定（zcode_sqlite/pty/ohos_sqlite_adapter）全兼容。三件套已替换（libelectron.so 不入库走 `fetch-ohos-libelectron.mjs`，默认源已切到该 npm 包；libadapter.so/libffmpeg.so 为入库产物，已同步替换）。io_uring 补丁脚本 `ohos-patch-libelectron.mjs` 改为**动态锚定**（按 UV_USE_IO_URING 字符串地址反查 adrp/add 引用对，不再硬编码指令字节），新旧基线通吃且幂等。

**结论：崩溃与运行时版本无关，升级不换崩溃修复；新基线是否保留见下**。崩溃修复后新基线全功能实测通过（终端敲命令回显、选模型发消息收回复、设置/菜单/会话历史），保留新基线（多一年平台补丁）；旧基线备份在 `../electron-runtime-backup-34.5.4-20250918.1/`（含 SHA256SUMS），回滚即复制还原。

### 12.6 v40 真机回归与两处 v40 平台行为差异（2026-10-21）

**回归通过（模拟器实测）**：登录态持久化、主界面完整渲染、项目/任务/会话历史、设置页（含全盘权限开关）、全盘权限提示卡（自包含右下角组件在 v40 正常工作）、**AI 消息完整闭环**（发送 → 任务自动命名 → 模型回复「收到」渲染 → 侧栏入库）。自动化通道：主进程 Node inspector（`--inspect` 由厂商 CmdArgsHelper 默认注入）经 `process._linkedBinding("electron_browser_window")` 拿 BrowserWindow，DOM 点击用 `webContents.executeJavaScript`（返回值通道在 v40 上恒为空对象，执行本身有效，盲发即可），文本输入用 `webContents.insertText`。

**差异一：appspawn 子进程禁止 exit(0)** — 宿主的 SIGTERM/disconnect/uncaughtException 退出路径直接 `process.exit()`，v40 的 NodeService 经 appspawn 拉起，`exit(0)` 被 `appspawn_server.c:69 Unexpected call: exit(0)` 拦截并 SIGABRT（faultlogger 实证，堆栈 node::Exit→DefaultProcessExitHandler→ChildMain）。修复：`exitHostProcess()`（host/index.ts）——OHOS 上设置 `process.exitCode`、断开 parentPort 让事件循环排空、3s 后 SIGKILL 兜底；非 OHOS 保持 `process.exit()`。修复后应用退出不再产生崩溃记录。

**差异二（未解，当前唯一阻塞）：v40 主进程内 spawn 子进程会被沙箱静默击杀** — 现象：打开终端面板后 ~180ms，主进程（pid 实证）无日志、无 faultlogger、无 crashpad dump 地整体消失，AMS 记录 `PROCESS_KILL` 并回收全部子进程；可复现。定位：A/B 实验禁用 main 侧 PTY relay（`shouldAttachTerminalPtyRelay`）后开终端应用完整存活（终端仅报 node-pty prebuild 缺失），证明击杀点在 relay 的 `child_process.spawn`；再在主进程内直接 `process.binding("spawn_sync").spawn("/bin/sh", ...)`，连接立即断开、进程归零，确证 **spawn 本身致命**。132 基线同模拟器同代码路径 spawn 正常（当日终端实测），属 v40 沙箱策略变化（疑 fork/seccomp 策略，待厂商确认）。中继加诊断开关 `ZCODE_OHOS_TERMINAL_RELAY=0` 可临时禁用保应用可用。**下一步**：向 openharmony-sig/electron 确认 v40 是否禁用应用进程 fork/spawn，以及官方推荐的启动原生子进程方式（`childProcessManager.startNativeChildProcess` 或 adapter 的 ChildProcessManager）；若不可用，终端需改为「无 shell 的受限终端」或等待厂商提供 PTY 通道。

### 12.7 v40 终端实现：原生子进程通道（原型已验证）

**背景**：v40 沙箱禁止应用进程 fork/spawn（§12.6），终端不能再用 `child_process`。

**机制（已落地）**：
- 主进程先 `net.createServer` 监听沙箱内 unix socket（`userData/zcode-pty/*.sock`）。
- 主进程经 NAPI 桥 `zcode_ohos_process.node` 调 `OH_Ability_StartNativeChildProcess("libzcode_pty.so:Main", args)`（`args.entryParams` 行式传递 socketPath/shell/cwd/argv）。
- appspawn 拉起原生子进程 → `libzcode_pty.so` 的 `Main` 连接 socket、`dup2` 到 0/1/2、`execv` 随包 zsh。
- Relay 以 socket 作为会话流，沿用回显/墓碑协议；失败降级为报错，不再触发 spawn。

**真机实证（模拟器）**：连续 4 次 `[ohos-pty] session N spawned (native-child) shell=.../tools/zsh/zsh pid=...`，子进程均成功连接并 exec。

**三个关键坑（都已解决）**：
1. NAPI 桥不能链接 `libchild_process.so`——addon 会静默加载成空导出；改为运行时 `dlopen`+`dlsym`。
2. 子进程库不能用 C++ 标准库——appspawn dlopen 时不带 `libc++_shared`（`Error relocating ... std::__n1`），子进程库改为零 std 依赖的 C 风格实现。
3. addon 需 `-DNAPI_VERSION=8`；addon 与宿主库经 HAP `libs/arm64-v8a/` 打包（安装后映射 `/data/storage/el1/bundle/libs/arm64/`），addon 从该路径加载。

**未完成**：v40 上终端面板组件未挂载（DOM 实测 `.xterm=0`，而 host 侧会话已创建）——属渲染层状态/挂载问题，与原生通道无关，下一步排查。

**终端面板不展开的两个后续根因（已修复，真机验证）**：
1. **随包 zsh 起不来 → 会话立即退出 → 面板自动收起**：zsh 的 `libncursesw.so.6`/`libtinfo.so.6` 在同级 `lib/` 下，appspawn 子进程没有该搜索路径（132 时代靠试跑探测降级 /bin/sh，迁移时探测被移除）。修复：子进程 exec 前注入 `LD_LIBRARY_PATH=<shell目录>/lib` 与 `TERM=xterm-256color`；exec 失败再依次回退 `libs/arm64/libzsh.so`（随包 zsh 镜像到可执行 libs 区）与 `/bin/sh`。注意：resfile 下 zsh 的 exec 本身是允许的，失败原因是动态库缺失，不是 noexec。
2. `Terminal` 在会话退出时会调用 `onClose` 收起面板（设计如此），所以 shell 起不来时表现为「面板闪一下消失」，容易误判为 UI bug。

**最终实证**：面板展开、zsh 提示符 `localhost%` 出现、输入 `echo OHOS_TERMINAL_OK $((40+2))` 回显 `OHOS_TERMINAL_OK 42`、提示符回归——终端链路（renderer→host→main→原生子进程→zsh→回显）全部打通。

### 12.8 Office/MCP 进程启动：窄适配（平台层，业务零改动）

**实证根因**（纠正早期假设）：
- 错误原文：`spawn /data/storage/el1/bundle/libs/arm64/electron EACCES`——NodeService 的 spawn API 本身可用，失败在**启动器不可执行**；
- 该启动器是 appspawn 专用包装二进制：libs 路径 execve 被拒（EACCES，终端实测同样 `permission denied`）；resfile 副本可 execve 但缺 `__wrap_malloc/__wrap_realloc/__wrap_free`（依赖 appspawn 的链接环境），无法独立运行；
- 结论：应用进程内无法通过 exec 启动 Electron-as-node，官方插件 MCP（上游用 `process.execPath + ELECTRON_RUN_AS_NODE` 拉起 `__zcode-plugin-host`）必须换一种等价运行方式。

**实现（`packages/shared/src/ohosSpawnCompat.ts`，agent preload 安装）**：
- 只拦截一条契约：`command === process.execPath` 且 args 含 `__zcode-plugin-host`；
- 用 `worker_threads` 在 agent 进程内运行 plugin-host，worker 内还原 argv/env，并把 stdout/stderr/stdin 经 MessagePort 与父进程的 `PassThrough` 桥接（stdout/stderr 严格分离）；`spawn/exit/close/error` 事件、`exitCode/signalCode`、`kill()` 按 ChildProcess 语义补齐；
- 其余 spawn（bash/ripgrep/用户 MCP 命令）原样透传，不做全局替换。

**验证**：`packages/shared/test/ohosSpawnCompat.test.ts` 覆盖 argv/env/三路 stdio/退出码/spawn 事件，通过。真机端到端待账号额度恢复（10-23）后用文档会话触发——office 插件是 session 级插件，其 stdio MCP 只在文档会话中连接；当前 MCP 页显示的失败状态是修复前的历史记录。

### 12.9 终端排版与字体（2026-10-21）

**根因（真机 + CDP 实证）**：OHOS 渲染进程里 `font-family: monospace` 在 DOM 中能落到系统等宽字体，但 xterm 的字符尺寸由 **OffscreenCanvas** 度量，canvas 对 generic monospace 及其常见别名（ui-monospace/SF Mono/Menlo…）全部回退到比例字体（`iiii`/`mmmm` 宽度 28/36），导致列宽与字形不一致或退化成细弱的系统 Noto Sans Mono。仅加 `"Noto Sans Mono CJK SC"` 能恢复等宽，但字形仍偏小、偏细。

**实现**：
- 随包 JetBrains Mono（OFL，latin/latin-ext，400/700，共约 58KB）放到 `packages/ui/src/assets/fonts/`，`styles.css` 以 `"ZCode Terminal Mono"` 声明四个 `@font-face`；字体栈只在 OHOS 且无自定义/系统 profile 时把该字体放到最前（`terminalProfile.ts`），其他平台仍优先 SF Mono/Menlo 等系统字体。
- OHOS 终端默认字号 14px（`OHOS_TERMINAL_FONT_SIZE`）；系统/自定义 profile 给的字号仍优先。
- xterm 排版统一在 `terminalTheme.ts`：行高 1.2、字距 0.2、细竖线稳定光标（`cursorBlink=false`，避免 OHOS DOM renderer 上被感知为整屏闪烁）、`minimumContrastRatio` 4.5；`.xterm` 增加 6/8px 内边距（FitAddon 会扣除 padding），并禁用连字避免多字符合成后错位。
- 字体加载时序：`document.fonts.load("14px ZCode Terminal Mono")` 完成后才把字体栈写进 xterm，再触发一次 fit/PTY resize——否则 canvas 会按回退字体算列，字体生效后网格错位。

**连带修复：无 tty 的换行**。字体切换后真机输出暴露出每行输出向右累积缩进：原生子进程的 stdin/stdout 是 unix socket，不是 pty，内核不会做 ONLCR，shell 发 `\n` 时 xterm 只下移不回车。`NativeChildShellSession` 对子进程输出补 `\r`（跨 chunk 记录上一字符，避免把已有 `\r\n` 改成 `\r\r\n`），提示符尾部的 `%` 残影随之回到上一行行尾（zsh 的 PROMPT_SP 正常行为）。

**验证**：`pnpm typecheck`、`terminalProfile.test.ts`（含 OHOS 字体栈/14px 用例）通过；模拟器实测字体已加载（`ZCode Terminal Mono` 400/700 loaded、canvas i/m 等宽 32/32）、14px、xterm padding 6/8px、行高 22.17px；多行输出全部从列 0 开始，ANSI 颜色、中文回退、粗体与竖线光标正常，原 `%` 残影消失。

### 12.11 终端系统 PATH 与光标闪烁（2026-10-21）

**现象**：终端执行 `ls` 报 `zsh: command not found: ls`；空闲时终端看起来一闪一闪。

**根因**：
- GUI 进程继承的 PATH 只有 `/data/app/bin:/data/service/hnp/bin`，没有 `/usr/local/bin:/bin:/usr/bin`。用户 `.zshrc` 只在 `$PATH` 前置/追加自定义目录，不会补系统目录，最终 `ls` 不可见。`/bin/ls` 本身可执行；`ls /` 的 Permission denied 是应用沙箱不能读根目录，不是命令缺失。
- 闪烁不是整块终端重绘：CDP 采样 2.4s，`.xterm-rows/.xterm-screen` 尺寸稳定、0 次 DOM mutation；只有 `.xterm-cursor` 的 `box-shadow` 按 1s 周期切换，来源是 `cursorBlink: true`。

**修复**：
- 原生子进程 exec 前把 `/usr/local/bin:/bin:/usr/bin` 追加到继承 PATH（保留用户/brew 优先级），并把 `SHELL` 设为实际 shell；`resolveTerminalEnv` 同步补齐系统目录。
- 关闭 `cursorBlink`，保留细竖线稳定光标。

**验证**：模拟器实测 `command -v ls` 返回 `/bin/ls`，`ls` 在当前目录与 `~` 下正常；光标 class 不再含 `xterm-cursor-blink`，连续 2s 采样 `box-shadow` 恒定，终端 DOM 尺寸稳定。`ls /` 仍会 Permission denied，这是应用沙箱不能读根目录，不是命令缺失。
